測ったもの

前回は合成した検査で比べ、次に実際の変換で測ったときは移植が途中だったため、変換だけの簡易版と本物を並べるしかなかった。移植が終わった今は、同じ振る舞いのもの同士で比べられる。

参照実装だった html2md-ps.ps1 は削除済みのため、比較から外してある。実際の変換に 29.6 秒かかることは前回の計測で分かっている。

条件

  • 対象は README.html と notes/10_plan ・ notes/90_rules の 10 ファイル（約 388 KB）
  • 実装ごとに別の作業フォルダへ複製してから変換する。同じ場所へ書くと互いに上書きしてしまう
  • 11 回まわして中央値を採る
  • メモリは時間と別に 1 回だけ測る。同じ実行で測ると、計測の分が時間に乗る

メモリの測り方

ピークの作業セット（PeakWorkingSet64）を採る。終了したプロセスからは 0 しか返らないので、実行中にポーリングして拾う。

出力はファイルへ逃がす。親がパイプを読まずに待つと、バッファが埋まったところで相手が止まる。ポーリングしながら待つ形では、標準出力を繋いだままにできない。

速さとメモリは逆に並ぶ

速い順とメモリの少ない順が、きれいに逆になる。bun は exe の 2.6 倍速いが、メモリは 2.7 倍使う。

公平でないところ

本物どうしの 3 行は、前回と違って公平に読める。同じテストが通る実装で、変換・検査・SVG 切り出しまで同じことをしている。前回「読み取ってはいけない」とした exe と移植版の差は、今回は読み取ってよい。

残る条件は次のとおり。

  • port 版は変換だけ。本物と並べて速さを比べない。.js ・ .mjs ・ .ts の差を見るための表である
  • メモリは 1 回の計測。時間のように中央値を採っていない。数 MB の揺れは意味を持たない
  • ポーリングの間隔を置いていない。短命なプロセスほど取りこぼす可能性がある。今回はどれも 170 ms 以上あり、拾えている
  • exe のビルド時間と tsc の型チェック時間は、頻度が低いので測っていない

node は型注釈を取り除くだけ

node は TypeScript を型注釈の除去だけで走らせる（strip-only）。型以上の意味を持つ構文は通らない。

引数に修飾子を付けて宣言を兼ねる書き方（parameter property）が 1 箇所あり、node で ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX で落ちていた。bun では通るため、この計測まで気づいていない。ランチャーは bun が無ければ node に落ちる作りなので、bun の無い環境では動かない状態だった。

直したのは src/html2md/table.ts の 1 箇所。フィールドの宣言と代入に分けるだけで、振る舞いは変わらない。

読み取れること

1. bun は exe より速い。前回の見込みどおり

前回は条件が揃わず「速い可能性がある」までしか言えなかった。同じことをする実装どうしで、bun 179 ms 対 exe 464 ms。2.6 倍速い。

exe が遅いのは処理ではなく起動と見てよい。port 版（変換のみ）が bun で 75 ms、本物が 179 ms。検査と SVG 切り出しを足しても 100 ms しか増えていない。

2. メモリは C# が最も少ない

29.7 MB 対 79.5 MB。bun は 2.7 倍使う。JavaScript の処理系はヒープを広めに確保してから使うため、小さな仕事でも下がりきらない。

この資料 10 ファイルの変換ではどちらも問題にならない量である。効いてくるのは、同時に何本も走らせるときと、メモリの少ない環境で動かすとき。

3. node も実用の範囲に入る

272 ms。bun の 1.5 倍かかるが、exe よりは速い。メモリは bun より少ない（71.3 MB 対 79.5 MB）。bun の無い環境では node で走らせてよい。

ただしnode は TypeScript の一部の構文を受け付けない（第 3 章）。node でも動くことを、時々でよいので確かめる必要がある。

4. 書き方（js ・ mjs ・ ts）の差は、やはり小さい

書き方bun 起動込みnode 起動込み
.js73 ms168 ms
.mjs76 ms162 ms
.ts75 ms174 ms

数 ms の揺れで、順位に意味は無い。型注釈を入れても速度は変わらない。.ts を選ぶ理由は型であって速度ではない、という前回の結論が、実際の変換でも変わらない。
