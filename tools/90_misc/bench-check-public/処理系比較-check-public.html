check-public の処理系比較

同じ検査を 6 つの処理系で書き、実行時の速さ・事前の段・行数を測った。JavaScript は CommonJS ・ ESM ・ TypeScript の差も測った。どれで実装するかを決めるための材料。

測ったもの

check-public 計画の第 2 章で「検査の本体をどこに置くか」が決まらなかった。推測で決めずに測る。

同じにした条件

  • 同じフォルダを同じ拡張子で走査する（.cs .ps1 .md .html .cmd .txt .json .js、.git ・ tmp ・ etc ・ node_modules は除く）
  • 同じ 4 つの検査を 1 行ずつに当てる（メールアドレス／実体パス／認証情報／キリル・ハングルの混入）
  • 各実装が自分で時間を測って出す（inner_ms）。外側はランナーが測る。差が起動の分になる
  • 21 回まわして中央値を採る

対象はこのプロジェクト自身。143 ファイル・約 22,000 行。プロジェクトが育つと件数も変わるため、比べるときは全実装を同じときに測り直す。

起動 は「起動込み − 検査のみ」。実行行数は空行とコメントだけの行を除いた数。メモリは実行中にポーリングして拾ったピーク作業セットで、時間と別に 1 回だけ測っている（終了したプロセスからは 0 しか返らない）。

1 回呼ぶのにかかる時間

PowerShell だけ桁が違う。棒の薄い部分が起動で、PowerShell は起動だけで 247 ms を使う。ほかの 5 つは起動込みでもそこに届かない。

メモリは実行物の大きさと関係しない

Rust は 4.7 MB の実行ファイルで 5.3 MB しか使わず、C# は 8 KB の実行ファイルで 20.5 MB 使う。実行物の大きさとメモリは対応しない。ランタイムを実行ファイルに抱き込むか、外に置くかの違いが出ているだけである。

PowerShell は 111 MB。ほかの 5 つの合計より多い。時間だけでなくメモリでも桁が違う。同時に何本も走らせる形には向かない。

書く量は逆に並ぶ

いちばん速い Rust がいちばん長く、いちばん短い PowerShell がいちばん遅い。2 つの図は、ほぼ逆順に並ぶ。

読み取れること

  • PowerShell の起動は約 247 ms。計画書に「1 秒弱」と書いたのは過大だった
  • 起動込みで見ると 14 倍の開きがある（Rust 41 ms 対 PowerShell 585 ms）
  • 書く量は逆に並ぶ。いちばん短いのは PowerShell の 37 行、いちばん長いのは Rust の 159 行
  • メモリも同じ順に並ぶ。Rust 5.3 MB に対して PowerShell 111.2 MB で、21 倍
  • コンパイルする 3 つは、直すたびに 0.2〜0.6 秒が乗る

この検査の重さは、量にほぼ比例する。22,238 行で PowerShell が 338 ms なので、10 倍の資料を持つプロジェクトでは 3 秒を超える。変換のたびに走らせる形では、ここが効いてくる。

JavaScript の書き方で変わるか

Node と Bun を採るなら、CommonJS（.js）・ESM（.mjs）・TypeScript（.ts）のどれで書くかも決めることになる。中身が同じ 3 本を用意して測った。条件は第 1 章と同じ、21 回の中央値。

実行時に型は検査されない

まずここを実測した。Bun も Node も、型注釈を取り除いて走らせるだけ。次のファイルは、どちらも警告すら出さずに最後まで走り、終了コードは 0 だった。

const n: number = "これは文字列";
const f = (x: number): string => x;
console.log("実行された:", n, typeof f);

型は「書ける」だけで「守られる」わけではない。守るには tsc --noEmit を別に走らせるしかない。そしてそれは、csc ・ rustc ・ go build と同じ「事前に通す段」である。TypeScript は「コンパイル不要の側」ではなく「コンパイルが要る側」に入る。

事前の段と、1 回あたりの実行

型チェックを必須とした場合の並べ直し。tsc の時間は第 1 章と同じ条件で 21 回測った中央値（--noEmit --skipLibCheck、対象は同じ 1 ファイル。tsc は 7.0.2 の Go 実装）。

TypeScript の 156 ms は、コンパイルする処理系の中でいちばん軽い。ただし得られるのは型の検査だけで、実行ファイルは作られない。実行時にはもう一度、型を捨てる処理が走る。

単一実行ファイルに固める（bun build --compile）

bun build --compile は、Bun の実行環境ごと 1 つの exe に詰める。Bun が入っていない環境でも動くようになる。試した結果を残す。採らない

この節の数値は最初に測ったときのもの（bun 1.4.0）。メモリを足した測り直しでは bun build --compile を対象にしていないため、上の表と数 ms ずれる。結論は変わらない。

見たこと結果
速さ変わらない。起動込み 48 ms（スクリプト）に対して 53 ms。むしろ微増した
大きさ84.7 MB（86,736 KB）。Rust の 18 倍、Go の 28 倍
コンパイル399 ms
型チェックされない。型エラーのあるファイルも終了コード 0 で exe ができ、そのまま動いた
構文チェックされる。括弧の閉じ忘れは位置を出して止まり、exe はできない

固めても速くならないのは、起動の 28 ms が Bun 実行環境そのものの初期化だからと見られる。スクリプトの読み込みではないため、詰めても減らない。exe 化の値打ちは「Bun が入っていない環境でも動く」ことだけになる。

また、固めても tsc --noEmit は要る。csc ・ rustc ・ go build はコンパイル時に型を検査するが、bun build は型注釈を取り除くだけである。

型チェックには依存が 2 つ要る

要るものなぜ
typescripttsc 本体。Bun にも Node にも型チェッカは入っていない
@types/node無いと node:fs ・ process が未定義になり、型チェックが通らない。実測で確認した

このプロジェクトは「テスト用の依存パッケージを増やさない」で通してきた。.ts を選ぶことは、その方針を変えることを含む。

ESM と CommonJS の差

  • Bun はどちらでも同じ（56 ・ 58 ・ 55 ms。誤差の範囲）
  • Node もほぼ同じ（79 ・ 86 ms。.ts だけ 127 ms）
  • 検査そのものの時間は 3 つとも変わらない。差はすべて起動側に出る

速度では決まらない。決め手は「型チェックのために事前の段と依存 2 つを持つか、持たないか」になる。

書き方得るもの代償
.ts型が守られる（tsc を回す前提）。検査の項目が増えても構造を保ちやすい事前の段 156 ms ＋ 依存 2 つ。Node で走らせると実行も 1.7 倍（124 ms）
.mjsBun でも Node でも最速。事前の段も依存も無い型が無い
.js同上。require で書けるESM に寄せる流れとは逆向き

食い違いから出てきたこと

各実装の出力を突き合わせたところ、Rust だけ検出数が違った。

C#（csc）        files=90 lines=19858 hits=3
Rust（rustc）    files=90 lines=19713 hits=0     ← 違う
Go               files=90 lines=19943 hits=3
Node             files=90 lines=19943 hits=3
Bun              files=90 lines=19943 hits=3
PowerShell 5.1   files=90 lines=19858 hits=3

3 件の内訳を数え直すと、すべて「キリル・ハングルの混入」の誤検出で、当たった先は build.cmd ・ build-text.cmd ・ build-convert-encoding.cmd の 3 本だった。

つまり SJIS のファイルを UTF-8 として読んだ文字化けが、異体字の検査に当たっていた。Rust が 0 件だったのは、UTF-8 として読めないファイルを丸ごと読み飛ばしたため（read_to_string が失敗する）。行数が少ないのも同じ理由。

これは測定の事故ではなく、検査対象の要件そのものである。cmd ・ bat は SJIS、reg は UTF-16 で書く決めになっている。そこを正しく読めない実装は、「検査したのに cmd だけ見ていない」状態になる。

Go と Rust は外部依存を足さないと要件を満たせない。このプロジェクトは「テスト用の依存パッケージを増やさない」「CDN を参照しない」で通してきたので、依存を足すこと自体が別の判断になる。

どれを選ぶか

決まっている条件

条件内容
実行時の速さ重視する。変換のたびに呼ぶため、1 回あたりの時間がそのまま効く
事前の段の速さ重み付けしない。コンパイルも型チェックも頻度が低い
動く場所Windows ・ Linux ・ Mac の 3 つ。これを満たさないものは選べない
型チェック必須。型を書くなら守る仕組みまで持つ
文字コードSJIS ・ UTF-16 を読めること（第 4 章）

条件で落ちるもの

処理系落ちる理由
PowerShell 5.1Windows 専用。Linux ・ Mac に存在しない。pwsh 7 へ移せば動くが、共通ルールの「ps1 は 5.1 で動くように書く」を変えることになる
C#（csc）Windows 専用。build.cmd が使う csc は .NET Framework 4.8 で、作られる exe も Windows でしか動かない。.NET 8 系へ移せば動くが、ビルドの作りごと変わる

残るのは Bun ・ Node ・ Go ・ Rust の 4 つ。事前の段を重み付けしないので、コンパイルの 574 ms ・ 595 ms は判断から外れる。

メモリでは差がはっきり出る。Rust と Go は 10 MB 前後、Bun と Node は 28 MB ・ 42 MB。ただしこの検査を 1 本ずつ呼ぶ使い方では、どれも問題にならない量である。

実行時の速さで差が付かない以上、決め手は残りの 4 つになる。check-public は誤検出を見ながら何度も直す道具で、そこは Bun のほうが向く。

書き方は TypeScript

型チェックが必須なら、.ts の代償は事前の段 156 ms と依存 2 つ（第 3 章）。事前の段は重み付けしないため、残る代償は依存 2 つだけになる。

そして Bun は .ts を .js と同じ 55 ms で実行する。実行時の速さを重視する条件で、型を持つ代償が実行時にはゼロになる。

Node でも走らせられるようにしておきたい場合だけ .mjs を採る。Node の .ts は実行が 127 ms（.js の 1.6 倍）で、実行時重視の条件に合わない。Bun に寄せるか、型を諦めるかの二択になる。

残る決めごと

  • Bun を共有ツール置き場の前提に加えてよいか。このプロジェクトに無い処理系が 1 つ増える
  • 型チェックのための依存 2 つ（typescript ・ @types/node）を受け入れるか。「依存パッケージを増やさない」の方針を変えることになる
  • 型チェックをいつ回すか。テストの一部にするか、コミット前にするか。走らせ忘れれば型は無いのと同じ
