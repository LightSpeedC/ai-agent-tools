html2md

なぜ必要か

ドキュメントは HTML で書き、GitHub で読むための Markdown をそこから生成する。HTML を正とし、Markdown は生成物として扱う。生成された .md を直接編集しても次回の実行で上書きされる。

変換スクリプトは以前プロジェクトごとに置かれていた。同じ処理が 5 通りに分かれ、直しが片方にしか入らない状態になっていたため、ここに 1 本だけ置く形に変えた。

使い方

このフォルダは PATH に入っているので、パスを書かずに html2md で呼べる。プロジェクト側にランチャーを置く必要はない。

html2md --root .
html2md --root . --dir docs --dir notes
html2md --root . --dry-run

html2md は exe、html2md-ps は参照実装の ps1 に解決される。PowerShell は同名の .ps1 を .exe より先に選ぶため、参照実装の名前を分けている。exe は ps1 の 65 倍速い（実測 228 ms 対 14.9 秒）。

オプション既定内容
--root <パス>カレントフォルダ対象のプロジェクトフォルダ
--dir <名前>notes探索するフォルダ。複数回指定できる
--exclude <名前>index.html変換しないファイル名。複数回指定できる
--extra <名前>—ルート直下の追加ファイル。複数回指定できる
--no-readme—ルート直下の README.html を対象から外す
--dry-run—書き出さず、変換結果と検査結果だけを表示する
--help—説明を表示する

終了コードは 0＝指摘なし、1＝指摘あり、2＝引数や対象の誤り。

--exclude の既定で index.html を外しているのは、README.html へのリダイレクト専用ページで本文を持たないため。

変換対象から外す

外し方は 3 通りある。何を外したいかで選ぶ。

外すもの書き方
ページ全体head に <meta name="md-skip"> を置く
要素だけその要素に class="md-skip" を付ける
ファイル名で--exclude <名前> を渡す

ページ全体を外すのは、変換すると構造が失われるものに使う。details で畳んだ課題一覧が該当する。Markdown に details の記法が無いため、畳みが解けて見出しも消える。

md-skip のページへのリンク

そのページを参照する側のリンクは、拡張子を置き換えず .html のまま残る。Markdown が生成されないため、.md にすると存在しないファイルを指すことになる。

[課題](../40_issues/issues.html)

除外の判定は html2md が行うので、書き手は常に .html と書けばよい。

GitHub はリポジトリ内の .html をレンダリングせずソース表示にする。details の畳みは効かないが、中身には到達できる。

仕組み

正規表現だけで解析する。対象は自分たちで書いた整形済みの HTML に限る。どのタグをどう変換するかはタグ対応仕様にまとめている。

タグのまま出すもの

ins sup sub mark kbd q はタグのまま残す。GitHub のレンダラで生き残ることを実測して選んだ。abbr small cite time は除去されるため平文に落とす。

del は ~~取り消し線~~ にする。ただし ~~ は ** と同じ前後判定を受けるので、成立しない位置では <del> で出る。

変換のあとに検査を行う。Markdown 側のリンク切れ・アンカー切れ、HTML 側が .md を参照していないか、HTML 側のリンク切れ、Markdown 側だけにある文言、更新日の古さを見る。HTML 側も独立に検査するのは、Markdown 側だけ見ると変換で .md になった分と区別できず見逃すため。

参照実装の ps1

html2md-ps は同じ処理を PowerShell で書いたもの。通常は html2md を使う。ps1 は exe の挙動を読んで確かめるためと、csc.exe が使えない環境のために残している。

html2md-ps -Root . -Dir docs,notes -DryRun

引数は exe と対応する（-Root -Dir -Exclude -NoReadme -DryRun）。ダブルクリックで実行する html2md-ps.cmd も同じフォルダにある。

両者の出力が一致することを tools/40_test/run-tests.cmd で検査している。片方だけ直すと落ちる。テストは exe の出力を読んだあとに削除してから ps1 を走らせる。残したままにすると、ps1 が 1 つも生成しなかった場合に exe の出力を読んで「一致」と誤判定する。

ビルド

build.cmd を実行する。Roslyn の csc.exe があればそれを使い、無ければ .NET Framework 4.8 の csc.exe を使う。標準搭載版は C# 5 相当なので、文字列補間や out var は書けない。

check-markdown

なぜ必要か

ローカルで正しく見える Markdown でも、GitHub では壊れることがある。代表が日本語の強調で、CommonMark は ** の前後の文字を見て開閉を判定する。

主題は**「何が流れるか」**です     ← ** が記号のまま表示される

開きの ** の直後が 「（句読点扱い）で、その直前が通常文字だと開き記号にならない。閉じ側も同様に、直前が 。 」 ） ］ だと閉じられない。

この種の不具合はローカルの目視では見つからない。実際、閉じ側だけを直して「60 件解決した」と判断した後、GitHub 上では開き側の 29 箇所が壊れたままだった。

使い方

# フォルダ配下をまとめて
check-markdown -Path . -Recurse

# 1 ファイルだけ
check-markdown -Path .\README.md

# レート制限を緩める（60 回/時 → 5000 回/時）
check-markdown -Path . -Recurse -Token ghp_xxxxx

check-markdown.cmd をダブルクリックしてもよい（カレントディレクトリが対象）。

問題があれば該当箇所を前後 45 文字つきで表示する。CI にも組めるよう終了コードを分けている。

終了コード意味
0問題なし
1表示が壊れる箇所がある
2検証できなかった（レート制限・通信断など）。「問題なし」ではない

2 を 0 と混同しないこと。検証できていないのに「問題なし」と報告するのは、このツールが防ごうとしている誤りそのもの。

仕組み

Markdown を GitHub の Markdown API（https://api.github.com/markdown）に投げ、実際に GitHub が返す HTML を見る。そこに ** が残っていれば強調が効いていない。コードブロックとコードスパンは対象外（** が実際のコードのことがあるため）。

項目内容
レート制限認証なし 60 回/時。-Token で 5000 回/時
文字コードConvertTo-Json の結果を UTF-8 のバイト列にして送る。そのままだと日本語が壊れる
除外の注意GitHub は <code class="notranslate"> とクラスを付ける。<code> 決め打ちでは拾えない

直し方

該当箇所だけ <strong>〜</strong> に置き換える。GitHub は Markdown 中の HTML を解釈するので確実に太字になる。半角スペースを入れて成立させる方法もあるが、日本語の文中に隙間が空くので使わない。

判定は変換スクリプト側で機械的に行い、書き手には意識させない。

check-contrast

なぜ必要か

CSS を読み返しても「白背景に白文字」は見つからない。CSS は宣言単位で無効化されるためで、色を CSS 変数で渡していると、変数が未定義のスコープで background だけが落ち、color だけが生き残る。

.toc a {
	background: linear-gradient(100deg, var(--dc), var(--dc2));  /* --dc 未定義 → この宣言だけ無効 */
	color: #fff;                                                  /* こちらは生き残る */
}

背景が消えてページの地色（白）になり、そこに白文字が乗る。ペアで書いたつもりでも片方だけ落ちる。同じ壊れ方をする経路は3つある。

経路起きること
変数が未定義その宣言だけ無効。背景が消えて文字色が残る
セレクタが広すぎる想定外の要素に片方だけ当たる
継承親の color を継いだ要素が、別の背景の上に置かれる

使い方

# フォルダ配下をまとめて
check-contrast -Path . -Recurse

# 1 ファイルだけ
check-contrast -Path .\README.html

# しきい値を変える（既定 1.5）
check-contrast -Path . -Recurse -Min 2.0

check-contrast.cmd をダブルクリックしてもよい（カレントディレクトリが対象）。

ブラウザは PlayWright 共有環境のものを使う。場所が違う場合は -PlaywrightRoot で指定する。

終了コード意味
0問題なし
1読めない配色がある
2検証できなかった（Playwright が無い・描画に失敗など）。「問題なし」ではない

仕組み

ブラウザで実際にレンダリングし、テキストを持つ全要素について getComputedStyle から前景色と実効背景色を取得してコントラスト比を計算する。

項目内容
実効背景色background-color が透明なら親を遡る。行き当たらなければページの地色（白）
グラデーション色停止点の平均色を使う
半透明下の色と合成してから比を求める
対象外SVG（文字色が fill で決まる）、非表示要素、サイズ 0 の要素
リダイレクトページmeta refresh / location.replace は転送先を二重検査するため除外

しきい値の既定は 1.5:1。目的は「読みにくい」ではなく「読めない」の検出に絞っている。

WCAG AA の 4.5:1 で判定すると、100deg のグラデーションでは文字が1文字も乗っていない右端の色まで拾ってしまう。実際に試したところ 16 件中 15 件が誤検出で、本当の問題が埋もれた。値を上げてはいけない。

検査自体を確かめる

検査が壊れていないことを、故意に壊したページで確認してから使う。

check-contrast -Path .\contrast\selftest.html

contrast\selftest.html には 7 ケースが入っている。4 件が検出され、3 件が検出されなければ正常。

ケース期待
変数未定義で背景が消えた白文字検出（1.00:1）
黒背景に黒に近い文字検出（1.13:1）
淡いグレー同士検出（1.10:1）
白文字を継承したまま白い箱に入った検出（1.00:1）
濃い紺のグラデーションに白文字検出しない
白背景に濃い文字検出しない
緑のグラデーションに白文字検出しない

直し方

原因直し方
色の var() が未定義var(--accent, #12224d) のようにフォールバックを書く
配色セレクタが広すぎる.toc a ではなく .toc ul a のように要素構造で絞る
親から color を継承したその要素に color と background を対で指定する

color を書く宣言ブロックには background も書く（逆も同じ）。例外は body のみ。

convert-encoding

なぜ必要か

Windows で扱うファイルは種類ごとに求められる形式が違う。書き込みツールは BOM なし UTF-8 ＋ LF でしか書けないため、書いたあとに毎回変換することになる。

ファイル求められる形式
ps1BOM 付き UTF-8 ＋ CRLF
cmd・batSJIS（CP932）＋ CRLF
regUTF-16 LE ＋ BOM ＋ CRLF
htmlBOM 付き UTF-8 ＋ LF

その変換を PowerShell で書くと、書き方がその場の判断に委ねられる。1 つのセッションで書き方が 3 回変わり、うち 1 回はウイルス対策に検知されて止まった。コマンド文字列は AMSI に読まれるため、書き方によって引っかかる。

観点手で書くこのコマンド
手法セッションごとに組み立てる引数を渡すだけ。判断の余地が無い
ウイルス対策コマンド文字列が読まれるexe の内部処理は読まれない
正しさ変換のたびに書き間違いの余地があるテストで担保できる

使い方

# 用途名で指定する。文字コードと改行の両方が決まる
convert-encoding tools/80_ops/foo.ps1 --to ps1
convert-encoding tools/80_ops/foo.cmd --to cmd

# 文字コード名でも書ける。改行は入力のまま
convert-encoding foo.txt --to sjis

# 改行も指定する。単独で書くと改行だけ変える
convert-encoding foo.txt --to sjis/crlf
convert-encoding foo.txt --to /crlf

# いまの状態を見るだけ。書き込まない
convert-encoding foo.cmd --info

# 中身を UTF-8 で標準出力へ出す。書き込まない
convert-encoding foo.cmd --read

読み取りツールは SJIS のファイルを UTF-8 として読むため化ける。文字コードを指定する手段が無く、化けたまま推測で扱うことになる。--read はその逃げ道。スクリプトから使うときは [Console]::OutputEncoding を UTF-8 にしておく（5.1 は外部コマンドの出力を CP932 として読む）。

用途名は ps1 cmd bat reg html、文字コード名は utf8 utf8bom sjis utf16le utf16be。改行は lf と crlf。

改行を書かなければ、改行は変えない。「指定しなかったものは変えない」で通している。文字コードごとに既定の改行を決めると、その対応を覚える必要が生じ、覚え違いが事故になる。用途名だけは例外で、種類ごとに改行まで決まる。

終了コード意味
0成功（変更なしを含む）
1引数が正しくない
2ファイルが無い、または読めない
3文字コードを判定できない。書き込まずに終える
4変換先で表現できない文字がある。--force で回避できる
5書き込みに失敗した

仕組み

変換元は BOM → UTF-8 → SJIS の順に調べる。判定できなければ何も書き込まずに終える。推測で変換すると、失敗したときに元へ戻せない。--from を指定すると判定を飛ばす。

UTF-8 の検査では過剰な長さの符号化を弾く。C0 80 のように短く書けるものを長く書いた並びを通すと、SJIS のファイルが UTF-8 と誤判定される場面が増える。

SJIS へ変換すると文字が失われることがある。絵文字・ハングル・簡体字は CP932 に無く、既定の変換では ? に置き換わって元に戻せない。変換の前に検査し、見つかれば書き換えずに終了コード 4 で終える。その文字と行番号を出すので、どこを直せばよいか分かる。

改行はいったんすべて LF に落としてから目的の改行へ置き換える。CR 単独（旧 Mac 形式）もこの順で拾える。1 段階で \r?\n を置き換える方法だと CR 単独が残る。

変換後のバイト列が元と同じならファイルに触らない。更新日時が変わらないので、何度実行しても同じ結果になる。書き込みは同じフォルダの一時ファイルを経由するため、途中で失敗しても元のファイルが壊れない。

判定・変換の詳細とテストケースは仕様書にある。
