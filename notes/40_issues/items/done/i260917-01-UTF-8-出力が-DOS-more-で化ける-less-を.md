html2md・convert-encoding・text 等の出力を DOS の `more` コマンドへパイプしてページングすると、UTF-8 の出力が CP932 として読まれて文字化けする。`more` 自体は Windows 標準の .NET／PowerShell 系が持つ「出力コードページ問題」の受け手側版で、i260912-06 と根が同じ。

<strong>UTF-8 セーフなページャー（`less`）を新設した。</strong>言語は他ツールと同じ理由で TypeScript。機能範囲は最小限のページング（`Space`／`Enter`／`q`）に、上下スクロール（`↑`/`↓` で1行、`PageUp`/`PageDown` で画面高さの2/3）を加えた形で決定。計画は [notes/10_plan/](../10_plan/i260917-01-less.md) を参照。

✅ **済** 2026-09-17 に実装した。他ツールと同じ形（`less`・`less.cmd`・`src/less/main.ts`）。**実装中に踏んだ落とし穴**: `cmd | less` の形では `process.stdin` がパイプのデータで埋まっており、上下スクロールのキー入力に使えない。Windows のコンソール入力を素の `'CONIN$'` で開こうとすると Node がカレントフォルダからの相対パスとして解決してしまい失敗する（実測で確認）。**Win32 のデバイス名前空間 `\\.\` を前置する**と正しく開けた。`tools/40_test/run-less-tests.ts` を新設し、出力先が端末でないときの素通し経路（UTF-8 のまま完全一致すること）・`--help`・知らないオプション・改行の正規化を自動で確認（bun・node とも成功）。**実際のキー入力による画面遷移は対話が要るため自動化しておらず、利用者による確認が要る**——と記録した上で「済」としたが、これは早すぎた。

⚠️ **着手** 2026-09-17、利用者が実機（Bun）で `aichat -h|less` を実行したところ、`page()` 内の `key.setRawMode(true)` で `setRawMode failed because it was called on something that is not a TTY` が発生して即クラッシュした。`isTTY` は `true` を返すため、実装時の確認（`isTTY` が `true` になることだけ）では検知できていなかった。原因を切り分けたところ2点あった。

- **Node にも同じ根の不具合があった。**`CONIN$` を読み取り専用（`'r'`）で開いており、Windows の `SetConsoleMode` は書き込みアクセスも要るため `setRawMode` が `EPERM` で失敗する。**`'r+'`（読み書き）で開き直して解決**（実測で成功を確認）。これは直し方が1つしかない不具合として修正した。
- **Bun は `'r'`／`'r+'`／`'w+'`／`'a+'` のどのモードで開いても直らない（4モードすべて実測）。**`setRawMode` が Node とは別のエラー（「TTY ではない」）で失敗し続ける。Bun の Windows 向け `node:tty` 実装が、標準入出力以外の fd を raw mode 対応の TTY として扱わないという実装上の制約と見られる（Bun の Issue 追跡でも Windows の Terminal/PTY 関連機能は未対応・制限ありと記載）。

複数の対処案があったため利用者に確認し、一旦「`less` だけ入口の振り分けを node 優先・bun 予備に変える」で暫定対応した。その後、**回避策を検索・検討した結果、恒久対策として `node:tty` を使わず MS-CRT（`msvcrt.dll`）の `_kbhit`/`_getch` を `bun:ffi` で直接呼ぶ方式を採用**。これらはコンソールを直接読む実装のため、標準入力がパイプで埋まっていても影響を受けない（実測で確認）。Win32 Console API（`ReadConsoleInputW` 等）を直接叩く前例（[bun-win32](https://github.com/ObscuritySRL/bun-win32)）も確認したが、外部パッケージへの依存と実装量（構造体の自前デコード）が大きいため見送り、`_getch`/`_kbhit` なら外部パッケージ無しで数十行で済むと判断した。

実装は `KeySource`（`onData`／`close`）という共通の形に抽象化し、Node は今までどおり `tty.ReadStream`、Bun は `_kbhit`/`_getch` のポーリングにした（`handleKey()` 以下のキー解釈ロジックは共通のまま変更無し）。`bun:ffi` の型は外部パッケージ（bun-types）を増やさず `src/less/bun-ffi.d.ts` に自前で宣言。実行時のランタイム判定は `typeof Bun !== 'undefined'`（このプロジェクトで main.ts 自身が実行時にランタイムを判断する初めてのコード）。`less`・`less.cmd` は bun 優先の振り分けに戻した（他ツールと同じ構成）。

修正後、`tools/40_test/run-less-tests.ts`（bun・node とも8件成功）・型チェック・全体テストを確認済み。`bun:ffi` での `dlopen`・`_kbhit()` 呼び出しが標準入力をパイプで埋めた状態でも例外を出さないことは個別に確認したが、テストスイートには組み込めていない。**対話キー操作（矢印・PageUp/Down 等、拡張キーのデコードを含む）による画面遷移は自動化できないため、利用者による実機での再確認が済むまで「済」にはしない。**

2026-09-18、上記の再確認で **Bun でのキー入力自体は反応した（↓キーで画面が動いた）が、キーを押すたびに画面全体をクリアして再描画するため点滅する**との報告。利用者の指示で差分スクロール描画に変更: 下方向（↓・Enter・Space・PageDown）は最下行から改行で1行ずつ流し込むスクロール方式、↑（矢印1行）は Reverse Index（`\x1bM`）でのスクロール方式、**PageUp だけは全画面再描画のまま**（複数行分の Reverse Index は端末依存の懸念があるため）。加えて、端に達していて実際には動かないとき（先頭で↑・末尾で↓等）は何も出力しない変更も実施。`render()`／`move()` の変更のみで、`handleKey()`・`KeySource` は影響を受けない。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済みだが、**画面遷移の見た目そのものは自動化できないため、利用者による実機での再確認が済むまで「済」にはしない。**

2026-09-19、上記の再確認で **↓キー・Enter を押しても表示が進まず、ステータス行の％表示だけが増える**不具合を報告。原因は、画面が「コンテンツ h 行＋ステータス行 1 行」の計 h+1 行を使っているのに、`scrollDown()` がコンテンツの最終行（端末にとっては画面の最終行ではない）にカーソルを置いて改行しており、スクロールが起きずステータス行へ上書きしていたこと。**DECSTBM（`\x1b[1;h r`）でスクロール範囲をコンテンツ用の h 行だけに限定して修正**（範囲内だけが正しくスクロールし、範囲外のステータス行は動かない）。あわせて利用者の指示で `q` 終了時の画面クリアも無くした（最後の表示を残したままカーソルをステータス行の下へ）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

同日、**端末の桁数（例: 140桁）を超える長い行があると、端末側の自動折り返しで「`lines[]` の1要素＝画面の1行」という前提が崩れ、行番号がずれる**可能性を指摘。複数の対処案があったため利用者に確認し、**B案（折り返しを許容し、1論理行が何画面行を使うかを計算に入れる）を採用**。実装量が大きいため**未実装のまま設計だけ計画書に記載**し、着手は今回のスクロール修正の確認が済んでからとした。まずは150桁端末で再現を確認する予定。詳細は [notes/10_plan/](../10_plan/i260917-01-less.md) を参照。

150桁端末での再確認で、**`Enter` を押すとステータス行が消えずに残ったまま画面がスクロールしていった**との報告。原因は `scrollDown()` の書き方: 改行を先に出してからテキストを書いており、改行だけでは列が先頭に戻らない（複数行分で列がずれる）うえ、書く前に行末までクリアしていなかったため、新しい行が前の内容より短い場合等に文字が残っていた。**利用者の指示で「行頭へ戻す（`\r`）→行末までクリア（`\x1b[K`）→テキスト→`\r\n`で次行へ」の順に修正**（`scrollUp()` にも同じ理由で行頭復帰＋行末クリアを追加）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

✅ **済** 150桁端末での再確認で **↓・Enter とも乱れなく動くことを確認**。あわせて**最初の表示・PageUp でステータス行が下から2行目に出る**不具合を新たに報告。原因は同種: `render()` がコンテンツを書いた後、改行だけでステータス行へ移っており、コンテンツ最終行の文字数ぶんカーソルが右へずれたままステータス行の反転表示が桁あふれ・自動折り返しして1行分ずれていた。**`render()` のステータス行書き込みを、絶対位置で書く `writeStatus()` に一本化して修正**。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

✅ **済** 同日、`less -h | less` で使い方の説明（全て日本語）が文字化けする不具合を報告。原因は **Bun が Windows のコンソール出力コードページを自動で UTF-8（65001）に設定しないこと**（Node は自動でする）。これまでの実機確認は ASCII 主体の内容が多く気づかれなかった。**`bun:ffi` から `kernel32.dll` の `SetConsoleOutputCP(65001)` を明示的に呼んで修正**。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

✅ **済** 同日、ヘルプの `↓・Enter` 行だけ桁が揃っていない不具合を報告。原因は手でスペースを数えて決め打ちしていたこと（並べ替え時に数え直しを忘れた、表示幅も実機で試すまで正しく分からなかった）。**表示幅を計算する `displayWidth()`／桁を揃える `pad()` を実装し、`Usage` の組み立てをこれに置き換えた**。再発防止のため**共通ルールに「全角・半角混在のテキストを桁揃えするとき」を追記し、ai-chat-lite の public ルームへ周知**（他プロジェクトでも同じ不具合を防ぐため）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

✅ **済** 同日、利用者の指示で機能追加: `q` 終了時、反転表示のステータス行を消し通常色の終了メッセージに置き換え。実データの最終行に到達したことが分かるよう反転表示の `[EOF]` を表示（改行なしで終わる場合は最終行の末尾へ、改行ありで終わる場合は次の1行に）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

✅ **済** 同日、実機確認で**ちょうど画面いっぱいになる回で `[EOF]` が表示されない**不具合を報告。原因は「画面に余裕があるときだけ追加する」形にしていたため。**`[EOF]` を「実データの後ろに続くもう1行（仮想行）」として扱い、`virtualLength = lines.length + (改行ありなら1)` を `clampTop`・表示範囲の計算にそのまま使う形に直した**。「余裕があるときだけ」という特別扱いが要らなくなり、この不具合の型自体が起きなくなった。ステータス行の％表示は実データの行数のまま変えていない。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

✅ **済** 同日、利用者の指示で仕様変更: `PageUp`／`PageDown` の移動量を 2/3 → 3/4 に、`Space` を「1画面分」から `PageDown` と同じ「3/4」に統一。ステータス行にキー一覧を追加（`-- less (NN%) q で終了 | Page Up | ↑ | ↓・Enter | Space・Page Down --`）。ヘルプの文言も合わせて修正（表示幅は `pad()` が自動計算するため、文言を変えても桁ずれは起きない）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

✅ **済** 同日、実機確認で<strong>下方向へ動くたび最下行に空行が1行できる（上方向では起きない）</strong>不具合を報告（十分行数のあるデータで再現）。原因は `scrollDown()` の順序: 「クリア→書く→`\r\n`」だと、**LF（スクロール）がテキストを書いた後に起きるため、書いたばかりの内容までスクロール範囲の中で1行分押し上げられ、最下行が空いたまま残っていた**。`scrollUp()` は逆に「まずスクロールしてから書く」順だったため起きていなかった。**`scrollDown()` も同じ「スクロールを先に、書くのを後に」の順に修正**（「`\r\n`→行末までクリア→テキスト」）。あわせてステータス行の表記を `Space・Page Down` → `Page Down・Space` に変更（利用者の指示）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

✅ **済** 同日、利用者の指示で機能追加: `PageUp` も全画面再描画ではなく `scrollUp()` のスクロール方式にした（複数行対応。画面の下寄りに来る行から先に書くと最終的に上から正しい順に並ぶ）。`move()` の `strategy` 引数・`'redraw'` 分岐・`render()` は今後また使う予定のため残した（既定値は `'scroll'`）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

⬜ **未** 2026-09-19、利用者から改めて指摘: **端末の桁数を超える長い行の折り返しは、まだうまく動いていない**（既存の指摘の再掲）。対処案（[notes/10_plan/](../10_plan/i260917-01-less.md) 参照）に、**右端に1桁しか残っていない位置へ2桁文字（漢字等）を表示しようとするときは、空白を入れて先に折り返した「仮想行」をあらかじめ持っておく**という具体案が加わった。まだ未着手。

✅ **済** ただし調査の過程で、**`less -h | less` のような「Bun で書いたプログラム同士をパイプで繋ぎ、かつ開始時のコンソールのコードページが UTF-8（65001）でない」ときに、Bun ランタイム自体が文字化けを起こす**という、このプロジェクトのコードでは直せない問題を発見した。`bun:ffi` を一切使わない最小構成（`bun -e "console.log(...)" | bun -e "process.stdin.pipe(process.stdout)"`）でも再現し、実行後コンソールのコードページが 65001 に変わる副作用も伴う。Node では同条件で再現しない。詳細な切り分け結果は [notes/10_plan/](../10_plan/i260917-01-less.md) の「落とし穴（8）」を参照。[oven-sh/bun#43660](https://github.com/oven-sh/bun/issues/43660) として報告済みだが、Bun 側の修正を待つのは現実的でないと判断し、**`less`・`less.cmd` のランチャーを node 専用に切り替えた**（`bun:ffi` を使う `psls` は node 版が無いため対象外。`psls | less` は bun→node の組み合わせになり、化ける条件から外れる）。テスト（bun・node とも10件成功）確認済み。
