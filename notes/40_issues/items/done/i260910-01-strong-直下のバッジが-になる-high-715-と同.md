報告（`public` #715）: `<strong><span class="badge b-ps51">5.1</span> では …</strong>` の変換結果が `****5.1** では …を必ず付けてください。**` になり、開きと閉じの数が合わない。7 箇所（PowerShell 学習資料）。

原因（`src/Html2Md/Inline.cs`・`Emphasis.cs`）: バッジの変換が中身を `Emphasis.StrongBegin`/`StrongEnd` で囲む。バッジが `strong` の直下にあると、外側の `strong` も同じセンチネルで囲むため、**同じ種類の強調が二重に入れ子になる。**`Emphasis.Resolve` は内側から順に確定させるだけで、外側が同じ種類の未解決ペアであることを見ていなかった。

✅ **済** 2026-09-10 に `Emphasis.Resolve`（exe）・`Resolve-Emphasis`（ps1）を直した。ペアの直前・直後に**同じ種類の生のセンチネル文字**が残っているかを見て、残っていればこのペアでは記法を確定させず中身だけを残す（外側が次の周でまとめて 1 組の記法にする）。生のセンチネルは HTML 由来の文字列に現れないので、文字列の中身（`**` など）を見る誤検出の心配がない。報告どおりの HTML で再現・修正を確認。テストケース `tests/cases/badge` を新設（strong 直下のバッジ／strong 外のバッジ／バッジ無しの通常強調の 3 パターン、`****` の禁止も検査）。全テスト成功（html2md 12・convert-encoding 98・text 50）。

⚠️ **着手** 定期レビュー #2（`html2md` #742）で**3 通りのうち 1 通りしか直っていない**との指摘。実測で再現を確認した。`touchesOuterSameKind` は一致の直前・直後の 1 文字だけを見るが、`Inline.cs` のバッジ展開は記号の有無にかかわらず**本文の後ろに空白 1 個**を入れるため、閉じ側は外側 `strong` の閉じセンチネルと隣接しない。隣接が成立するのは「バッジが `strong` の先頭にあり、かつ記号なし」の場合だけ。

| 形 | 出力 |
|---|---|
| `<strong><span class="badge b-ps51">5.1</span> では …</strong>`（先頭・記号なし） | **直った** |
| `<strong>本文 <span class="badge b-ps51">5.1</span></strong>`（末尾） | `**本文 **5.1****` |
| `<strong>… <span class="badge">x</span> …</strong>`（中間） | 同じく崩れる |
| `<strong><span class="badge b-ok">完了</span> 本文</strong>`（記号あり） | `**✅ **完了** 本文**` |

`tests/cases/badge/README.html` の既存 4 行はこの 3 パターンを 1 件も踏んでおらず、テストが穴を見逃していた。**直すには「バッジが本体の後ろに空白を足す」処理自体を、外側の未解決ペアの有無を見てから行うよう組み替える必要がある**（touchesOuterSameKind の判定タイミングと、バッジの空白付与のタイミングの順序が絡む）。回帰リスクがあるため、次に着手する。

> [!IMPORTANT]
> <strong>記述の是正（判断が要る）。</strong>上の修正方針（隣接判定の組み替え）を現在の TypeScript 実装（`emphasis.ts`・`inline.ts`）で追ってみたところ、**「末尾」パターンは直せても「中間」パターンは直らない**ことが分かった。「中間」（`<strong>… <span class="badge">x</span> …</strong>`）では、バッジ自身が外側のどのセンチネルにも隣接しないため、隣接判定をいくら精緻にしても**バッジ単体が独立して `**x**` に確定してしまう**。これが外側の `**…**` と衝突し、同じ種類の強調が入れ子になった markdown（`**… **x** …**`）ができて崩れる。**根本原因は「隣接しているか」ではなく「同じ種類の強調に入れ子で囲まれているか」**。直すには、外側に同種のペアが未解決のまま残っている（隣接の有無を問わず）ときは `**` ではなく `<strong>` タグで出す、という判定に組み替える必要がある。**生成物の記法（** か タグか）が変わる範囲が当初の想定より広がるため、実装せず記録だけ残す。**

> [!TIP]
> ✅ **済** <strong>2026-09-16、別解を検討した (2026-10-28 に実装)。</strong>タグへ落とす以外に、**入れ子の内側だけ `__`（アンダースコア2つ）へ記法を替える**という手がある。CommonMark は `**` と `__` を別種の区切りとして扱うため、`**外側 __内側__ 続き**` は入れ子として正しく解釈される（`<strong>外側 <strong>内側</strong> 続き</strong>`）。先頭・末尾・中間のどのパターンでも Markdown の記法のまま表現でき、**HTML タグへ落とすより自然**（このプロジェクトは、記法で表現できない場合の最終手段としてのみタグを使う方針）。ただし**この関数（`emphasis.ts`）は既に2度不具合を起こしている**ため、実装するなら `check-markdown` で GitHub の実レンダラ確認を通してからにすべきで、今回は知見の記録だけに留める。

✅ **済** <strong>2026-10-28、実装した（65-A。利用者の判断）。</strong>入れ子の内側の強調だけを `__` にした（`emphasis.ts` の `nestedInSameKind`）。外側に同じ種類の未解決のペアがあるかを、隣接ではなく、前にある開き・閉じのセンチネルの数で見る。先頭は従来どおり隣接の判定で 1 組にまとまる。末尾・中間・記号ありの 3 通りは、`**BNEST1 本文 __5.1__**` ・ `**BNEST2 前 __x__ 後**` ・ `**✅ __完了__ BNEST3 本文**` になった（期待値を手で書き、ケース `tests/cases/badge` に足して、崩れた出力で ❌Red を確かめてから直した）。変換後の検査 `checks.ts` は、記法の記号に `__` を足した（両側に同じ規則で効く）。`check-markdown`（GitHub のレンダラ）は問題なし。描画された HTML でも、記号は残らず、全体が 1 つの太字になった。html2md の全 30 ケースが成功。
