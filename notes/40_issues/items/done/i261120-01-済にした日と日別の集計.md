file-manager の依頼 (#2064)。課題の「済にした日」を記録し、日別の「立てた数・済にした数・残り」を出せるようにしてほしい。今は立てた日 (created) しか持たず、消化の速さを測れない。fm では、直近 5 日で立てた数が約 190、済が約 30 と、git の履歴から手で数えた (fm の数え方による報告で、こちらでは確かめていない)。困った場面は、残課題が消化より速く増えていないかを、数で確かめたかったこと。

ほしい形 (依頼の原文どおり): (1) issue set --state 済 のときに、済にした日 (done) を課題に書く。(2) 日別の集計 (立てた・着手にした・済にした・残り) を出すコマンド (例: issue stats --since <日> --json)。(3) 既存の済には、git の履歴から分かる範囲で done を埋める移行 (分からないものは空)。

事実 (根拠): (1) 状態は置かれたフォルダ (todo/・doing/・done/・archived/) で持ち、issue set --state は、課題のファイルを隣のフォルダへ動かすだけで日付を書かない (src/issue/ops.ts の setState の 334-348 行と、動かす moveIssueFile の 313-326 行。追跡中のファイルは git mv、git の管理外は renameSync)。git mv は名前の変更だけを stage し、中身の変更は載せない。done を書く処理を足すと、名前の変更 (stage 済) と中身の変更 (stage 前) が別の状態で残る。書いてから動かすのか、動かしてから書くのか、stage の扱いは、実装のときに決める。(2) 課題が持つ日付の鍵は created だけ (メタ情報の鍵: schema・id・title・group・created・from・confirmed・refs・version・released・kind・note)。(3) 済にした日が無いため、issue archive --done-before は「立てた日 (created) で選ぶ」形になっている (決定 i261109-04-d3 の A、ops.ts:425 の説明)。済にした日があれば、済にした日で選べる。(4) 着手にした日も持たない。依頼の (2) の「着手にした」を数えるには、着手の日も要る (依頼は done の記録だけを (1) に書いていて、着手の日の記録には触れていない)。(5) 既存の済は、items/done/ に 82 件、items/archived/ に 23 件で、合わせて 105 件 (2026-11-20 に ls で数えた)。archived/ の分も、日別の集計 (済にした数・残り) と --done-before の選び方に効く。これらの done を git の履歴から埋められるかを、2026-11-20 に実測した (git log --diff-filter=A で、done/ と archived/ に最初に現れた commit の日付を、ファイル名ごとに最古で数えた)。105 件すべて追跡できた。ただし 66 件は、2026-11-07 の 1 commit (87acf8b、issues.html から 1 件 1 ファイルへ移した migrate の commit) で一度に現れていて、その日付は「移した日」で、済にした日ではない (分からないとして空にするのが正しい)。残りの 39 件は、done/ に入った commit の日付が目安になる (11/07 の別の 1 件 ・ 11/08 3 件 ・ 11/09 5 件 ・ 11/10 11 件 ・ 11/11 5 件 ・ 11/14 4 件 ・ 11/15 3 件 ・ 11/17 4 件 ・ 11/18 3 件の日付別の数のうち、87acf8b の 66 件を除いた分)。commit の日は、set --state 済 を流した日より後になることがある (commit は作業の区切りで行うため。同じ日に収まる場合が多いと見ているが、確かめていない)。(6) 「済にした日」は set --state 済 を流した日で、作業が終わった日ではない。やることが全部済になっても、状態は自動で済にならない (doneBlockers の条件を満たさないと、set --state 済 は拒否される。ops.ts:342-345)。

今ある動き (直すときに守るもの):
- issue set --state は、フォルダを動かし (moveIssueFile)、メタ情報の鍵を書き換えない。済にするときは doneBlockers の条件で拒否することがある。すでにそのフォルダなら動かない (moved: false、ops.ts:341)。archived/ の課題は動かさず、先に unarchive を求める (ops.ts:339)
- issue archive と issue unarchive は、状態 (フォルダ) を動かすだけで、日付を書かない。unarchive で done/ に戻しても、done を変えない (これから足す done も、この線引きにする)
- issue archive --done-before は、立てた日 (created) で選ぶ (ops.ts:424-430、決定 i261109-04-d3 の A)
- メタ情報の書き換え (setFields ・ todo ・ confirm ・ decide set ・ render) は、write-atomic の writeText で原子的に書く。issue new の作成 (ops.ts:204) や initProject (ops.ts:95) は、別の書き方 (wx の作成・writeFileSync)
- メタ情報の未知の鍵は保たれ、issue check が警告を出す (check.ts:343 の unknown-key)
- issue check は、released の形の誤りを error、version と kind の形の誤りを warning で出す (check.ts:288-294、決定 275-A)
- issue list --missing は、version・released・kind・note を持たない課題を探す
- created は todayJst() (JST) で書く (ops.ts:49、198)

## やること
- [済] 決めることを整理して、利用者に選択肢で聞く。候補: (a) キー名と書式 (done: yyyy-mm-dd か yyyy-mm-dd hh:mm。released が hh:mm まで持つのと揃えるか。JST で書くか) (b) 着手の日 (started) を持つか (c) 済から未・着手へ戻したとき done を消すか残すか。済 → 済は上書きしない (d) issue archive --done-before を済にした日で選ぶか。done の無い課題の扱い。決定 i261109-04-d3 を改める形にするか (e) 集計の出力 (日別・JSON・テキスト) と、残りの数え方 (その日の終わりの未 + 着手。戻した課題の数え方) (f) 既存の済 105 件 (done/ 82 + archived/ 23) の移行の範囲と、埋められないものの扱い。issues.html からの migrate で done/ に入った課題には、移した日を書かない (済にした日として誤るため) (g) issue check で done を検査するか (日付として実在するか・done/ と archived/ 以外にあるのに done を持つ課題・created より前の日付) (h) issue set --done <日> で、移行で埋められなかった分や誤りを手で直せるか
- [済] 既存の済 105 件 (done/ 82 + archived/ 23) の done を git の履歴から埋められるかを、実測する (移行の範囲を決める材料)。落とし穴: 1 件 1 ファイルへ移した日 (migrate) より前に済だったものは、履歴では「移した commit で done/ に入った」としか見えない (分からないとして空にする)。git log --follow は名前の変更を推定でたどり、中身も同時に変わるとたどり切れないことがある (どちらも確かめていない)
- [済] 実装 (set の done 書き込み ・ 集計コマンド ・ 移行) と試験 ・ 仕様 ・ TOOLS-USAGE の更新
- [済] file-manager に知らせ、確かめてもらう (課題を閉じるのは確認のあと)

実装した: set --state の started ・ done の書き込み、set --started / --done、check の検査 (形 = error、done-folder ・ before-created = warning)、archive --done-before の done 選び、issue stats、issue backfill-done。試験は tools/40_test/run-issue-done-tests.ts (bun ・ node とも 64 件成功)。仕様 (課題ファイルの形と検査) と TOOLS-USAGE を更新した。(287-D で closed に改名)

決めたこと (stage と順): (1) 動かしてから日時を書く。書けなければ (理由を問わず) 状態は動かしたまま、標準エラーに警告 (終了コード 0。直し方は issue set <id> --done / --started)。(2) git mv は rename だけを stage するので、日時の書き込みは stage 前の変更 (git status では RM)。stage しない。(3) 鍵の順は created の次に started ・ done。(4) stats の既定は、since がいちばん古い日付・until が今日。done の無い済は残りに数え、件数を undatedDone に出す。(5) backfill-done は、一度に 10 件以上が (それまでに無かった名前で) 済に入った commit を移行とみなして飛ばす。日時は author の日時、最後に済に入った commit。実リポジトリへの --dry-run は 39 件を書き、87acf8b の 66 件を飛ばす。(287-D で closed に改名)

tools-review のソースレビューへの対応 (指摘 1〜10):
- 1 直した: 名前ごとに「最後に済に入った commit」を取る (済 → 着手 → 済は入り直し、done/ → archived/ は数えない)。試験の材料の不具合で、直す前の ❌Red は確認できていない (旧実装は最初の commit を返す設計)

- 3 直した: 動かしたあとの書き込みの失敗は、種類を問わず警告にした (❌Red を見て直した。読み取り専用のファイルで確かめた)
- 4 直した: %aI (author の日時)
- 5 直した: nowJst は 1 つの Date から日付と時刻を取る (試験で再現できない。0 時をまたぐ瞬間のため)
- 6 直した: stats は done/ ・ archived/ にある課題の done だけを数える
- 7 直さない: 読めない課題 (loadFile が失敗する) を済から戻したときだけ done が残る。rare。issue check が closed-folder の警告を出すので気づける。条件: 読めない課題を戻す操作が実際に起きたら直す

stats の「残り」は、利用者が 286-A (決定 i261120-01-d9。283-A を置き換える) に決めた: done の無い済は、済として数え、残りから外す (件数は undatedDone)。移行 commit より前の日の残りは、少なめに出る。実装し、試験 (run-issue-done-tests.ts) を先に直して ❌Red を見てから通した。仕様と TOOLS-USAGE に、少なめに出ることを書いた。(287-D で closed に改名。undatedDone は undatedClosed)
