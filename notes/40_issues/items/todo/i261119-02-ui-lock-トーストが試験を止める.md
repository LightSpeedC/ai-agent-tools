file-manager の依頼 (#2055)。ui-lock run が、待つ間 5 分ごとに Windows のトーストを出す (--wait の有無によらない)。画面の試験を流している別のセッションの前面をトーストが取り、試験が止まる (今日、右クリックの試験が複数回止まった)。待つ間のトーストを止める引数 (例 --no-toast)、または既定でトーストを出さない形の検討が依頼。fm は短い --wait の繰り返しで回り道している。

事実 (根拠): (1) トーストは決定 i261114-01-d3 (254-A、2026-11-14、案は A トースト・B chat へ発言・C 画面の出力だけ)。src/ui-lock/main.ts の run が、待つ間 TOAST_SEC (5 分) ごとに toast() を呼ぶ。Rust 版 (src/ui-lock-rs/src/main.rs) も同じ。(2) 環境変数 UI_LOCK_NO_TOAST=1 で止められる形が、TS 版 (main.ts:277) と Rust 版 (main.rs:399) の両方にすでにある。試験 (run-ui-lock-tests.ts) が使っている。TOOLS-USAGE には書かれていない。(3) トーストが前面を取る・試験が止まる、は報告からの事実で、こちらでは再現していない。前面を取っているのが、トースト自体か、通知を出す powershell の起動かも分からない (TS は detached ・ windowsHide、Rust は CREATE_NO_WINDOW で起動のしかたが違う)。(4) 最初のトーストは、待ち始めてから 5 分後 (main.ts:379 の lastToast = Date.now()、Rust は 554 行)。待ちが 5 分より短ければ出ない。fm の「短い --wait の繰り返し」が効くのはこのため。(5) 既定の待ちは 60 分で、--wait を付けなくても待つループの中でトーストが呼ばれる (main.ts:349-350、382-394)。

仕様を疑う: 決定 i261114-01-d3 には、案と選んだ字だけがあり、理由が書かれていない (理由が無いことは確かめた事実。害を検討せずに選ばれたかどうかは、記録から言えない)。構造として、トーストを出すのは待っている側で、表示されるのはロックを持って画面を使っている持ち主の画面 (同じデスクトップ) である。守る相手にちょうど当たる作りで、ロックの目的と逆に働く。

今ある動き (直すときに守るもの):
- 取れるまで待ち、1 分ごとに持ち主を画面へ出し (OWNER_PRINT_SEC、TS・Rust とも同じ)、5 分ごとにトーストを出す
- --wait で待つ上限 (既定 60 分) を指定でき、過ぎると終了コード 3
- UI_LOCK_NO_TOAST=1 でトーストだけが止まる。この環境変数は子のプロセスの環境 (runChild の env) にも受け継がれ、包まれた中の ui-lock も黙る
- トーストが出せなくても待ちは続く (main.ts:287-291、Rust は spawn の失敗を捨てる)
- 包まれた中 (UI_LOCK_HELD) では待たないので、トーストも出ない (main.ts:366-371)
- --also で複数のロックを待つときも、トーストは 1 本で、文面にロックの名前は出ない
- 文言は、持ち主が user のとき「利用者が使用中です」、それ以外は「持ち主: …」
- --evict-user-after で利用者の画面へ終了を知らせる (main.ts:395-399)
- 待っている分数の数え方が違う (TS は Math.round で 9 分 45 秒が 10 分、Rust は切り捨てで 9 分)。既存の差で、この課題の範囲の外
