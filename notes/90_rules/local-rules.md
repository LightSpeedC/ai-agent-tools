## 1. 共通ルールとの関係

ここに書くのは、このプロジェクトでしか言えないことだけ。全プロジェクトに通ることは共通ルールにある。同じ文を両方に書かない。

### 共通ルールと違う運用にしている点

| 共通ルールの見出し | どう違うか | なぜ |
|---|---|---|
| フィードバックの記録先 | 作業の進め方のフィードバックを、共通ルールではなく**この文書に置く**（第 2 章） | このプロジェクトの課題の持ち方に結びついた決めごとであるため。`issues.html` に未検証の項目が数十件積まれる状態が続いており、そこから何を自動で消化してよいかの線引きは、ほかのプロジェクトには当てはまらない |
| ai-chat-lite（AI 間チャット）の利用 | 待受けの参加を、利用者の指示を待たず**自分の判断で張る**（第 4 章） | 共通ツールのメンテをしており、各プロジェクトから不具合報告・フィードバックを受けることが多い。窓口として常時聞いておく必要がある |

ほかの見出しは共通ルールのとおりに運用する。食い違いを見つけたら、まずこの表に載っているかを見る。載っていなければ共通ルールが正しい。

## 2. 判断が不要な作業はいつも消化する

適用条件: 課題（`notes/40_issues/issues.html`）に手を付けるとき。

<strong>判断が要らないものは、指示を待たずに最後まで進める。</strong>毎回どれをやるか聞き返さない。

### 判断が要らないもの

- **直し方が 1 つしかない不具合**。原因と直し方が特定できていて、選択肢が無いもの
- **exe と ps1 の乖離**。どちらが正しいかが仕様・資料から決まるもの
- **記録を実態に追いつかせる**。課題の状態・件数、資料の更新日、既に直っている項目の消し込み
- **資料が実装と食い違っている**。実装したものが正で、資料が古いだけのもの
- **テストの穴**。既にある振る舞いに回帰テストを足す

ここまでは**実装・テスト・資料・課題の記録まで進めてよい**。コミットは別（共通ルール「修正は1点ずつ、確認を重視」に従い、指示を待つ）。

### 判断が要るもの

- **仕様を決める**。出力の形・オプションの既定値・クラス名を増やす
- **直し方が 2 つ以上ある**。共通ルール「複数の解決案がある場合の対応」に従って案を出す
- **ほかのプロジェクトに影響する変更**。生成物の形が変わるもの、共通ルールの書き換えが要るもの
- **元の指摘が手元に無く、拾い直しが要るもの**。調べる範囲が読めないため、先に見積もりを出す

これらは課題に残して報告だけにする。**消化のついでに決めない。**

> [!NOTE]
> 迷ったら「これを間違えたとき、直すのに何が要るか」で見る。<strong>コードを書き直すだけで済むなら判断は要らない。</strong>生成物やほかのプロジェクトに残るなら判断が要る。

## 3. 消化するときに踏んだ落とし穴

### 記録を先に「済」と書かない

実装する前に課題へ「済」と書き、外部（ai-chat-lite）にも直したと伝えたのに、<strong>コードを直していなかったことがある。</strong>まとめて消化していると、記録の更新だけが先に進む。

<strong>「済」と書くのは、テストを通したあと。</strong>共通ルール「課題の管理」の「まだ済んでいないものを済にするのは別」は、この順序のこと。

### 回帰テストを先に入れる

exe と ps1 の乖離は、<strong>テストを先に書くと、課題に挙がっていない分まで出てくる。</strong>リンク解決の食い違い（`i260911-02` の 6）では、指摘は検査の 2 経路だけだったが、テストを入れたら `.html` → `.md` 置換にも同じ原因があった。

直してからテストを書くと、**直した分しか見つからない。**

### 部分的なステージでコミットを分けない

1 つのファイルに 2 つの変更が混ざったとき、`git diff -U0` の一部だけを `git apply --cached` で載せてコミットを分けたところ、<strong>挿入位置が 7 行ずれて、中間のコミットが単体では動かない状態になった。</strong>零文脈のパッチは位置を照合できない。

分けられないときは<strong>1 つのコミットにまとめる。</strong>履歴の粒度より、各コミットが単体で通ることを優先する。

### issues.html は更新日の検査が効かない

`md-skip` のページなので `.md` が生成されず、<strong>html2md の「更新日が古い」検査に掛からない。</strong>書き換えたら自分で日付を直す。

### C# と TypeScript でフォルダ名が衝突する

`src/Text/`（C#）と `src/text/`（TypeScript）は**同じフォルダ**になり、`.cs` と `.ts` が混ざる。一般則は共通ルール「大小だけが違う名前を作らない」。

> [!WARNING]
> **2 度踏んだ**（`Text` と `Html2Md`）。1 度目に `src/TextCs/` へ分けたのに、2 度目も同じ手順を繰り返した。

**C# 側は `〜Cs` にする**（`ConvertEncodingCs` ・ `TextCs` ・ `Html2MdCs`）。移植を始める前に移す。あとから分けると、ビルドスクリプトの書き換えとビルドし直しが移植作業の途中に割り込む。

- 衝突するのは**ハイフンを含まない名前**。`ConvertEncoding` と `convert-encoding` は別フォルダになるので起きない
- 移す手順は共通ルール「ファイルの移動・分割・置き換え時の順序」に従う。**新しい場所でビルドが通ることを確かめてから元を消す**

### 移植で落ちるのは「言語が肩代わりしていた比較」

C# は `HashSet<string>(StringComparer.OrdinalIgnoreCase)` で<strong>大小を無視して比べていた。</strong>TypeScript の `Set` にその仕組みは無いので入れるときに小文字へ寄せた——が、**引くときを直し忘れた。**

`.html` → `.md` の置き換えが**すべて素通り**し、16 ケース中 8 ケースが落ちた。<strong>例外は出ず、リンクが `.html` のまま残るだけ。</strong>一般則は共通ルール「移植で落ちるのは、言語が肩代わりしていた比較」。

### 道具を作ったら、外側で同じことをしない

`psh` は PowerShell の出力を読み分けて UTF-8 で流す。<strong>その出力にさらに `iconv -f CP932` をかけて壊した。</strong>PowerShell を直接呼んでいた頃の手癖が残っていた。

> [!CAUTION]
> <strong>二重変換はエラーにならない。</strong>集計行が 1 行も出なくなり、「文字化けで読めない」と誤って報告した。実際はこちらが壊していた。

### cmd を書いたら必ず `--to cmd` を通す

共通ルール「bat / cmdファイルの文字コード・改行コード」にあるとおりだが、<strong>このセッションで 2 度忘れた。</strong>UTF-8 のまま置くと `'ら、ここを' は、内部コマンドまたは外部コマンド` で落ちる。

<strong>Write でファイルを作った直後に変換する。</strong>あとでまとめてやろうとすると、その間に実行して失敗する。

### ヒアドキュメントで作ったファイルが消えた

`cat > "$t" <<EOF` で作った `text` ・ `html2md` の sh 入口が、作成・動作確認のあとで**消えていた。**`rm foo.exe` が拡張子なしの `foo` を消すか再現を試したが**再現せず、原因は特定できていない。**

<strong>ファイルは Write ツールで作る。</strong>共通ルール「Python 等のヒアドキュメントでファイルを書き換えない」と同じ扱いにする。

### 置いてからテストしない

移植版の入口を `public/` に<strong>置いてからテストを回した。</strong>計画では「テストが全件一致してから置く」と決めていた。結果は全件一致で害は出なかったが、順序としては逆だった。

<strong>PATH に置いた瞬間、ほかのプロジェクトも移植版を使う。</strong>確かめてから置く。

### 「全部成功」は、何を検査したかを見るまで意味がない

移植が済んだあと、テストの既定が `〜-cs.exe` のままだった。`run-all-tests` は `-Target` を渡さないので、**一括実行はずっと C# 版を検査していた。**「8 本すべて成功」と何度も報告したが、**移植版は 1 ケースも通っていない**回があった。

気づいたのは、`text find` に変更を入れて 4 件落ちたとき。**変更を入れなければ、ずっと気づかない。**

> [!WARNING]
> 共通ルール「検索・集計の結果が 0 件なら、まず検索式を疑う」の裏返し。**成功の表示も、対象を見るまでは何も言っていない。**

### 移植の計画に「切り替え後の既定」を書く

計画（`p260912-02`）の「切り替えの後に回すもの」には 4 項目あったが、**「テストの既定をどちらにするか」が入っていなかった。**「`$Exe` を差し替えれば移植版に当たる」とだけ書き、**差し替えっぱなしにするか戻すかを決めていない。**

**2 つの実装が並ぶ期間を作るなら、どちらを既定にするかを先に決める。**

### 優先するランチャーがあると、もう一方は 1 ケースも通らない

入口は bun を優先し、無ければ node に落ちる。**bun のある環境では、node で 1 ケースも回らない。**「node でも動く」は `run-node-tests` の 8 件（起動して基本動作が通ること）しか確かめていなかった。

`tools/40_test/runners/` に node 専用の当て木を置き、**218 ケースを両方で回す**ようにした。時間は 2 倍（71 秒）になる。

## 4. chat の待受けは、無ければ自分で張る

適用条件: このプロジェクトで作業するとき。

- 共通ルール「ai-chat-lite（AI 間チャット）の利用」の「参加するのは利用者の指示があったときだけ。自分の判断で参加しない」と異なり、**このプロジェクトでは待受けが無ければ自分で張る**
- 作業の区切り（セッション開始時・大きな作業の切れ目等）に、共通ルール「ai-chat-lite（AI 間チャット）の利用」の手順に従って待受けの有無を確かめ、**誰も待受けていなければ自分で張る**

> [!NOTE]
> <strong>なぜ。</strong>共通ツールのメンテをしており、各プロジェクトから不具合報告・フィードバックを受けることが多い。窓口として常時聞いておく必要がある。

### 待受けの生死を cron でも確認する

- **3 時間毎に cron を張り、待受け（`aichat wait`）の生死を確認する**。`aichat waiters` で数え、0 本なら張り直す
- **新着の有無にかかわらず、毎回「月/日 時:分」の見出しを付けて報告する**。新着があれば概要を添え、無ければ「新着なし」と書く
- **共通ルール「終わったら親が、数えてから黙って張り直す（報告は要らない）」の例外**。ここでは生死確認そのものを定期的に可視化する目的があるため、新着の有無によらず毎回報告する
- **cron は共通ルール「cron はセッションの中だけで生きる」に従い 7 日で失効し、ディスクに残らない**。セッションを開き直したときは「セッションを開き直したとき」に従い張り直す
