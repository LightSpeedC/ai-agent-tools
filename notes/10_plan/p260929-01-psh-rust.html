背景と狙い

psh は PowerShell を呼び、出力を UTF-8 に直して流す当て木（src/psh/psh-main.ts）。入口の bin/psh.cmd ・ bin/psh が bun を優先し、無ければ node で走らせる。

Rust にすると、次が見込める（全部を狙う。とくにコードページ・パイプとプロセスツリーの深さ。第 6 章）。

  • bun がコードページを 65001 にする件を避けられる。bun は動いている間、窓の入力・出力のコードページを 65001 にする（共通ルール「Bun 同士のパイプは文字化けすることがある」）。bun から起動した PowerShell はその状態で起動するため、ps1 の中で SJIS を出す cmd や .NET Framework の exe の出力を受け取ると、psh に届く前に化けるおそれがある（未検証）。Rust の exe はコードページに触らない
  • bun 同士のパイプを避けられる。psh … | text … のように相手が bun のとき、oven-sh/bun#43660 に当たる（課題 i260927-01）
  • 処理系が要らない。bun も node も無い環境で動く
  • プロセスとメモリが軽くなる。処理系が 1 段減る見込み（前後で実測する。第 5 章）
  • 起動が速い（ランタイムの起動が要らない。どれだけ速くなるかは実測する）

環境: cargo 1.96.1 ・ rustc 1.96.1 が入っている（2026-09-29 に確認）。

守る仕様

いまの main.ts の動きを変えずに移す。移植で動きを変えない。変えたいものは移植と別に決める。

項目いまの動き
呼び方psh <path.ps1> [引数...]（-File）、psh -c "<式>" ・ --command（-Command）。どちらも -NoProfile -ExecutionPolicy Bypass を付ける
処理系既定は powershell（5.1）。先頭の --pwsh で pwsh（7）
使い方先頭の --help ・ -h は標準出力へ出して 0。引数なしは標準エラーへ出して 2。psh x.ps1 --help の --help は ps1 に渡す
終了コードPowerShell のものを素通し。ps1 が無い・-c に式が無い・起動できない・シグナルで落ちたときは 2
出力標準出力と標準エラーを分けたまま、終わるまでまとめて受け取ってから流す
文字コード全体を UTF-8 として厳密に読み、読めなければ行（\n まで）ごとに UTF-8 → CP932 の順で読み分ける。CP932 は WHATWG の shift_jis（Windows-31J の表）
標準入力起動した直後に閉じる（課題 i260927-03 で扱いを検討中）
引数の渡し方シェルを挟まず配列で渡す。空白・引用符を含む引数が割れない
i260927-03（標準入力を渡さない）とは切り離す。移植では「閉じる」をそのまま写す。扱いは移植が済んでから決める（第 6 章の 5）。

実装の方式

  • 子プロセス: std::process::Command で配列のまま起動し、output() で標準出力・標準エラーを受け取る。標準入力は Stdio::null()（すぐ閉じるのと同じ）
  • UTF-8 の厳密な判定: std::str::from_utf8（標準ライブラリ）
  • CP932 の読み: encoding_rs（WHATWG のエンコーディング仕様の実装）。いまの TypeScript 版の TextDecoder('shift_jis') と同じ表なので、結果が一致する。Windows の MultiByteToWideChar を直接呼ぶ案は保留（第 6 章）
  • 出力: 読み直した文字列を UTF-8 のバイト列として書く。コンソールのコードページは変えない（共通ルール「コンソールのコードページを変更しない」）。Rust の標準出力は、窓に直接書くときは UTF-16 で書き込むため、コードページに関係なく化けない（リダイレクトされていれば UTF-8 のバイト列のまま）
  • 表示文言: 使い方・エラーの文言は TypeScript 版と同じ日本語にする

置き場と呼び出し

  • ソース: src/psh-rs/（Cargo のプロジェクト）。src/psh/（TypeScript）とは大小違いではなく接尾辞で分ける（共通ルール「大小だけが違う名前を作らない」）
  • ビルドの出力: Rust の既定の target/。.gitignore に target/ を足す（共通ルール「トップレベル」で dist は言語の既定に読み替える）。exe は git に含めない（i260830-16 の決定どおり）
  • ビルド: tools/20_build/build-psh-rs.cmd（cargo build --release）
  • 入口: bin/psh.cmd ・ bin/psh を「Rust の exe（psh.exe）があればそれ、無ければ今までどおり bun → node」にする（第 6 章の 3）。exe を bin/ に直接置かない（Windows は psh.exe を psh.cmd より先に見つけるため、入口の切り替えが効かなくなる）
TypeScript 版は消さない。共通ルール「移植で落ちるのは、言語が肩代わりしていた比較」の「元の実装を消さない」に従い、突き合わせる相手として残す。消す時期は利用者が指示する（第 6 章の 4）。

テスト方針

  • いまの 22 件をそのまま両方に当てる。run-psh-tests.ts は main.ts を処理系で直に呼ぶ作りなので、対象を exe に差し替えられるようにする（引数か環境変数）
  • 移す前に、両方の出力を突き合わせるテストを足す（共通ルール「移植で落ちるのは…」）。とくに文字コードの読み分け: UTF-8 だけ・CP932 だけ・行ごとに混ざる・行の途中で \r\n を含む・末尾に改行が無い。同じバイト列を両方に読ませ、結果が一致すること
  • run-all-tests で両方を回す。ローカルルール「優先するランチャーがあると、もう一方は 1 ケースも通らない」を踏まない。exe が無いとき（ビルドしていない環境）は Rust 側を飛ばしたと表示する（黙って成功にしない）
  • 入口を切り替えるのは、両方で全件が通ってから（ローカルルール「置いてからテストしない」）
  • 起動の速さを実測し、資料に残す

プロセスツリーとメモリ使用量の比較

Rust 版を書く前に、bun と node で測っておく（あとから測ると、前の状態に戻して測り直すことになる）。Rust 版ができたら同じ手順で測り、3 つを並べる。

  • 測り方: 数秒止まる ps1（Start-Sleep）を psh に走らせ、その間に psls でツリーと物理メモリを取る。bun ・ node は処理系を名指しして起動する（bun src/psh/psh-main.ts … ・ node src/psh/psh-main.ts …）。入口の cmd ・ sh を通す場合と、通さない場合の両方
  • 見るもの
    • ツリー: 入口（cmd ・ sh）→ 処理系（bun ・ node ・ psh.exe）→ powershell の段数と、途中に挟まるプロセス
    • メモリ: 各段の物理メモリ。psh 自身の分と、powershell の分を分けて書く（powershell の分はどの実装でも同じはずなので、差が出たら理由を調べる）
    • 終わったあとに残るプロセスが無いこと（共通ルール「残ったプロセスを調べるときは psls を使う」）
  • 回数: それぞれ 3 回測り、ばらつきも書く
  • 置き場: 測る手順は tools/90_misc/bench-psh/ に置き（既存の bench-html2md ・ bench-check-public と同じ置き場）、結果はこの計画書に表で残す

tests/psh/callexe.ps1 は .NET 製の exe の例として、tests/psh/callexe.cs を Windows 標準の csc で tmp/ にビルドして呼ぶ。

決めたこと

2026-09-29 に利用者が決めた。

  1. 狙い: 第 1 章の見込みの全部。とくに bun のコードページとパイプの問題、プロセスツリーが深いこと。コードページの件は、移植の前に「bun から起動した PowerShell の中で化ける」ことを実測で確かめる
  2. CP932 の読み方: encoding_rs。Windows API は保留
  3. 入口の優先順: psh.exe があればそれを使う
  4. TypeScript 版: まだ消さない。消す時期は利用者が指示する
  5. 標準入力（i260927-03）: 移植のあとで扱う

進める順

  1. bun ・ node の測定（プロセスツリー・メモリ）と、コードページの件の実測（第 5 章）
  2. 文字コードの読み分けを両方に当てる突き合わせのテストと、run-psh-tests の対象の差し替え
  3. Rust 版の実装とビルドスクリプト
  4. 両方で全件が通ってから、入口を psh.exe 優先に切り替える
  5. Rust 版で同じ測定をし、結果を並べる。資料（TOOLS-USAGE の第 6 章）を更新する

実装の結果（2026-09-29）

1〜5 を済ませた。全テストが通る（psh は TypeScript 版を bun ・ node で、Rust 版を bun ・ node の両方から呼んで、それぞれ 53 件）。

コードページの件（実測）

psh の起動元PowerShell のコードページSJIS の cmd の出力の取り込み
bun（TypeScript 版）65001化ける
node（TypeScript 版）932正しい
  • Rust 版にしても、呼び出し元に bun がいれば 65001 のまま（bun が窓を変え、同じ窓の子に及ぶ）。
  • PowerShell を自分専用のコンソール（CREATE_NO_WINDOW）で起動すると 932 になり SJIS は読めたが、今度はこのリポジトリのツールの UTF-8 を取り込む ps1（テスト）がすべて化けた。いままで通っていたのは、bun が窓を 65001 にしていたため。
  • どちらのコードページでも、片方の出力は化ける。取り込みは PowerShell の中で起き、psh の読み分けは届かない。

計画と違えた点（利用者の決定）

  • PowerShell を UTF-8（65001）に固定する。TypeScript 版も同じ。UTF-8 のツールの出力を正しく取り込み、SJIS を取り込むと化ける
  • 固定のしかた: 自分専用のコンソールで起動し、最初の 1 行で PowerShell 自身にそのコンソールを 65001 にさせる。外から一時停止中に設定する案は、一時停止中はコンソールがまだ無く接続できなかった（実測）。起動直後に外から設定する案は動いたが、競争に勝っているだけで保証が無い
  • 共通ルール「コンソールのコードページを変更しない」に、例外「自分専用に作ったコンソールは変えてよい」を足した（利用者が反映）
  • -File をやめ、-Command の中から ps1 を呼ぶ。- で始まる語は引数の名前、それ以外は単一引用符で囲んだ値として並べ直す（配列を渡す形では、名前付きの引数が名前として結び付かなかった）。trap { break } で、引数の結び付けの失敗を -File と同じ終了コード 1 にする
  • -File との違いが 1 つ残る: exit を書かない ps1 の最後で外部コマンドが失敗すると、-File は 0、psh はその終了コードを返す
  • 別のコンソールで起動しないで済む方法は、課題 i260929-04 に残した
