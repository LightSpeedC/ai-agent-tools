背景

課題 i260929-01。src/lib/detector.ts の detect() は、UTF-8 と SJIS の両方で成立し非 ASCII を含むバイト列を null（判定しない）にする。半角カナの SJIS（ﾂｱ = C2 B1）が UTF-8 の ± と同じ形になるためである。

ところが UTF-8 の日本語（あ = E3 81 82）も SJIS の並びとして成り立ちやすく、ふつうの日本語の UTF-8 まで止まる。bin/cx.cmd を UTF-8 にしたものは、SJIS の構造検査も CP932 の厳密なデコードも通った。

案 A（UTF-8 の 2 バイト列を含まなければ UTF-8）では、× ° ± を含む日本語の UTF-8 が直らない。そのため B を採る。

判定の方式

BOM の判定と、片方だけが成立する場合は今までどおり。変えるのは「両方で成立し、非 ASCII を含む」場合だけ。

2 つの点数

両方で読み、読んだ文字が「よく使う文字」かを数える。非 ASCII の文字だけを数え、ASCII はどちらで読んでも同じなので入れない。両方に同じ物差しを当てる。

  • Nu: UTF-8 で読んだ非 ASCII の文字のうち、よく使う文字の割合
  • Ns: SJIS で読んだ非 ASCII の文字のうち、よく使う文字の割合

よく使う文字は、ひらがな（U+3041〜U+3096）・カタカナと長音（U+30A1〜U+30FC）・全角空白と句読点（U+3000〜U+3003）・全角英数（U+FF01〜U+FF5E）・半角カナ（U+FF61〜U+FF9F）・JIS 第一水準の漢字（SJIS の先頭 88〜98 の字）。

決め方

  • Nu ≧ 0.75 かつ Nu ＞ Ns → UTF-8
  • Ns ≧ 0.9 かつ Nu ≦ 0.1 → SJIS
  • それ以外 → 今までどおり null（止まる）

しきい値の根拠（2026-09-29 に実測）

このリポジトリの cmd ・ ps1 55 件から、非 ASCII を含む行を 1 行ずつ切り出し、元の文字コードと、もう一方へ変換したものの両方を測った。

結果行数
片方だけ成立（今の判定で決まる）2,050
両方成立。すべて UTF-8 で、案では UTF-8（全件当たり）207
  • 両方成立した 207 行: Nu の最小 0.83、Ns の最大 0.80、差の最小 0.20
  • 半角カナの SJIS（ﾃｽﾂｱ）: Nu 0.00、Ns 1.00
  • ファイル単位（BOM を除いたとして）では、両方成立するものは 0 件
計画時の S（先頭バイトで数える）は使えなかった。UTF-8 の 2 バイト目以降（81〜BF）が SJIS のかな・記号の先頭として読まれ（82 E3 は「ゃ」）、UTF-8 の日本語でも 0.6 前後になった。文字単位の物差しに替えた。
両方成立する SJIS の実例は見つからなかった。SJIS のかな（先頭 82 ・ 83）は UTF-8 ではすぐに崩れるため。SJIS 側の条件と「止まる」側は、手で作ったケースでしか確かめていない。

変更する範囲

  • src/lib/detector.ts: 点数を出す関数と、両方で成立したときにそれを使う判定を足す。detect() から呼ぶ
  • src/text/engine.ts の detectCombo(): いまは両方で成立すると UTF-8 に倒して ambiguous を立て、edit ・ write が拒否する。同じ判定を使い、決まったときは ambiguous を立てない
  • C# 版: src/ConvertEncodingCs/Detector.cs と、src/TextCs/ の同じ判定を揃える
  • 資料: TOOLS-USAGE の判定の説明と、issues.html の i260929-01

テスト方針

共通ルール「テストを先に書く」に従い、直す前に落ちるテストを書き、落ちるのを見てから実装する。期待値は手で書く。

ケース期待いま
cx.cmd を UTF-8 にしたもの（報告された再現条件）utf8null
カタカナ語（ファイル）の UTF-8utf8null
± を含む日本語の UTF-8（ドライブ±）utf8null
半角カナだけの SJIS（ﾃｽﾂｱ = C3 BD C2 B1）sjisnull
どちらとも言えない並び（C2 B1 E3 82 A2。UTF-8 で ±ア、SJIS で ﾂｱ繧｢）null（止まる）null
純 ASCII ・ BOM 付き ・ 片方だけ成立するもの今までどおり―

既存の全テストを bun と node の両方で通す。text の既存テストは両方成立の例に C2 B1 を使っている。これは SJIS に決まるようになるため、止まる例（C2 B1 E3 82 A2）に差し替える。

決めたこと

  1. しきい値: 第 2 章のとおり（0.75 ／ 0.9 ／ 0.1）
  2. text の edit ・ write にも効かせる。今は拒否しているファイルを書き換えられるようになる
  3. C# 版も揃える

実装の結果（2026-09-29）

  • 第 2 章の判定を src/lib/detector.ts の decideAmbiguous に置き、detect() と text の detectCombo() から呼ぶ。C# 版（ConvertEncodingCs/Detector.cs ・ TextCs/Engine.cs）にも同じものを入れた
  • 第 4 章のケースを先に書き、落ちるのを見てから直した。全テストが bun ・ node とも通る
  • 計画と違えた点: 第 4 章の番号は、convert-encoding の仕様書 6 章「両方とも妥当になる並び」の 32〜37（テストが未実装だった）と、新しく足した 57〜61 に振った。仕様書のケース 32（C2 B1）は「止まる」から「SJIS に決まる」へ変わった
  • 副作用: 判定できずに文字コードの検査を素通りしていた tests/cases/ の HTML 4 件が BOM 無しと分かった。BOM を付けた
  • C# 版には判定と関係のない以前からのずれが 8 件あった。課題 i260929-02 に残した
