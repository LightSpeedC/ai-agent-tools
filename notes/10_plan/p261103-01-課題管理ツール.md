# p261103-01 課題管理ツール 計画 (ai-agent-tools)

課題が大きくなったプロジェクトのために、課題を 1 件 1 ファイルで持ち、AI エージェントが読み書き・検索でき、人向けの HTML も出せる共有ツールを作る。保存方法を比べ、案と決めることを示す。

> 📅 作成: 2026-11-03 / 更新: 2026-11-03

[^^](../../README.md)

**対象 ・ 入力 ・ 出力**: 対象は ai-agent-tools (共有ツールの置き場)。入力は、各プロジェクトの課題 (まず ai-agent-tools の `notes/40_issues/issues.html`)。出力は、課題の保存形式の案と、課題を扱う共有 CLI と、人向けの HTML 生成の案。**この計画は案と決めることの提示まで。承認をいただくまで実装しない。**

> [!IMPORTANT]
> **結論 (推奨)**: **課題を 1 件 1 ファイルのテキスト (先頭に `キー: 値` のメタ情報、本文は Markdown。形式は F2、第 3 章) で持ち、これを正本にする**。SQLite は**正本にせず**、ファイルから作り直せる索引 (検索・集計用) に使う。`issues.html` のような人向け HTML は、ファイルから**生成**する。操作は共有 CLI 1 本にまとめ、AI エージェントはそれと、ふだんの Read ・ Edit ・ Grep の両方で扱える。

## 1. 目的と現状

### やりたいこと

- **各プロジェクトで課題を管理する**。課題が大きくなったプロジェクト (file-manager 等) が、自分の中で完結して持てる
- **全体でも使える**。プロジェクトをまたいで、未・着手の課題を横断して見られる
- **commit できて、差分が読める**。「いつ・何が・なぜ変わったか」が git の履歴で追える
- **人が読む見た目**は、いまの `issues.html` のような HTML
- **AI エージェントが読み書き・検索しやすい**。1 件を開いて読める、状態を 1 行で変えられる、条件で探せる

### いまの `issues.html` の実測

| 項目 | 値 | 読み取れること |
|---|---|---|
| issues.html の大きさ | 214 KB ・ 1224 行 | 1 回の Read で全部は読めない。部分読みの位置合わせが要る |
| 課題の数 (`class="no"`) | 68 件 | うち未・着手は 3 件 (済が大半。済は元のグループに残す決まり) |
| issues-archive.html | 70 KB | グループごと片付いたものの置き場。本文は書き換えない決まり |

### いまの形で困っていること

- **1 ファイルに全件があるので、変更が混ざる**。複数のセッションが同じファイルを書き換えると、commit に別の変更が入る (共通ルール「修正は1点ずつ、確認を重視」の背景)
- **件数・状態を手で数え直している** (共通ルール「課題の管理」: 件数と状態は中身から数え直す)。ずれたら直す運用は、機械が行えば要らない
- **探すのに Grep で HTML の行を拾う**。「着手の課題だけ」「報告元が ai-chat-lite のもの」といった問いに、一発で答えられない
- **「報告元の確認が取れるまで済にしない」が文章の決まりだけ**。記録を先に「済」にした失敗が実際にあった (ローカルルール第 3 章)
- 課題が大きくなると、1 件の中の「やること」と経過が長くなり、`issues.html` の全体が読みにくくなる

なお、共通ルール「課題の管理」には「1 件が長くなってきたら 1 件 1 ファイルへ切り替える (`i260830-13-件名.html`)」がすでにある。この計画はその延長で、**切り替え方を道具にする**もの。

## 2. 保存方法の比較

候補は 6 つ。「commit できる」「差分が読める」「競合しにくい」「AI が扱いやすい」「人の見た目」で見る。外部ツールの説明は、Web 検索で得た紹介の範囲で、**実際には動かしていない**。

| 案 | 正本 | 差分 | 競合 | AI の扱い | 人の見た目 |
|---|---|---|---|---|---|
| ① 1 件 1 ファイル (テキスト) | ファイル | ✅ **良い** 1 件の変更が 1 ファイルの数行になる | ✅ **良い** 別の課題を直せば別ファイル | ✅ **良い** Read ・ Edit ・ Grep がそのまま効く | 生成する (HTML) |
| ② 1 つの JSONL (1 行 1 件) | ファイル | ⚠️ **注意** 1 件 = 1 行で、長い本文の差分が読みにくい | ⚠️ **注意** 同じファイルを複数が触る | ⚠️ **注意** 1 行が長く、Edit が難しい | 生成する (HTML) |
| ③ SQLite を正本にする | DB (バイナリ) | ❌ **悪い** 差分が読めない。レビューできない | ❌ **悪い** 同時に書くと、どちらかが失われる。`-wal` ・ `-shm` の扱いも要る (共通ルール「SQLite の大原則」) | ⚠️ **注意** SQL では探しやすいが、中身を直接 Read できない | 生成する (HTML) |
| ④ HTML のまま (いまの形) を道具で編集する | HTML | ⚠️ **注意** タグを含むので差分が読みにくい | ⚠️ **注意** 全件が 1 ファイルの間は混ざる | ⚠️ **注意** 構造が自由すぎて、機械的に読み書きしにくい | ✅ **良い** そのまま |
| ⑤ git のオブジェクトに入れる (git-bug 型) | git の参照 (作業ツリーに現れない) | ⚠️ **注意** 操作の列を重ねる形。ファイルの diff では読めない | ✅ **良い** 競合しにくい設計 | ⚠️ **注意** 専用ツール経由のみ。Read ・ Grep では見えない | 専用の画面 |
| ⑥ 既存ツールを採る (Beads ・ Backlog.md) | ツール次第 | ツール次第 (下の注) | ツール次第 | どちらも AI 向けを掲げる | ツールの画面 |

### 外部ツールについて分かったこと (紹介記事の範囲)

- **Beads (`bd`)**: AI エージェント向けの、git に載せる課題管理。CLI のみで、JSON 出力・依存関係・「いま着手できる課題」の問い合わせ・ハッシュの ID (競合を避けるため) を持つ。保存は版で変わった (古い版は JSONL ＋ SQLite の写し、新しい版は Dolt というバージョン管理付き DB)。**人向けの画面を持たない**。ID の付け方 (ハッシュ) と、いまの ID の決まり (`i` ＋ 日付 ＋ 連番) が合わない。出典: [Better Stack の紹介記事](https://betterstack.com/community/guides/ai/beads-issue-tracker-ai-agents/)
- **Backlog.md**: Markdown のファイルを 1 件 1 ファイルで持つ、git の中のタスク管理。CLI ・ ブラウザの画面 ・ MCP を持ち、TypeScript 製。**形が①にいちばん近い**。ただし状態の名前 (未・着手・済の 3 段階) ・ ID ・ 日本語表示・見た目が、こちらの決まりと合うかは未確認。出典: [Backlog.md のリポジトリ](https://github.com/MrLesk/Backlog.md)
- **git-bug**: 課題を git のオブジェクトとして持ち、操作の列を重ねて現在の状態を計算する。**作業ツリーにファイルが現れない**ので、このプロジェクトの「差分を commit で読む」「Grep で探す」の前提と合わない。出典: [git-bug のデータモデル](https://www.github.com/MichaelMure/git-bug/blob/master/doc/model.md)

> [!IMPORTANT]
> **見立て**: ③ (SQLite を正本) と ⑤ (git のオブジェクト) は、「commit して差分で読む」「AI が Read と Grep で扱う」の 2 条件で外れる。②・④ は、全件が 1 ファイルに集まる弱点が残る。**残るのは ① と ⑥ (Backlog.md)**。⑥ は試さずに採るか決められないので、計画に試用の手順を入れる (第 5 章)。

## 3. 推奨する構成

案 ① を骨格にし、SQLite は「作り直せる索引」にだけ使う。構成は 4 層。

| 層 | 中身 | git | 誰が書くか |
|---|---|---|---|
| 正本 | 課題 1 件 = 1 ファイル。`notes/40_issues/items/i261103-01-li内の表.md` のような置き場 | 管理 | CLI と AI (Edit)。人も読める |
| 索引 | SQLite (FTS5 の全文検索)。ファイルから作り直せる派生物 | 除外 (先頭 `_` のフォルダ) | CLI が自動で作り直す |
| 人向けの表示 | `issues.html` (いまと同じ見た目。章ごとの色、`details` の開閉、状態のバッジ) | 管理 (案 95-A) | CLI が生成する。手で直さない |
| 全体の横断 | 登録したプロジェクトの課題を集める読み取り専用の索引と HTML | 管理外 (集約側) | CLI (後続のフェーズ) |

### ファイル形式 (決定: F2)

**決定 (2026-11-03、利用者の判断): F2**。先頭に `キー: 値` の行を並べ、本文は Markdown にする。メタ情報の書き方を、YAML の部分集合に絞った**自作の単純な形**にする。比べた候補は次のとおり。

| 案 | 形 | 良い点 | 気になる点 |
|---|---|---|---|
| F1 | Markdown ＋ YAML のメタ情報 | 見慣れた形。GitHub でメタ情報が表で出る。Backlog.md に近い | YAML の型の落とし穴 (`true` ・ 数字 ・ コロン)。パーサが要り、依存が増える |
| **F2 (採用)** | Markdown ＋ 自作の `キー: 値` 行 | 数十行で読み書きでき、依存が増えない。落とし穴を仕様で潰せる | 独自仕様なので、仕様書が要る。ほかのツールは直接読めない |
| F3 | Markdown ＋ TOML | 型が素直 | bun ・ node の標準に読み込みが無く、パーサが要る |
| F4 | メタ情報を別ファイル (JSON ＋ `.md`) | JSON は標準で読み書きできる | 1 件が 2 ファイルになり、差分と commit の単位が割れる |
| F5 | HTML の断片 (94-B) | いまの課題を無損失で移せる | タグが混ざり、AI の編集と差分が読みにくい |
| F6 | JSON 1 件 1 ファイル | 機械で確実に読み書きできる | 長い本文が 1 行の文字列になり、差分が読めない |

### キー項目 (案)

| キー | 必須 | 値 | 備考 |
|---|---|---|---|
| `schema` | 必須 | 整数 (いまは 1) | 形の版。あとで項目を足すときに読み替える |
| `id` | 必須 | `i` ＋ `yymmdd-nn` (nn は 36 進数 2 桁) | ファイル名の先頭 (`<id>-<件名>.md`) と一致させる。重複は `issue check` が止める |
| `title` | 必須 | 1 行の文字列 | 最初の `: ` で分けるので、値の中にコロンがあってもよい |
| `state` | 必須 | `未` / `着手` / `済` | 3 段階 (共通ルール「課題の管理」)。`済` は、やることが残っている間・報告元の確認が無い間は拒否する |
| `group` | 必須 | 文字列 | いまの章 (グループ) の名前。表示順の持ち方は 109 |
| `created` | 必須 | `yyyy-mm-dd` (JST) | 立てた日。変えない。書式は「ドキュメントの作成日・更新日」と同じ |
| `from` | 任意 | 文字列 (`プロジェクト名 #発言番号`) | 報告元。他プロジェクトからの報告のときだけ書く |
| `confirmed` | `from` があるとき必須 | `true` / `false` | 報告元の確認。`true` になるまで `済` にできない |
| `refs` | 任意 | カンマ区切りの番号 (`p261103-01, r261025-01`) | 計画・調査の番号。`issue check` が、参照先の有無を確かめる |

**置かないキー**: `updated` (更新日。持つかは 108) ・ 優先度 ・ 担当 ・ ラベル ・ 期限 ・ 依存。いまの運用に無く、足すかは 107。

### F2 の書き方の決まり (案)

- **先頭行が `---`、次の `---` までがメタ情報**。1 行 1 キー
- **`キー: 値` の形**。最初の `: ` で分け、前後の空白を除く。キーは小文字の英数字と `_`
- **引用符・コメント (`#`)・複数行・入れ子は使わない**。`#` が値の一部 (`#1737`) になるので、コメントは無い
- **値の型は 4 つだけ**: 文字列 ・ 整数 ・ 真偽 (`true` / `false`) ・ 一覧 (カンマ区切りの文字列)。どのキーがどの型かは、キー項目の表が決める。型の取り違えは `issue check` が止める
- **値が空のキーは書かない**。任意のキーは、無ければ省く
- **キーの順は固定** (表の順)。CLI は必ずこの順で書く。直接 Edit で順が変わっても読めるが、`issue check` が警告する
- **知らないキーは、CLI が書き戻すときも残す**。`issue check` が警告する (将来の版の項目を、古い CLI が消さないため)
- **UTF-8 (BOM 無し) ・ LF**。`.editorconfig` の `*.md` の決めと同じ
- **YAML のパーサでも同じ値に読める範囲に収める**。将来 F1 に替えるときの道を残すため。ただし、Backlog.md との互換は保証しない

### ファイル名と置き場 (案)

- **置き場は 2 つ**: `notes/40_issues/items/` (進行中。済も、グループが片付くまでここに残す) と、`notes/40_issues/items/archived/` (グループごと片付いたもの)。**状態ではフォルダを分けない**。状態は `state` キーだけが正本で、状態を変えてもファイルは動かない
- **ファイル名は `<id>-<件名>.md`** (例: `i261103-01-li内の表.md`)。件名は**立てるときに決める短いスラッグ**で、**あとから変えない**。題を直しても名前は動かず、パスが安定する。題は `title:` に自由に書ける
- **件名の決まり**: 30 文字ほどまで。使える文字は共通ルール「ファイル・フォルダの名前に使ってよい文字」に従う (英数字 ・ ハイフン ・ 下線 ・ ピリオド ・ 日本語。空白なし)。`issue new` は題から案を作り、使えない文字を `-` に直す
- **同じ ID の重複を、2 段で止める**。件名が違うと別のファイルになり、git でも競合しないので、ファイルの排他だけでは防げない。
    - **同じ PC**: 立てる前に、`notes/40_issues/_lock/<id>/` を `mkdir` で作る (先頭 `_` のフォルダは Git 管理外。`mkdir` は既にあれば失敗するので排他になる)。取れなければ次の番号にし、立て終えたら消す
    - **別の PC ・ クラウド**: `issue check` が、同じ ID のファイルが複数ないかを止める。`issue check` は commit の前の決まりにし、pull のあとにも流す
- **`archived/` に入れるのは、グループの全件が済になったときだけ** (`issue archive <group>`)。`git mv` で動かし、本文は書き換えない。`group` キーは残る。`issue check` は、`archived/` の中がすべて済であることを検査する
- **一覧と検索は、既定で `archived/` を見ない** (`--all` で含める)。Grep を使うときは `items/*.md` に絞る
- **参照は ID で書く** (`refs` ・ 資料の文中)。パスで書かない。ID からパスを引くのは CLI。パスが動くのは `archived/` へ移すときだけだが、件名が名前に入るので、パスを直接書くと壊れやすい

### 識別子と索引 DB の表 (決定: 122-A ・ 123-A ・ 124-A ・ 125-A)

**決定 (2026-11-03、利用者の判断)**。PC とクラウドで、同じ DDL ・ 同じ `schema_version` の索引 DB を使う。「どのプロジェクトか」と「どの checkout (clone) の観測か」を、別の識別子で持つ。**ホスト名とコンピュータ名は、キーにも列にも使わない** (共通ルール「機密情報のマスキング」の対象であり、クラウドのコンテナ名は毎回変わるため)。

- **`project_id` (122-A ・ 125-A)**: リポジトリに commit する UUID のファイル `notes/40_issues/items/project-id.txt`。F2 と同じ `キー: 値` の行で、`---` の区切りは付けず、ファイル全体をメタ情報として読む。キーは `schema` と `project_id` (小文字 32 桁の 16 進数、ハイフンなし)。`project_name` はファイルに持たず、フォルダ名から読む (リネームで古くならないため)。`issue init` か、最初の `issue new` が作る
- **`checkout_id` (123-A)**: DB の `meta` に、作るときの乱数の UUID を入れる。DB を捨てれば、新しい観測として始まる。**横断の DB は、各プロジェクトの DB を取り込まず**、課題のファイルを直接読み直す。登録 1 件ごとの `checkout_id` は、横断の DB の中で覚える (毎回作り直すと、全行が新しい観測になるため)
- **同じ DDL (124-A)**: PC とクラウドで、表の定義も `schema_version` も同じにする。クラウドは環境が毎回作り直されるので、最初の呼び出しで DB を作り直す
- **`issue check` が見ること**: `project-id.txt` が無い・形が違う。同じ `project_id` なのにフォルダ名が違う (フォルダごとコピーの検出。横断で見る)。`items/` の `.md` に、`i` で始まらない名前が混ざっている

| 表 | 主キー | 主な列 (案) |
|---|---|---|
| `project` | `project_id` | `project_name` (フォルダ名) |
| `checkout` | `checkout_id` | `project_id` ・ `environment_kind` (`local` / `cloud`) ・ `created_at` ・ `last_scanned_at` |
| `issue_file` | (`checkout_id`, `file_path`) | `issue_id` ・ `file_modified_at` ・ `file_bytes` ・ `file_sha256` ・ `cached_at` ・ 課題の内容。`file_path` は、プロジェクトのルートからの相対パス |

列名と表名は、共通ルール「DB 定義のルール」に従う (日時は JST の 23 文字、語尾は `_at`)。**列は案**で、変更の判定方法 ・ 全体を捨てる条件 ・ 日本語の検索などの決めること (検討中) が決まると変わりうる。主キーを `file_path` にするのは、同じ ID が複数のファイルにあっても衝突させないため。

### 索引 DB と、ファイルの更新日付との比較 (案)

索引 DB は**派生物**で、捨てても課題のファイルから作り直せる。各行に「元のファイルのどの状態から作ったか」を持たせ、現在のファイルと比べて、捨てる行を決める。<strong>比べ方は「ファイルのほうが新しいか」ではなく「前と同じか」</strong>にする。`git checkout` で古い版へ戻すと更新日時は戻した時刻 (新しい) になり、`cp -p` や zip の展開は古い更新日時のまま内容だけが違うファイルを作る。「新しければ作り直す」では後者を見逃す。

| ファイルの状態 | 判定 | 動き |
|---|---|---|
| 更新日時もサイズも同じ | 変わっていない | 読まない (`stat` だけ) |
| 更新日時だけ違い、サイズは同じ | 中身を確かめる | SHA-256 が同じなら、更新日時だけ直す (checkout や touch) |
| 更新日時かサイズが違い、SHA-256 も違う | 変わった | 再解析して、行を置き換える |
| ファイルが無くなった | 消えた | 行を削除する |
| ファイルが新しく現れた | 増えた | 行を追加する |
| ID は同じで、パスだけ違う (`archived/` へ移動) | 動いた | SHA-256 が同じなら、パスだけ直す |

- **全体をまとめて捨てる条件**: `meta` に持つ `schema_version` (形の版) と `parser_version` (ファイルの読み方の版) の違い、DB の破損。捨てるときは、本体 ・ `-wal` ・ `-shm` を**3 つまとめて**捨てる (共通ルール「SQLite の大原則」)。作り直しは、一時の DB に作ってから置き換え、途中で止まっても半端な DB を残さない
- **形が変わったら、捨てて作り直す**。派生物なので移行は要らない。共通ルール「DB 定義のルール」の「版管理」(`ver_000001/`) の例外にあたる。ローカルルールへの書き方は、案を示して指示を待つ
- **置き場**: プロジェクトごとの DB は `notes/40_issues/_index/issues.sqlite` (先頭 `_` のフォルダなので Git 管理外)。横断の DB は ai-agent-tools の `_` フォルダ
- **効果は測ってから決める** (共通ルール「性能」)。いまの課題は 68 件で、全部を Grep するだけでも速い可能性がある。効くのは、全文検索と横断が入ったとき。`stat` の走査の時間は未測定
- **日本語の全文検索は未確認**。FTS5 の標準の分かち書きは日本語に向かない。`trigram` なら部分一致できるが、2 文字以下の語は引けない。組み込みの SQLite に FTS5 があるかを、bun と node で実測する
- **更新順の一覧には使えない**。ファイルの更新日時は checkout で変わる。更新順が要るなら、108-B (`updated` キー) か `git log` から取る

### 範囲: プロジェクト ・ PC 内の全体 ・ クラウド (案)

- **プロジェクトローカル** (この計画の主題): CLI は、作業フォルダから親をたどって `notes/40_issues/items/` を探す。見つからなければ `--root`。ほかのプロジェクトを読み書きしない
- **PC 内の全体 (横断)**: 登録リストに載せたプロジェクトだけを、**読み取り専用**で集める。外を読む承認は、登録のときに利用者が取る (共通ルール「プロジェクトフォルダ外へのアクセス」)。ID はプロジェクトをまたぐと重なりうるので、`プロジェクト名 + ID` で指す。**出力は commit しない** (他プロジェクトの課題が、public のリポジトリに載る恐れがあるため)
- **クラウド**: ファイルが git の中にあるので、プロジェクトローカルはそのまま動く。条件は、PowerShell が無いので拡張子なしの sh 入口を `cloud-session-start` の PATH に乗せること、TypeScript の本体が Linux で動くこと (未実測)、同じ PC にしか効かない `_lock/` の代わりに `issue check` が重複 ID を止めること。横断は、ほかのリポジトリが clone されておらず、private は書き込み権限付きで追加しないと読めないので難しい
- **将来案 (今は作らない)**: C2 = 集約用のリポジトリを 1 つ持ち、各リポジトリの課題を集めて生成する (他のリポジトリを読む権限と更新の仕組みが要る)。C3 = GitHub Issues と同期する (双方向の同期が複雑で、「ファイルが正本」と衝突しやすい)
- **いま決めておくと将来が楽になること**: `refs` に `プロジェクト名:ID` も書ける。CLI の既定の範囲はそのプロジェクトだけ。集約はすべて派生物にする。絶対パスをファイルに書かない (登録リストは `~` 表記)

### 1 件のファイル (案)

```markdown
---
schema: 1
id: i261103-01
title: li の中の表を、表のまま出す
state: 未
group: html2md
created: 2026-11-03
from: ai-chat-lite #1737
confirmed: false
refs: p261103-01
---

(本文。Markdown)

## やること
- [未] convertList で項目の中の表を convertTable に渡す
- [着手] check-markdown で実測する
- [済] 原因の特定
```

- **メタ情報は先頭の十数行**。状態を変えるのは 1 行の差分になる
- **「やること」は 1 行 1 件、行頭に状態**。いまの「やることも 3 段階」の決まりと同じ。件数は機械が数える
- **ID はいまの決まりのまま** (`i` ＋ `yymmdd-nn`、nn は 36 進数 2 桁)。**連番は CLI が付ける**。同じ日に 2 つのセッションが同じ番号を取らないよう、**番号の予約を排他で取る** (前の小節「ファイル名と置き場」)。取れなければ次の番号にする
- **課題の並びは保存しない**。表示のときに、グループ・状態・番号で並べる。並びの変更が差分に出ない
- **履歴は git が持つ**。`git log -- 課題のファイル` が、その課題の経緯になる。ファイルの中に更新履歴を書かない
- **形の版を持つ** (`schema: 1`)。あとで項目を足すときに、読み替えられる

### CLI (案。名前は決めること)

| 操作 | 例 | AI にとっての利点 |

| 立てる | `issue new --title "…" --group html2md --from "ai-chat-lite #1737"` | ID の採番・日付・形の誤りが起きない |
| 一覧・検索 | `issue list --state 未,着手 --group html2md --json` ／ `issue search "li の中の表"` | Grep で HTML の行を拾わずに、条件で一発 |

- 置き場は ai-agent-tools の `bin/` (他プロジェクトから名前で呼ぶ公開 CLI)。実装は TypeScript で、bun ・ node の両方で動かす (共通ルール「使用言語」「テストのルール」)

### 人向けの HTML

- **いまの `issues.html` と同じ見た目** (章ごとの色相、`details` の開閉、バッジ、目次、タイトルにプロジェクト名)。生成なので、共通ルール「課題の管理」の「既定の開閉は状態で決める」「件数と状態は中身から数え直す」が自動で守られる
- `<meta name="md-skip">` のまま。Markdown は作らない
- **`issues.html` は `items/` 直下から、`issues-archive.html` は `items/archived/` から生成する**。README がリンクするのは `issues.html` だけ、という決まりは変わらない
- 生成物は commit する (案 95-A)。README からのリンクが切れず、GitHub 上でも見える。同じ中身なら書かないので、差分は課題が変わったときだけ

### 差分と commit の見え方

- 課題を 1 件直すと、**そのファイル (数行) と、生成した HTML の該当部分**だけが変わる。いまのように、別の課題の編集が同じファイルで混ざらない
- 2 つのセッションが別の課題を触っても、ファイルが別なので競合しない。同じ課題を同時に触ったときだけ、通常の git の競合になる
- commit の単位が「課題 1 件」に揃う (ローカルルール第 6 章「1 つの作業を 1 commit」と相性が良い)

### 全体の横断

- 各プロジェクトが同じ形でファイルを持つので、**集めるのは、登録したプロジェクトの `items/` を読み取りで走査するだけ**。形が揃っているから簡単になる
- 出力は、集約用の SQLite (索引) と、横断の HTML (`未・着手の一覧`、プロジェクト別の件数)
- **プロジェクトの外を読む**ので、共通ルール「プロジェクトフォルダ外へのアクセス」に従い、**読み取りの対象のプロジェクトと目的を利用者が承認する**。登録のリストを 1 つ持ち、そこに載せたものだけを読む。書き込みはしない

## 5. 進め方とリスク

### フェーズ

承認のあと、小さく区切って進める。各フェーズの終わりに、全件テストを通し、commit と push をする (ローカルルール第 6 章)。

1. **フェーズ 0 (決める)**: 第 4 章の番号の採否をいただく。98-A なら、Backlog.md を試して、93-A と 93-B を最終決定する
2. **フェーズ 1 (形と検査)**: 1 件のファイルの形 (項目・状態・やること) を、仕様として `notes/50_spec/` に書く。読み込みと `issue check` を、テストを先に書いて実装する
3. **フェーズ 2 (操作)**: `new` ・ `list` ・ `show` ・ `set` ・ `todo` ・ `search` ・ `archive` ・ `unarchive` を実装する。番号の予約 (`_lock/`) もここで入れる。**「済」の拒否** (やることが残っている・報告元の確認が無い) もここで入れる
4. **フェーズ 3 (表示)**: `issue render` で、いまの `issues.html` と同じ見た目の HTML を生成する。**先に期待値を手で書いた golden** で比べる。`check-contrast` で実測する
5. **フェーズ 4 (移行)**: 96-A なら、未・着手の課題を新しい形へ移し、`issues.html` を生成物に切り替える。共通ルール「課題の管理」と「プロジェクトフォルダ構成」に、書き換えが要るかを確かめる (書き換えは案を示して指示を待つ)
6. **フェーズ 5 (横断)**: 97-A なら、登録リストの形と、外を読むことの承認の取り方を決め、集約を作る
7. **周知**: 公開 CLI なので `TOOLS-USAGE` に使い方を足す。共通ルールを変えたときだけ、周知の案を出す

### テストの方針

- **不具合を直すときと同じ順序**: 期待値を先に手で書き、落ちる (❌Red) のを見てから実装する (✅Green)
- **並行書き込みのテスト**: 2 つの採番が同時に走っても、同じ ID にならない
- **冪等**: `render` を 2 回流しても、2 回目は何も書かない (更新日時も変わらない)
- **文字コードと改行**: ファイルは UTF-8 ・ LF (HTML は BOM 付き)。`convert-encoding` で確かめる
- **bun ・ node の両方**で通す

### リスク

| リスク | 備え |
|---|---|
| 課題の形が、他プロジェクトの実情に合わない (file-manager 等) | フェーズ 1 の仕様を、先に file-manager 側の課題の数と形を見て決める。**そのプロジェクトの課題を読むには、対象と目的を示して確認を取る** (共通ルール「プロジェクトフォルダ外へのアクセス」)。この計画の作成では、他プロジェクトの課題は読んでいない |
| 新旧 2 か所に課題が分かれて、探しにくくなる (96-A) | `issue search` が旧 `issues.html` も走査できるようにするか、移行の終わりに旧側へ案内の 1 行を置く |
| 直接 Edit した誤りが、生成物に出る | `issue check` を commit の前の決まりにする (全件テストに組み込む) |
| 別の PC ・ クラウドで、同じ ID が別の件名で立つ (git では競合しない) | `issue check` が、同じ ID の複数ファイルを止める。commit の前と pull のあとに流す。並行書き込みのテストで確かめる |
| 索引 (SQLite) が古い | 索引は派生物。古ければ作り直す。ファイルの更新日時と比べて、CLI が自動で判断する |
| 外の形に寄せすぎて、既存の運用 (3 段階の状態・36 進数の ID) が崩れる | 93-B を採る場合は、合わない点を先に一覧にして、採否を決める |
