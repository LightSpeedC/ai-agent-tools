背景

プロセスの調査（テスト用サーバーが残っていないか、目的のプロセスの PID・起動時刻・実行ファイル・コマンドライン全体を確かめたい等）で、毎回 Get-CimInstance Win32_Process 等を手で打っている。決まった形式で一覧・絞り込みができる道具を作る。

実装方式（要判断）

プロセスの起動時刻・実行ファイルパス・コマンドライン全体を取るには、Windows では WMI（Win32_Process）が最も直接的で、これは PowerShell の領分。一方このプロジェクトの他の CLI ツール（html2md・text・convert-encoding・less・check-contrast 等）は全て TypeScript（bun/node）で統一されている。

案やり方長所短所
A（却下） TypeScript 本体。生データの取得だけ psh 経由で PowerShell（Get-CimInstance Win32_Process）に投げる 他ツールと同じ入口の形に揃えられる 2026-09-21、利用者の判断で却下。PowerShell を子プロセスとして毎回起動する分、重い・遅い
B（採用） TypeScript 本体。bun:ffi（Node は未対応。下記参照）で kernel32.dll を直接呼び、プロセスの列挙・情報取得を行う。less の _kbhit/_getch／SetConsoleOutputCP と同じ手法の延長 子プロセスを起動しない。外部パッケージへの依存も無い Windows API を直接扱う分、実装量が多い（下記「コマンドライン全体の取得」を参照）

2026-09-21、利用者の指示で B（FFI）を採用。

コマンドライン全体の取得は、他の項目より難度が高い

PID・実行ファイルパス・起動時刻は、比較的単純な documented API で取れる。

  • プロセスの列挙: CreateToolhelp32Snapshot + Process32FirstW/Process32NextW（PID・実行ファイル名（パスなし）・親 PID が取れる）
  • 実行ファイルのフルパス: OpenProcess でハンドルを取り、QueryFullProcessImageNameW
  • 起動時刻: 同じハンドルで GetProcessTimes（FILETIME で返る）

2026-09-21、検索して見つけた、より単純で壊れにくい方法を採用。ntdll.dll の NtQueryInformationProcess には ProcessCommandLineInformation（値 60）という専用の問い合わせ種別があり、これを使うとコマンドラインを1回の呼び出しで UNICODE_STRING（長さ2つ＋ポインタ）1つとして直接受け取れる。PEB → RTL_USER_PROCESS_PARAMETERS → CommandLine と自分でたどる必要が無い。

  1. OpenProcess（PROCESS_QUERY_LIMITED_INFORMATION だけでよい。PROCESS_VM_READ は不要）でハンドルを取る
  2. NtQueryInformationProcess（ProcessCommandLineInformation = 60）を呼ぶ。返る UNICODE_STRING をそのまま読めばコマンドライン文字列になる

利点（PEB を自分でたどる方式との比較）。

  • 読む構造体が UNICODE_STRING 1つだけになる（RTL_USER_PROCESS_PARAMETERS 内のオフセットを知る必要が無い）
  • ビット数（32/64bit）の違いを NTDLL 側が内部で吸収するため、自分でビット数分岐を書かなくてよい
  • 要る権限が低い（PROCESS_VM_READ 不要）ため、開けるプロセスが増える

制約。

  • 権限。それでも開けないプロセス（管理者権限のプロセス・保護されたプロセス等）はある。その行はコマンドラインを取れないものとして扱う（エラーで落とさない）
  • undocumented API。この情報種別自体は Microsoft の正式文書（winternl.h のリファレンス）には載っていないが、Windows 8.1 以降で広く使われており安定している
  • Windows 8.1 未満は非対応。このプロジェクトの実行環境では影響が無いと見ている

取れないプロセスがあっても、pid・実行ファイル・起動時刻だけは出す（コマンドライン欄だけ - にする）方針でよいか確認したい。

ツール名: psls。2026-09-21、pslist から変更。pslist は Debian/Linux の既存コマンド（man page あり）、および Windows の Sysinternals PsList（用途もほぼ同じ）と衝突することが検索で判明したため。psls は Linux の一般的なコマンド・このプロジェクト内のどちらとも衝突しないことを確認済み。

機能範囲

  • 既定でツリー表示にする（2026-09-21、利用者の指示。--tree のような別オプションではなく、通常の実行がそのままツリー表示になる）
  • 引数（キーワード）を1つ渡すと、それを含む行だけに絞り込む（大小文字は区別しない）。一致したプロセスの祖先を残し、先祖からツリーの形を保ったまま表示する（子だけ表示して親が消えるとツリーとして読めなくなるため）
  • キーワードに一致した行は太字にする（利用者の指示）。ツリーの中で該当プロセスがどれかを目立たせる
  • 1行の形式: <pid> <開始時刻> (<経過時間>) <exe> <ツリーの罫線＋インデント><コマンド行>。ツリーの罫線・インデントは exe とコマンド行の間に置く（利用者の指示）。pid・開始時刻・経過時間・exe の列は深さに関わらず桁が揃ったままになる

詳細仕様

データの取得

  • bun:ffi で kernel32.dll（CreateToolhelp32Snapshot／Process32FirstW／Process32NextW／OpenProcess／QueryFullProcessImageNameW／GetProcessTimes）と ntdll.dll（NtQueryInformationProcess、ProcessCommandLineInformation でコマンドライン全体を1回で取る）を直接呼ぶ
  • コマンドラインを取得できないプロセス（権限不足）はコマンドライン欄を - にする。pid・実行ファイル・起動時刻は出す

bun:ffi は Bun 専用。Node では動かせない

less は Bun で tty.ReadStream が使えないときの回避策として bun:ffi を使ったが、Node 側には tty.ReadStream という代替経路があった。このツールはプロセス情報の取得そのものを bun:ffi に頼るため、Node 側の代替が無い。Node の追加パッケージ（ffi-napi 等）を入れれば可能だが、外部パッケージへの依存を増やさない方針に反する。

この案では、このツールは bun が無い環境では動かせない（node で実行すると「bun が必要です」のようなメッセージで終了する形にする）。他ツールの「bun 優先・node 予備」という構成とは違う扱いになる点を認識しておきたい。

表示形式

項目形式例
開始時刻yyyy/mm/dd hh:mm:ss（JST）2026/09/21 09:15:32
経過時間d日 hh:mm:ss（1日未満は日を省く）(01:23:45) ／ (2日 03:00:10)

これらの書式は決め打ちの案。確認のうえで変更してよい。

キーワード絞り込み

  • 組み立てた1行の文字列（pid・時刻・exe・コマンド行すべて）に対して、大小文字を区別せず部分一致で絞り込む

ツリー表示

  • 親子関係は Process32FirstW/Process32NextW（PROCESSENTRY32W）が返す親 PID（th32ParentProcessID）でそのまま組み立てられる。追加の API 呼び出しは不要
  • 親 PID が既に終了している・存在しない場合（親が先に終わった等）は、そのプロセスをツリーの根として扱う
  • 循環参照（親子関係がループする）は理屈上起きないはずだが、念のため深さの上限を設けて無限ループを防ぐ
  • キーワード絞り込みと併用したときは、一致したプロセスの祖先を辿って残す（一致しないプロセスも、子孫に一致があれば表示する）

ツリーの罫線・太字（2026-09-21、利用者の指示）

  • 罫線・インデントは exe の列とコマンド行の間に置く。pid・開始時刻・経過時間・exe の列は、ツリーの深さに関わらず桁が揃う（罫線が伸びるのはコマンド行の手前だけ）
  • 罫線は一般的なツリー表示の記号を使う: 兄弟がまだ続く祖先の縦棒は │ 、兄弟が最後まで終わった祖先は空白 、自分が最後の子でない場合は ├─、最後の子なら └─（根のプロセスは罫線無し）
  • キーワードに一致した行を太字（\x1b[1m）にする。祖先として表示しているだけの行（一致していない）は通常表示のまま

表示イメージ（案）。

1000  2026/09/21 09:00:00 (10:00:00)  explorer.exe  explorer.exe
2000  2026/09/21 09:10:00 (09:50:00)  cmd.exe       ├─ cmd.exe
3000  2026/09/21 09:15:00 (09:45:00)  node.exe      │ └─ node script.js

（node で絞り込んだ場合、太字になるのは3行目のみ。1・2行目は祖先として残る）

テスト方針

FFI で直接プロセスを列挙するため、他ツールと同じ「対象を直接 import しない、spawnSync で本物の psls を起動して確かめる」黒箱テストになる。Get-CimInstance のような差し替え可能な入力は無く、実行するたびに変わる本物のプロセス一覧を相手にする。

  • 自動テストにする: --help、知らないオプション、自分自身（bun／node）が今まさに実行中であることを利用して、キーワード絞り込み（例: bun）で該当行が1件以上出ること、絞り込みが大小文字を区別しないこと、出力の各行が期待する形式（pid 開始時刻 (経過時間) exe コマンド行）に一致すること（正規表現で検証）、ツリー表示で親子のインデントの深さが親 PID の関係と一致すること
  • 手動確認にとどめる: 実際のプロセス一覧が正しく取れているか（自分自身のプロセス等で目視確認）、権限で取れないプロセスの扱い

置き場は他ツールと同じ tools/40_test/run-psls-tests.ts。

機能拡張（未実装・設計）

2026-09-21、利用者から3件の拡張案。まだ実装していない。オプション名の検討を含めてここに設計をまとめる。

1. exe 欄は既定でパス名を省略する

  • 既定はファイル名だけ（a.exe）にする。フルパスを見たいときは新しいオプションを渡す
  • オプション名（案）: -f / --full-path。渡すとフルパスで表示する（今の既定の動き）
  • 引数の扱い: - または -- で始まるものはオプション、それ以外の1つはキーワードとして扱う（今までどおり）。parseArgs（src/lib/args.ts）はこの形をそのまま扱えるので、オプション定義を1つ足すだけでよい

2. 各欄の桁を全行で揃え、コマンド行は端末幅に収まるよう切り詰める

  • pid・開始時刻・経過時間・exe（3の *N 付きも含む）の各欄は、表示する行の中での最大幅に揃えてパディングする。今は pid だけ固定6桁で他は揃っていない
  • コマンド行は、端末の桁数（process.stdout.columns）からそれまでの欄・罫線の幅を引いた残りに収まるよう切り詰める（超えた分は末尾を省略記号（... 等）に置き換える）。端末でない出力先（リダイレクト等）のときは columns が取れないため、既定の幅（160）を使う
  • 切り詰めない（全部表示する）オプション（案）: --no-trim。渡すと端末幅を無視してコマンドライン全体を出す

3. 同名で別パスの exe は番号で区別する

  • exe 欄をファイル名だけで表示する（既定）とき、同じファイル名で違うフルパスのプロセスが2つ以上あれば、それぞれに *1・*2…を振って区別する（例: a.exe *1／a.exe *2）
  • 番号は、表示対象（キーワード絞り込み後）に実際に出てくる順（先に見つかった方から）で振る。絞り込みで消えたパスの分の番号は詰める（欠番を作らない）
  • 出力の最後に、ファイル名ごとの対応表を1行にまとめて出す: a.exe: *1: <パス1>, *2: <パス2>（複数のファイル名で衝突があれば、ファイル名ごとに1行）
  • -f/--full-path のときは元々フルパスが見えているので、この番号付け・対応表は出さない

実装順序への影響

2 の「桁を全行で揃える」は、3 の *N 付き exe 欄の幅にも影響する（*N を振った後の文字列の最大幅で揃える必要がある）ため、3 → 2 の順で組み立てるのが自然。1（フルパス省略オプション）は独立していて、どちらより先でも後でもよい。

この設計で進めてよいか確認をお願いします。

物理メモリ使用量の表示

済2026-09-21、利用者の指示で実装。exe 欄の前に物理メモリ使用量の列を追加した。実機（管理者モード・一般ユーザーの両方）で取得できることを確認済み。

  • 取得方法。kernel32.dll の K32GetProcessMemoryInfo（PROCESS_MEMORY_COUNTERS の WorkingSetSize）で、そのプロセスが実際に使っている物理メモリ（ワーキングセット）を取る。タスクマネージャーの「メモリ」列と同じ考え方の値
  • 表示形式。1024 未満は B、10242 未満は K、10243 未満は M、それ以上は G。値は小数第1位まで（例: 128.0M／1.3G）。pid・開始時刻・経過時間・exe と同様、表示する行の中での最大幅に揃える
  • 列の並び順: <pid> <開始時刻> (<経過時間>) <物理メモリ> <exe> <ツリーの罫線＋インデント><コマンド行>（利用者の指示で exe の前に置く）
  • 取れない場合の表示。物理メモリ欄・exe 欄は -、コマンド行欄は (-)（利用者の指示。経過時間欄の (-) と揃えた）

退行: 権限を1つ足しただけで既存の取得まで巻き添えで壊れた

原因。GetProcessMemoryInfo は PROCESS_VM_READ を要るため、既存の OpenProcess（exe・起動時刻・コマンドライン取得用、PROCESS_QUERY_LIMITED_INFORMATION）にこの権限を足して1つのハンドルで済まそうとした。OpenProcess は要求した権限を すべて 満たせないとハンドル自体を返さないため、PROCESS_VM_READ が通らないプロセスでは、管理者権限でも exe・起動時刻・コマンドラインまで一緒に取れなくなった（利用者が実機で発見）。

修正。メモリ取得専用に別ハンドルを開く形に分離した。メモリ側だけが取れなくても、他の項目の取得には影響しない。

管理者モードでの取得範囲を広げる: SeDebugPrivilege

管理者として実行しても、既定の OpenProcess は DACL ベースの通常のアクセスチェックしか行わないため、SYSTEM 権限のプロセス等は PROCESS_VM_READ を拒否される。自プロセスのトークンで SeDebugPrivilege を有効化すると、DACL に関わらずほぼ任意のプロセスを開けるようになる（タスクマネージャーを管理者で実行したときに全プロセスのメモリが見える仕組みと同じ）。

  • advapi32.dll の OpenProcessToken → LookupPrivilegeValueW（"SeDebugPrivilege"）→ AdjustTokenPrivileges を、起動時に1回だけ呼ぶ
  • 一般ユーザーには副作用が無い。この特権は既定で管理者グループのトークンにしか割り当てられておらず、一般ユーザーでは OpenProcessToken／AdjustTokenPrivileges が静かに失敗するだけ（try/catch で囲み、失敗しても他の取得には影響しない）。有効化は自プロセスのトークンだけに、そのプロセスが終了するまで効く一時的なもの
  • 例外は Protected Process（Light）（Secure System・Registry 等）。カーネルレベルの保護のため、SeDebugPrivilege があっても開けない

実機（管理者モード）で、この特権を有効化した状態でメモリが取得できることを確認済み。
