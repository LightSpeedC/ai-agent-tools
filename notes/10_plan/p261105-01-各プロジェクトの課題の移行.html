各プロジェクトの課題の移行 計画 (ai-agent-tools)

課題を 1 件 1 ファイルで持つ issue ツールへ、ほかのプロジェクトがどう移るか。このPC のプロジェクトと、別の PC ・ クラウドのプロジェクトの両方を扱う案。

📅 作成: 2026-11-05 / 更新: 2026-11-06

対象 ・ 入力 ・ 出力: 対象は、課題を notes/40_issues/issues.html で持つ、各プロジェクト (このPC の 28 件と、別の PC ・ クラウドのもの)。入力は、各プロジェクトの旧 issues.html (未・着手の課題)。出力は、各プロジェクトの notes/40_issues/items/ (1 件 1 ファイルの Markdown) と、issues-legacy.html。この計画は案と決めることの提示まで。承認をいただくまで実装しない。 ツールの設計は 課題管理ツール 計画 (このプロジェクトでは、フェーズ 4 まで済)。

結論 (推奨): 各プロジェクトのセッションが、利用者の「移行して」の指示で、自分の課題を移す (他プロジェクトのファイルは直さない、という共通ルールのまま)。移すのは未・着手だけ (96-A) で、旧 HTML は書き換えずに issues-legacy.html へ改名する (127-A)。写し間違いを避けるため、未・着手を機械で移す issue migrate を足す (このプロジェクトの 3 件は手で書き写したが、28 件の書き方のばらつきを手作業では抱えきれない)。未・着手が 0 件のプロジェクトは急がず、次に課題を立てるとき (issue new が案内して止まる) に移す。別の PC は、移す PC を 1 台に決め、事前に全 PC で push しておく。順序は、ツールの公開 → 共通ルールの書き換え (132) → 周知 → 試しの 2 件 → 残り。

現状と制約

現状 (2026-11-05 の調査と、このプロジェクトでの実施)

  • このPC の対象は 28 件。Claude Code の設定に載るプロジェクト 145 件のうち、notes/40_issues を持つもの。課題は約 740 件で、file-manager が 392 件、ai-chat-lite が 98 件、ai-agent-tools が 97 件。ほかは 1〜20 件 (課題管理ツール 計画の調査の節)
  • 書き方がそろっていない: 課題の番号の要素が span.no (24 件) ・ code.no (1 件) ・ span.id (1 件) ・ 番号なし (1 件)。状態のバッジは、番号の後が 17 件、前が 9 件。ai-chat-lite だけバッジの class が b-done ・ b-todo。md-skip は 3 件
  • 何件が未・着手かは、まだ数えていない。このプロジェクトは 97 件のうち 3 件 (すべて着手) だった。「済が大半」という見込みで、未・着手を移すだけにすれば量は小さいが、実測するまでは見込み
  • このプロジェクトでは移行済み (フェーズ 4): 3 件を items/doing/ へ書き写し、旧 issues.html を issues-legacy.html へ改名し、README ・ 計画のリンク ・ check-public-allow.txt を直した。これが、ほかのプロジェクトの手本になる

制約

  • 他プロジェクトのファイルは直さない (共通ルール「プロジェクトフォルダ外へのアクセス」)。ai-agent-tools のセッションから、各プロジェクトへ書き込めない。移すのは、各プロジェクトのセッション。読み取りは、プロジェクトごとの承認で足りる
  • commit と push は、利用者の指示を待つ (共通ルール「修正は1点ずつ、確認を重視」)。各プロジェクトで、移行の指示と、commit の指示が要る
  • 共通ルール「課題の管理」と README のルールが、まだ旧形式のまま (issues.html に集約する、README は issues.html へリンクする)。書き換え (132) は、ツールの公開の後に、案を示して指示を待つと決めてある。ルールが旧形式のまま移すと、各プロジェクトの AI が旧形式へ戻してしまう
  • 課題を持たない ・ 動いていないプロジェクトを、急いで移さない。移しても、集める相手が増えるだけで、得るものが無い
  • 画像 ・ 図で壊れるものは、いまの調査では無い (どの課題ページにも <img> も本文の <svg> も無い)

1 つのプロジェクトの移し方

手順 (プロジェクトのセッションが、利用者の指示で行う)

  1. 前提を確かめる: issue が呼べる (issue --help)。作業ツリーがきれい (git status) で、リモートと同じ (pull 済み)。別の PC に push していない課題の編集が無いことを、利用者に確かめる (第 3 章)
  2. 数える: issue migrate --dry-run が、旧 issues.html から、未・着手の課題の数と、読めなかったものを出す。書き込まない
  3. 移す: issue migrate --apply が、未・着手の課題を items/todo/ ・ items/doing/ へ書く (番号と作成日は旧のまま)。読めなかったものは書かず、一覧で出す。人 (AI) が、旧の記録を見て手で書き写す (このプロジェクトで行った方法)
  4. 数が合うか確かめる: 旧の未・着手の数 = 新の todo/ + doing/ の数。issue check が問題なし。.gitignore に _* がある (無ければ足す。issue check が警告する)
  5. 旧 HTML を残す: issues.html を、書き換えずに issues-legacy.html へ改名する (git mv。127-A)。旧 issues-archive.html があれば、戻るリンクの名前だけを直す
  6. リンクを直す: text find --path . --recurse で issues.html を探し、リンク先の名前だけを直す (README ・ 計画 ・ ローカルルール ・ check-public-allow.txt 等。本文は触らない。計画の本文は書き換えない)。README は、notes/40_issues/items/ と旧課題へ案内する
  7. 検査して、利用者の指示で commit と push: html2md ・ check-markdown ・ そのプロジェクトのテスト。移行は 1 commit にする (戻すときは 1 つを戻せばよい)

issue migrate の案 (ai-agent-tools の側で作る)

項目案
入力旧 issues.html (既定は notes/40_issues/issues.html)。details の summary に、状態のバッジ ・ 番号 ・ 題があるものを 1 件と読む。グループは、直前の章 (section の h1) の見出し
書き方のばらつき調査で見つかった形 (番号が span.no ・ code.no ・ span.id。バッジが番号の前 ・ 後。class が b-ok ・ b-warn ・ b-none ・ b-done ・ b-todo と、バッジの文字) を、すべて読む。読めない形は、推測せず「読めなかった」に出す
出力未 → todo/、着手 → doing/ (済は移さない。96-A)。created は番号の日付。本文は、html2md の変換部品を再利用できるかを、先に確かめる (できなければ、課題管理の render の逆向きの小さな変換を書く)。やること行は - [未|着手|済] 文
番号が無い課題番号が無い旧形式 (調査では 1 件のプロジェクト) は、issue new と同じ規則で番号を振り、対応表を出す
安全既定は --dry-run (書かない)。--apply は、items/ に同じ番号が既にあれば、そのプロジェクトで止まる (重複を作らない)。旧 issues.html は、書き換えも削除もしない (改名は人が行う)。絶対パスを出さない
試験期待値を先に手で書く。調査で見つかった各形 (番号の要素 3 種 × バッジの位置 2 種 ほか) と、このプロジェクトの旧 issues.html (git の履歴にある移行前の版) を、材料にする。このプロジェクトで手で書き写した 3 件と、機械が出したものを突き合わせる

旧形式のプロジェクトを、うっかり使わない備え

  • issue new が、旧 issues.html だけのプロジェクトで立てようとしたら、案内して止まる (終了コード 5。issue migrate を促す)。issue init も同じ。未・着手が 0 件のプロジェクトは、次に課題を立てるときに、ここで移す
  • issue check が、items/ と旧 issues.html が両方あるとき警告する (legacy)。旧形式のルールで動く AI が、移行後に issues.html を作り直した場合を、見つける

別の PC ・ クラウド

何が違うか

  • 同じプロジェクトを、複数の PC (と、クラウド) が git で共有している。移行は 1 つのリポジトリの 1 回の commit で、ほかの PC は pull で受ける。PC ごとに移さない (同じ課題が 2 度立ち、git は競合を出さずに、重複した番号が残る)
  • このPC には無いプロジェクトがある。このPC の調査 (28 件) には載らない。名簿は、利用者に伺うか、その PC のセッションに issue migrate --dry-run で数えてもらう (第 4 章 141-A)
  • ツールが、その PC に入っているとは限らない。ai-agent-tools を git pull し、bin/ が PATH にあり、node か bun がある PC でだけ動く。クラウドは cloud-session-start が、clone と PATH を行う
  • 共通ルールも、その PC で最新とは限らない。ルールが旧形式のままの PC の AI は、移行後に旧 issues.html を書き始める
  • project-id.txt は、移行のときに 1 度だけ作り、commit するので、どの PC でも同じ値になる (122-A ・ 125-A)。PC ごとに作らない。_issues.html は、各 PC が自分で生成する

別の PC があるプロジェクトの手順 (第 2 章の前後に足す)

  1. 移行日を決める。その日まで、全 PC で、課題の編集を commit して push しておく (旧 issues.html への未 push の編集が、あとの競合の元になる)
  2. 移す PC を 1 台に決める (そのプロジェクトのセッションが開いている PC)。第 2 章を行い、push する
  3. ほかの PC は、課題を触る前に pull する。そのとき、ツールと共通ルールも最新にする (ai-agent-tools ・ ai-agent-rules を pull)
  4. pull のあとに issue check を流す。重複と旧 issues.html の再出現を見つける

クラウド

  • クラウドの環境は、毎回作り直される。移行後のリポジトリを clone するだけで、新しい形になる。cloud-session-start が ai-agent-tools を最新にするので、issue も呼べる (sh の入口は bun を優先し、無ければ node。確かめる)
  • クラウドで課題を立てると、PC の番号と重ならない保証は 同じ PC の中だけ (_lock/)。別の場所での重複は、issue check が後から止める (課題管理の 計画のリスクと同じ)

決めること

共通ルール「複数の解決案がある場合の対応」に従い、推奨を A にする。番号は、前の計画 (p261103-01) の 136 の続き (137 から) の通し番号。

番号決めること案推す理由
137-A 移す作業を、だれが行うか (恒久) A: 各プロジェクトのセッションが、利用者の「移行して」の指示で行う 他プロジェクトのファイルは直さない、という共通ルールのまま動く。そのプロジェクトのテストと検査で確かめられる。ただし、利用者が 1 つずつ指示する手間がかかる
137-B B: ai-agent-tools のセッションが、プロジェクトごとの許可を得て、まとめて書き込む 指示が少なく、速い。ただし、書き込みの許可をプロジェクトごとに取る必要があり、そのプロジェクトのテストと commit の指示は結局そちらで要る。別の PC のプロジェクトには届かない
138-A 移す道具 (恒久) A: issue migrate を足し、機械が移す。読めない形は手で書き写す 28 件のばらつきを、1 回の実装で抱えられる。写し間違いが起きにくく、数の確認も機械で行える
138-B B: 道具を作らず、各プロジェクトの AI が手で書き写す (このプロジェクトでやった方法) 道具の実装が要らない。ただし、課題が多いプロジェクト (file-manager 等) で、写し間違いと手間が大きい
139-A 移す時期 (恒久) A: 未・着手があるプロジェクトは、周知のあと順に移す。0 件のプロジェクトは、次に課題を立てるとき (issue new が案内して止まる) 得るものがあるプロジェクトから移せる。動いていないプロジェクトに、手間をかけない
139-B B: すべてのプロジェクトを、期間を決めていっせいに移す 新旧が混ざる期間が短い。ただし、動いていないプロジェクトも指示が要る。別の PC の都合を合わせにくい
139-C C: そのプロジェクトで課題を触るときだけ移す 手間が最小。ただし、未・着手があるのに旧形式のままのプロジェクトが、いつまでも残る
140-A 別の PC があるプロジェクト (恒久) A: 移す PC を 1 台に決め、事前に全 PC で push する。移したあと、ほかの PC は pull し、issue check の legacy と重複の警告で、事故を見つける 1 回の commit で済み、競合が起きない。事故が起きても、道具が見つけられる
140-B B: 警告は足さず、移行期間は別の PC で課題を書かないことを周知するだけにする 道具の変更が要らない。ただし、周知を読まなかった PC の編集に、気づけない
141-A 進み具合の記録 (暫定) A: 状態は、各リポジトリの中身で判定する (items/project-id.txt と issues-legacy.html の有無)。ai-agent-tools では、名簿 (プロジェクト ・ 所在 ・ 未・着手の数 ・ 移行の済) を、報告のたびにこの計画の表へ足す 道具の追加が要らず、すぐ始められる。暫定: 別の PC の分は、報告が来るまで分からない
141-B B: 課題管理の「横断」(フェーズ 5) ができてから、各プロジェクトを読んで判定する 名簿を手で更新しない (恒久)。ただし、横断は、移行の後ろの作業で、移行の管理には間に合わない。別の PC の分は届かない
142-A 共通ルールとの前後 (恒久) A: ツールの公開 → 共通ルールの書き換え (132) → 周知 → 試し → 残り、の順にする。ルールの書き換えの前には、どのプロジェクトも移さない ルールが旧形式のままだと、移したあとの AI が旧形式へ戻す。周知も、新しい形のルールを読ませる形にできる
142-B B: 試しの 1〜2 件を、ルールの書き換えの前に行う 実際のプロジェクトで、ルールの文言の穴を先に見つけられる。ただし、試しのプロジェクトでは、ルールと実態が一時的に食い違う

利用者に伺いたいこと (決めることとは別): (1) このPC 以外の PC は何台で、どのプロジェクトがあるか (名簿は、このPC の調査にしか無い)。(2) 試しに移すプロジェクトの候補。推奨は、書き方が違う 2 件 (たとえば、バッジが番号の前で class が b-done の ai-chat-lite と、md-skip で番号が span.id の claude-code-proxy。ただし、どちらも課題を読む承認が要る)。(3) 動いていないプロジェクトの扱い (139-A なら、次に使うときに移す)。

決定 (2026-11-06)

  • 137〜142 は、すべて A を採る
  • (1) 別の PC は 2〜3 台。特に気にしなくてよい (名簿は作らず、140-A の手順と issue check の警告で足りる)
  • (2) 試しに移す 2 件 (ai-chat-lite ・ claude-code-proxy) の課題を読むことを許可
  • (3) 動いていないプロジェクトは、次に動かすときに移す (139-A のとおり)
  • 165-A (2026-11-07): --apply は、旧 HTML の「やること」のうち、バッジ付きの列挙だけを - [状態] 文 の行にする。番号付きの列挙 ・ 表は、本文の Markdown のまま残す (状態が書かれていないものを推測しない)

進め方とリスク

フェーズ

承認のあと、小さく区切って進める。このプロジェクトの作業は、各フェーズの終わりに、全件テストを通し、commit と push をする (ローカルルール第 6 章)。各プロジェクトでの作業は、そのプロジェクトのセッションが行う。

  1. フェーズ 0 (決める): 第 4 章の番号の採否と、利用者に伺いたいことの回答をいただく
  2. フェーズ 1 (道具): issue migrate ・ issue new の案内 ・ issue check の legacy 警告を、テストを先に書いて (❌Red を見てから) 実装する (✅Green)。材料は、調査で見つかった各形と、このプロジェクトの旧 issues.html。bun ・ node の両方で通す
  3. フェーズ 2 (公開): TOOLS-USAGE に issue の使い方と移行の手順 (第 2 章)を書く。これは公開資料なので、書く前に利用者の指示を待つ
  4. フェーズ 3 (共通ルール): 142-A なら、共通ルール「課題の管理」と README のルールの書き換え (132) を、差分で示して指示を待つ。ローカルルール第 1 章 ・ 第 2 章の issues.html の記述も同じ
  5. フェーズ 4 (周知): public ルームに、見出し名と変わった点だけを短く出す (案を示して確認を得る)。移行の手順は TOOLS-USAGE の見出し名で指す
  6. フェーズ 5 (試し): 2 件のプロジェクトで、利用者の指示で移す。数が合うか ・ 書き方の違いで読み落としが無いか ・ 手順の穴を、issue migrate と手順の資料へ返す
  7. フェーズ 6 (残り): 139-A の順に、未・着手があるプロジェクトから移す。別の PC のプロジェクトは、第 3 章の手順で行う。名簿 (141-A) を更新する

テストと確かめ

  • 期待値を先に手で書く。issue migrate の出力から、期待値を作らない (共通ルール「テストを先に書く」)
  • 数の突き合わせ: 旧の未・着手の数と、新の todo/ + doing/ の数が一致する。1 件ずつ、番号 ・ 題 ・ グループ ・ やること行の状態も比べる
  • 手で書き写した 3 件との突き合わせ: このプロジェクトの旧 issues.html (移行前の版) を、issue migrate に通し、手で書いたものと比べる。機械が出したものに、手で書いたものが無い点 (経緯の要約) は、差として記録する
  • 移したあとの確かめ: issue check ・ issue render ・ そのプロジェクトのテスト ・ html2md ・ check-markdown ・ check-html-rules (あれば)

リスク

リスク備え
