JSONL 二分探索ツール 計画 (ai-agent-tools)

セッションの JSONL が数百 MB になっても、時刻や位置で必要な範囲だけを速く読めるようにする。バイト位置へ飛び、改行で行頭に合わせる二分探索の CLI を、TypeScript (node ・ bun) と Rust で作る案。

📅 作成: 2026-11-03 / 更新: 2026-11-03

対象 ・ 入力 ・ 出力: 対象は ai-agent-tools (共有ツールの置き場)。入力は、Claude Code のセッションログ (JSONL。~/.claude/projects/<プロジェクト>/<セッション>.jsonl と、各プロジェクトの etc/history/jsonl/ の写し)。出力は、時刻・位置で範囲を絞って読む共有 CLI の案 (TypeScript 版と Rust 版)。この計画は案と決めることの提示まで。承認をいただくまで実装しない。

結論 (推奨): 二分探索が効くのは「時刻や位置で範囲を絞る」問い (この時間帯の発言・最後の N 件・この位置の 1 行)。語の検索は並びが無く二分探索できないので、範囲を絞ってから走査する。時刻の並びは厳密には単調でない (実測で最大 560 秒の逆戻り) ので、余裕 (マージン) を持たせた二分探索で入口を決め、そこから前方へ走査して正確に絞る。まず TypeScript で作り、実測してから Rust で同じ出力のものを作る (突き合わせテストの相手がある状態で移す)。

目的と実測

やりたいこと

  • セッションの JSONL が長くなる (file-manager 等) と、ふつうの検索は遅い。バイト位置で読み、改行で行頭に合わせ、二分探索で見つける
  • 実装は node ・ bun の TypeScript と、Rust の両方
  • AI エージェントが「あの時刻の前後」「最後の数十件」を、ログ全体を読まずに取れる

  • 600 MB に比例すれば、Select-String は十数秒、readline ＋ JSON.parse は数秒 (見込み。この 2 つは 600 MB では未測定)
  • ただし、全体を走査する速さは、JSON を読まなければ 600 MB でも 1 秒未満。二分探索が効くのは、走査を避けられる問いだ

見立て: 「遅い」の中身は、ツールの選び方 (全行を文字列にして比べる・全行を JSON にする) が大きい。それでも、時間帯や位置で絞れる問いは二分探索ならミリ秒 (600 MB で約 30 回の読み) に収まり、読む量も数百 KB で済む。AI の文脈に入れるべき量を小さくできる点が、速さ以上の利点になる。

何が二分探索できるか

改行で位置を合わせる仕組み

  • 任意のバイト位置 p から次の改行 (0x0A) まで読み進めると、行頭に合う。UTF-8 では 0x0A が複数バイト文字の途中に現れない (後続バイトは 0x80〜0xBF) ので、日本語・絵文字の途中に飛んでも壊れない
  • JSONL の 1 行の中に生の改行は無い (文字列中の改行は \n と書かれる)。この前提は、上の 2 本で行数の数え方が一致していることを確かめた範囲では成り立つ
  • 行が長い (最大 1 MB 超) ので、位置合わせの読みは 64 KB から倍々に増やす
  • 書き込み中の (生きている) セッションは、最後の行が途中のことがある。最後の改行で終わる位置までを対象にする

問いの種類ごとの方法

問い方法かかる読みの量
この時刻の前後の行が欲しい二分探索 (時刻)。マージンを引いた時刻で入口を決め、前方へ走査して正確に絞る約 30 回の位置合わせ ＋ 範囲の分
この時間帯の発言を全部二分探索で入口を決め、終わりの時刻まで走査範囲の分
最後の N 件末尾から逆向きに塊を読み、改行を数えるN 行ぶん
この位置 (バイト) の 1 行位置合わせの 1 回1 行ぶん
この語を含む行 (時間帯の指定なし)二分探索できない (並びが無い)。全走査 (メモリは一定)全体 (600 MB で 1 秒未満の見込み)
この語を含む行 (時間帯の指定あり)二分探索で範囲を絞ってから走査範囲の分
行番号 N の行二分探索できない (行の長さがばらばら)。位置か時刻で指す—

時刻の並びは厳密には単調でない

  • 時刻のある行でも、前の行より古いことがある (2 本で 1,793 回と 15,706 回。最大は 379 秒と 560 秒)。中央値は 0 秒で、ほぼ整列していて、時々少し戻る形
  • 時刻の無い行が 4 割前後ある (custom-title ・ agent-name ・ mode ・ permission-mode ・ bridge-session ・ api-request-blob ・ last-prompt ・ cost-state ・ tools-used ・ atis-latch)。二分探索の途中で止まった行に時刻が無ければ、時刻のある次の行まで読み進める
  • 厳密な二分探索は、逆戻りで入口を取りこぼす。マージン M を引いた時刻 (T − M) 以上の最初の行を二分探索で見つけ、そこから前方へ走査して、T 以上の行を正確に拾う。M が逆戻りの最大より大きければ、取りこぼさない
  • M の既定は、実測の最大 (560 秒) の約 3 倍の 30 分 (決めること 101)。実測が 2 本だけなので、--margin で変えられるようにする
  • 時刻の範囲が長い (約 880 時間) のは、再開 (resume) したセッションがつながっているためと見込まれる (確かめていない)。範囲は 1 本の中で、おおむね前から後ろへ進む

ツールの案

コマンド (案。名前は決めること 104)

操作例中身
概要jsonl-seek stat <file>大きさ・最初と最後の時刻・おおよその行数 (行数は標本から推定。数え切るなら全走査)
時刻で入るjsonl-seek at <file> "11/02 06:47"その時刻以上の最初の行。位置 (バイト) を付けて返す
範囲jsonl-seek range <file> --from "11/02 06:00" --to "11/02 07:00" [--type user] [--grep 語]時間帯の行を、種類や語で絞って返す
末尾jsonl-seek tail <file> -n 30最後の N 行 (最後の途中の行は除く)
位置で 1 行jsonl-seek show <file> --offset 123456その位置を含む 1 行の全文
語で探すjsonl-seek find <file> 語 [--from … --to …]範囲を絞って走査。結果に位置を付ける
  • 時刻の書き方は JST (月/日 時:分 または yyyy/mm/dd hh:mm:ss)。ログ内の時刻は UTC なので、ツールが変換する (共通ルール「会話中で日時を報告するときはJST」)
  • 結果にバイト位置を付ける。あとから show --offset で 1 回の読みで再取得できる (位置指定の読みを、使い回せる形にする)
  • 既定の出力は 1 行 1 件の短い形 (位置 ・ 時刻 ・ 種類 ・ 先頭 300 文字ほど)。最大 1 MB 超の行が AI の文脈を使い切らないように、全文は show で取る (決めること 102)。--json で機械向けの出力も出す
  • パスは ~ に伏せて表示する (共通ルール「フルパスを出さない」)。行の中身にユーザプロファイル配下のパスがあれば、既定で ~ に置き換える。--raw で生のまま出す
  • プロジェクト名で選べるようにする (--project file-manager)。~/.claude/projects 配下のセッションから、最後の時刻 (末尾の標本) で選ぶ。確認なしで参照してよい範囲 (共通ルール「プロジェクトフォルダ外へのアクセス」) の中で動く
  • 読み取り専用。ログを書き換えない。開いたら閉じる。生きているセッションの追記と競合しない (開いた時点の大きさを使う)
  • Claude Code の JSONL の形 (type ・ message) への依存は、表示用の抽出に限る。抽出に失敗した行は、生の行を返す (形は版で変わりうる)

実装の分担

実装役目要点
TypeScript (bun ・ node)仕様を固める本命の最初の実装。ほかの共有ツールと同じ入口 (bin/) に置くfs.readSync の位置指定と Buffer.indexOf(0x0A)。同期 API を使うので、固まらないよう上限を付ける (共通ルール「同期 API は、そのプロセスの非同期処理を止める」)。bun ・ node の両方で通す
Rust同じ出力を出す別の実装。TypeScript 版の結果と突き合わせるFile の seek と、memchr での改行探し。cargo は 1.99.1 が入っている (実測)。フォルダ名は C# の 〜Cs に倣い 〜Rs を提案 (決めること 100)
  • Rust にする価値は、実測してから決める。TypeScript の生の走査が 600 MB で 1 秒未満なので、速さの差は小さいかもしれない (Rust の速度は未測定)。差が小さくても、単体で配れる exe にできる (bun ・ node が無い環境) ことと、Rust の共有ツールの足がかりになることが利点
  • 2 つの実装は同じ試験の材料で通す。出力が一致することを、総当たりで突き合わせる (第 5 章)

決めること

共通ルール「複数の解決案がある場合の対応」に従い、推奨を A にする。番号は、前の計画 (p261103-01) の 93〜99 の続き (100 から) の通し番号。

番号決めること案推す理由
100-A 実装の順序 (恒久) A: TypeScript を先に作り、実測してから、同じ出力の Rust を作る TypeScript 版が突き合わせの相手になる (共通ルール「移植で落ちるのは、言語が肩代わりしていた比較」)。Rust の価値を実測で確かめてから作れる
100-B B: TypeScript と Rust を同時に作る 早く揃う。ただし、仕様の穴が両方に入り、直しが 2 倍になる
100-C C: Rust だけを作る exe 1 本で済む。ただし、ほかの共有ツールと入口・試験の仕組みが違い、bun ・ node での確認ができない
101-A 時刻の逆戻りのマージンの既定 A: 30 分 (--margin で変更可) 実測の最大 (560 秒) の約 3 倍。実測が 2 本だけなので余裕を取る。余裕分の走査は 30 分ぶんで、読みは増えても小さい
101-B B: 10 分 読みが少ない。ただし、実測の最大の約 1.1 倍しかなく、別のログで取りこぼす恐れがある

102-B B: 生の行をそのまま出す 加工が無い。ただし、1 行で 1 MB 近く出る行があり、使いにくい
103-A 対象の指し方 A: パスを渡す形と、--project でプロジェクト名から選ぶ形の両方 「file-manager の最後の 1 時間」のような問いが 1 コマンドで済む。参照は確認なしの範囲 (~/.claude) に限る
103-B B: パスだけ 作る量が最小。ただし、セッションのパスを毎回探す手間が残る
104 CLI の名前 案: jsonl-seek。ほかの共有ツールや OS のコマンドとぶつからないかを、実装の前に Get-Command で確かめる 名前の衝突は、採否が決まってから確かめる
105-A 語の検索 A: 範囲を絞ってから走査 (全走査も許す)。索引は作らない 全走査が 600 MB で 1 秒未満 (生の走査) なので、索引は過剰。作り直しや古さの管理が増えない
105-B B: 索引 (SQLite の全文検索) も作る 繰り返しの語検索は速い。ただし、ログが追記されるたびに作り直しが要り、機密を含む内容を別の DB に複製する

進め方とリスク

フェーズ

承認のあと、小さく区切って進める。各フェーズの終わりに、全件テストを通し、commit と push をする (ローカルルール第 6 章)。

  1. フェーズ 0 (決める): 第 4 章の番号の採否をいただく
  2. フェーズ 1 (仕様と試験の材料): 振る舞いの仕様を notes/50_spec/ に書く。試験の材料 (合成した JSONL) を tests/ に置く。逆戻りのある並び ・ 時刻の無い行 ・ 1 MB 超の行 ・ 日本語と 4 バイトの絵文字 ・ 最後が途中の行 ・ 空のファイル ・ 1 行だけのファイルを含める
  3. フェーズ 2 (TypeScript 版): stat ・ at ・ range ・ tail ・ show ・ find を、テストを先に書いて (❌Red を見てから) 実装する (✅Green)。bun ・ node の両方で通す
  4. フェーズ 3 (実測): 600 MB のログで、二分探索 ・ 全走査 ・ Select-String ・ readline ＋ JSON.parse を比べる。計測の道具は tools/ に置く。Rust 版を作る価値をここで決める
  5. フェーズ 4 (Rust 版): 同じ試験の材料で通す。TypeScript 版と出力を突き合わせる (下)。元の実装は消さない
  6. フェーズ 5 (公開): bin/ に入口を置く (テストが全件一致してから置く。ローカルルール第 3 章「置いてからテストしない」)。TOOLS-USAGE に使い方を足す。使い方 (見出し名) を知らせる周知の案は、必要なときに出す

テストの方針

  • 答え合わせの相手がある: 単純な全走査 (1 行ずつ読んで時刻を比べる) を相手に、二分探索の結果が一致することを総当たりで確かめる (共通ルール「答え合わせの相手があれば突き合わせる」)。時刻・マージン・並び (逆戻りの量) を変えて、取りこぼしが無いことを見る
  • ランダムな並びのテストは、結果の正しさも見る (件数 ・ 順序 ・ 内容)。壊れていないことだけを見ない
  • 期待値は先に手で書く。実装の出力から golden を作らない
  • 位置合わせ: 全バイト位置から始めて、行頭が正しく取れる (日本語・絵文字の途中を含む)
  • 生きているログ: 追記中のファイルを読んでも、最後の途中の行を出さない
  • 冪等 ・ 本番のログを触らない (材料は tests/ と tmp/)。実ログに対する試験は、中身を出さず件数や位置だけを見る

リスク

リスク備え
逆戻りが想定より大きいログで、入口を取りこぼすマージンを引数にする。ツールが、見つけた範囲の手前に「マージンより古い行があるか」を調べる自己点検 (--verify) を持つ。実測は 2 本だけ。別のログで最大を測り直す
行が 1 MB を超え、位置合わせの読みが大きくなる読む塊を倍々に増やす。上限を決め、超えたら警告して先へ進む
Claude Code の JSONL の形が版で変わる形への依存は表示用の抽出だけに限る。失敗したら生の行を返す。type ・ timestamp の読み取りが外れたら、警告を出す
出力に個人名・パス・機密が出て、AI の応答にそのまま載るパスと行の中のユーザプロファイルの値は、既定で伏せる。出力を応答へ引き写すときは、共通ルール「機密情報のマスキング」に従う
TypeScript と Rust で結果がずれる (正規化 ・ 時刻の解釈 ・ 文字の扱い)同じ材料で総当たりに突き合わせる。例外は出ず静かにずれるので、突き合わせが唯一の安全網
同期 API で固まる1 回の読みの大きさと回数に上限を付ける。固まったことに気づけるようにする

この計画の限界: 実測は、このマシンの 2 本のログだけ。Rust の速度、600 MB での Select-String ・ readline の時間、時刻の逆戻りの最大は未測定または 2 本だけ。構成は変わりうる。時刻の範囲が長い理由 (再開) は見込みで、確かめていない。
