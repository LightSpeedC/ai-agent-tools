safe-push 計画（Git の同期を壊さずに行う共有ツール）

複数のセッション ・ PC ・ クラウドから書き換えられるリポジトリを、commit → pull --rebase → push の一続きで、壊さずに GitHub と同期する共有コマンドを足す。

背景と依頼の条件

2026-10-18、ai-agent-rules から依頼が来た（ai-chat-lite #1530。ai-agent-rules の計画 p261018-01）。Obsidian Vault と、ai-agent-rules の共通ルールは、複数のセッション ・ PC ・ クラウドから書き換えられる。commit ・ push は Stop フックが行うので、同じ clone に同時に何本も来る。壊さずに GitHub と同期する共有ツールを、こちらで作る。名前 ・ 引数 ・ ロックの持ち方 ・ 期限 ・ 終了コードは、こちらに任された。

満たすこと

  • 排他: 同じ clone で同時に呼ばれても、commit → pull --rebase → push の一続きが重ならない。ロックが取れないときは 3 秒おきに 9 秒まで取り直し、だめなら飛ばす。残ったロックで止まり続けない
  • 載せ方は 2 通り: 変更をすべて載せる呼び方と、名指しのパスだけを載せる呼び方。名指しのときは、名指し以外の commit 前の変更を残したまま同期できる
  • 取り込んでから送る: ほかの clone の push を取り込んでから送る。ぶつかったら止めて報告し、手元の commit と変更を消さない
  • 動く場所: Windows ・ Linux ・ Mac ・ クラウド（sh のみ）。git の呼び出しは timeout 付き。日時は JST。出力は短く
  • 使わない操作: reset --hard ・ stash ・ checkout --。git の設定は書き換えない
  • テストを先に: 裸のリポジトリと clone 2 つで書く。名前は safe-push に決まり、依頼元へ知らせる

Stop フックから呼ばれる前提で作る。Stop フックは、終了コード 2 を「終わらずに続ける」と読む（連続 8 回まで）。引数の誤りなどでこのツールが 2 を返すと、利用者の応答が終わらなくなる。終了コードに 2 を使わない（決める点 46）。

動き（一続きの手順）

1. 引数を調べる（clone か。ブランチは上流を持つか）
2. ロックを取る（3 秒おきに 4 回。約 9 秒まで。だめなら飛ばして終了）
3. 載せる
     --all:      git add -A して commit
     名指し:     git add -- <パス> して、そのパスだけを commit
     載せるものが無ければ、commit を飛ばす
4. 取り込む（git pull --rebase）
     名指しで、追跡しているファイルの書きかけが残っていれば、取り込まない（決める点 43）
     浅い clone で失敗したら、fetch --unshallow してやり直す（決める点 52）
     ぶつかったら rebase --abort で手元に戻し、止めて報告（終了）
5. git push（失敗したら、やり直さず、エラーとして終了）
6. ロックを外す（どの終わり方でも、自分のロックだけを外す）
  • やり直しは 2 つだけ: ロックの取り直し（3 秒おき ・ 4 回）と、浅い clone の fetch --unshallow の 1 回。push は、やり直さない（失敗したらエラー。commit は手元に残り、次の回の呼び出しが送る）
  • git の呼び出しは 1 回ごとに timeout を付ける（60 秒。決める点 50）。〜Sync の API は使わず、非同期で呼ぶ
  • 一続き全体の上限は 3 分。超えたら、動いている git を止め、ロックを放して、終了コード 1（決める点 54）
  • git の設定は書かない。必要な設定は、呼び出しごとの -c で渡す
  • rebase --abort は使う。rebase を始める前の手元の commit に戻すだけで、reset --hard ではない。手元の commit と変更は残る
  • commit のメッセージは固定で、safe-push yyyy/mm/dd hh:mm:ss（JST。決める点 48）

出力

1 行。件数とファイル名だけを出す。会話や中身は出さない。

✅10/18 12:34 同期しました（commit 1 ・ push 済）
⬜10/18 12:34 別の同期が動いているため、飛ばしました（約 9 秒待ちました）
❌10/18 12:34 取り込みでぶつかりました: notes/a.md ・ notes/b.md（手元の commit と変更は残してあります）
❌10/18 12:34 push に失敗しました（commit は手元に残してあります）
⚠️10/18 12:34 古いロックを取り除きました（pid 1234 ・ 開始 10/18 12:30 ・ 別のホスト）。同期しました（commit 1 ・ push 済）

ホスト名は出力に出さない（共通ルール「機密情報のマスキング」）。同じホストか、別のホストかだけを書く。

決める点

41. 名前

案は、41-A safe-push（推奨）・ 41-B sync-push ・ 41-C commit-sync ・ 41-D repo-sync。git- で始まる名前は、同じ名前の既存のツールがあり、Git のサブコマンドと誤解されるため、案から外した。

決めたこと（2026-10-18、利用者の判断）。41-A。名前は safe-push。「壊さずに送る」という目的が、名前で伝わる。

依頼元の計画（ai-agent-rules の p261018-01）と比べ、47 〜 53 を取り入れた。決めたことは、利用者の判断（2026-10-18）。

42. すべて載せる呼び方

safe-push "<リポジトリ>" --all               # 変更をすべて載せる
safe-push "<リポジトリ>" <パス> [<パス> …]    # 名指しのパスだけ載せる

決めたこと（42-B）。すべて載せるときも --all を必ず付ける。パスも --all も無ければ、止める（終了コード 5）。パスの渡し忘れで、全部を載せてしまう事故を防ぐ。依頼元の計画（パスなしで全部）とは形が違うので、依頼元へ知らせる。

  • --all とパスを両方渡したときも、止める（終了コード 5）
  • Stop フックの登録は、リポジトリと --all を渡す

検討して採らなかった案: 42-A（パスなしで全部載せる）。渡し忘れで全部を載せるおそれがある。

43. 名指しで、ほかの未 commit の変更が残っているときの取り込み方

git pull --rebase は、作業ツリーに未 commit の変更があると、取り込み側とぶつからなくても止まる。名指し以外の変更を残したまま同期するための決め。

決めたこと（43-B）。作業ツリーに、名指し以外の未 commit の変更（追跡しているファイルの書きかけ）が残っているときは、取り込みをしない。名指しのパスを commit して、そのまま git push だけを試す。

  • 別の clone がまだ push していなければ、push が通る
  • 別の clone が先に push していたら、push が拒否され、終了コード 4 で止まる。commit は手元に残り、書きかけが commit されるか無くなったあとの呼び出しで、取り込んで送られる
  • 追跡していないファイル（新しいファイル）は、pull --rebase を止めないので、書きかけに数えない
  • 書きかけが無いとき（すべて載せる呼び方を含む）は、ふつうの pull --rebase で取り込む

書きかけが残る間は取り込みが遅れる。取り込んだ結果を壊すことは無い。

検討して採らなかった案

  • 43-A（一時の作業ツリーで載せ替える）: 実装が重く、手元の変更を残したままブランチを進める操作が要る。採らない
  • 43-C（ロックを持ったまま stash → fetch → rebase → stash pop）: ロックは、ファイルを直接書く側のセッションを止めない。stash の間に書きかけが一時的に元へ戻り、その間の読み書きが壊れる。依頼の「stash は使わない」にも反する。却下
  • 51-A（pull --rebase --autostash）: 同じ理由で外した（依頼元の計画の指摘）

44. ロックの持ち方

決めたこと（49-A）。.git/safe-push.lock というファイルを、「無いときだけ作る」書き方で作る（wx）。中にホスト名 ・ pid ・ 開始時刻（JST）を書く。.git/ の中なので、追跡されず、別の clone と混ざらない。

  • 古いロックの判定: 同じホストで、pid のプロセスが無ければ、残骸として取り除く。ホストが違うときは、pid を確かめられないので、期限（5 分。決める点 54）だけで判断する
  • 放すのは自分のロックだけ: 中のホスト名と pid が自分のときだけ消す。古いと見なされて取り除かれ、別の呼び出しが取り直したロックを、消さないため
  • 作るのと中身を書くのが 1 つの操作で、Windows ・ Linux ・ Mac で同じに動く

期限と、古いロックの扱いは、決める点 54。

45. ロックを取る待ち（依頼のとおり。決める点ではない）

決めたこと。取れなければ、3 秒おきに取り直す。初回を含めて 4 回、約 9 秒まで。それでも取れなければ、飛ばして終了する。待つのは長くても約 9 秒。

46. 終了コード

決めたこと（46-A）。2 を使わない。Stop フックは終了コード 2 を「続ける」と読む。引数の誤りや衝突が 2 だと、応答が終わらなくなる。ほかのツールは引数の誤りを 2 にしているが、このツールはフックから呼ばれるので変える。依頼元の計画の「衝突 ＝ 2、push 失敗 ＝ 3」は、「3、4」に変わるので、依頼元へ知らせる。

コード意味
0同期した、載せるものも取り込むものも無かった、またはロックが取れず飛ばした（出力で区別する。飛ばしても、フックに誤りの表示を出さないため）
1そのほかの失敗（commit の失敗 ・ git が時間切れ）。手元の commit と変更は残してある
3取り込みでぶつかった。ぶつかったファイル名を出す。人の対応が要る
4push に失敗した（認証 ・ 回線 ・ 拒否）。やり直さない。commit は手元に残り、次の回が送る
5引数や置き場の誤り（clone でない ・ 上流が無い ・ パスが clone の外）

47. リポジトリの渡し方

決めたこと（47-A）。リポジトリを最初の引数に必須で渡す。--path は無い。Stop フックも cron も、必ずリポジトリを渡すので、カレントの取り違えで別の clone を触る事故が起きない。

48. commit のメッセージ

決めたこと（48-A）。固定で safe-push yyyy/mm/dd hh:mm:ss（JST）。--message は無い。

50. 時間切れ（git の 1 回と、一続き全体）

決めたこと（利用者の判断。案の外から選んだ）。git の 1 回は 60 秒で打ち切る。一続き全体の上限は 3 分（決める点 54）。

52. 浅い clone

決めたこと（52-A）。クラウドの clone は浅い。pull --rebase が失敗したら、git fetch --unshallow をして、この回の中で 1 回だけ取り込みをやり直す。2 回目も失敗したら、エラーで終わる。初回だけ時間がかかる。

53. 衝突のときの出力

決めたこと（53-A）。ぶつかったファイル名を出す（リポジトリ内の相対パス）。中身は出さない。

54. 一続き全体の上限と、ロックの期限

一続きの呼び出しは、status ・ add ・ commit ・ pull --rebase ・ push の 5 回前後（浅い clone では fetch --unshallow が加わる）。git は 1 回ごとに 60 秒で打ち切るので、全部が詰まった最悪は 300 〜 360 秒になる。ふつうは数秒で終わる（見込み。実測はしていない）。固定の期限だけでは、最悪の場合に超えるため、一続き全体にも上限を付ける。

決めたこと（54-A）。

  • 一続き全体の上限は 3 分。超えたら、動いている git を止め、ロックを放して、終了コード 1 で終わる
  • ロックの期限は 5 分。持ち主は 3 分以内に必ず終わるので、5 分より古いロックは、確実に持ち主が居ない
  • 古いロックは、取り除いて、報告する。出力に「古いロックを取り除きました（pid ・ 開始時刻 ・ 同じホストか別のホストか）」を足し、そのまま同期を続ける。取り除かずに止めると、残ったロックで止まり続けてしまう（依頼の条件に反する）
  • 同じホストで pid が無ければ、期限を待たず、すぐに取り除く（取り除いたことは、同じく報告する）
  • ホストが違うロックは、pid を確かめられないので、期限（5 分）だけで判断する

検討して採らなかった案: 54-B（全体の上限は無しで、ロックの期限を 5 分にする）。極端に遅い回で、動いているロックを取り除くおそれが残る。

実装で、計画から変えた点

  • 出力にホスト名を出さない。計画の例には「ホスト」と書いたが、共通ルール「機密情報のマスキング」に合わせ、「同じホスト ・ 別のホスト」とだけ書く（ロックの中身には、ホスト名を書く）
  • リポジトリは、最上位のフォルダだけを受ける。サブフォルダを渡すと、終了コード 5。別の clone や、親のリポジトリを取り違えないため
  • 全体の上限（3 分）は、ロックを取ったあとから数える（ロックの待ちは数えない）
  • 載せるものがあるかは、git add のあと git diff --cached --quiet で見る。無ければ commit を飛ばす
  • push は、git push <remote> HEAD:<上流の ref> と、先を明示する（設定の push.default に左右されない。設定は読むだけ）
  • 失敗の種類は、git の出力の文字で見分ける（LC_ALL=C で言語を揃える）。出力そのものは、画面に出さない

踏んだ落とし穴（テスト）

  • 2 つ目の clone を、改行の変換が有効なまま作ると、全ファイルが「変更あり」になり、ありもしない衝突が出た。Git for Windows は、既定で checkout 時に CRLF へ変換する。clone の時点で -c core.autocrlf=false を渡す（あとから設定しても、すでに変換されている）
  • テストの補助が出力の前後の空白を削るため、git status --porcelain の先頭の行の空白が落ち、照合が外れた。落ちた原因は、道具ではなくテストだった

残っている穴

  • 古いロックを取り除く瞬間に、別の呼び出しが同じロックを取り除き、取り直されたロックを消す窓が、ごく狭く残る（取り除く直前に中身を読み直して、変わっていれば消さない形にして、狭めてある）
