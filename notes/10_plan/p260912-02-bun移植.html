なぜ急ぐか

もともとは速さの話だった。html2md のベンチで bun が C# の 5 倍速いと分かっていたが、動いているものを置き換える理由としては弱かった。

事情が変わったのは 2026-09-12。開発環境から PowerShell ツールが使えなくなり、Bash から exe を呼ぶしかなくなった（課題 i260912-06）。そこで文字コードの食い違いが表に出た。

処理系標準出力Bash から呼ぶと
.NET（いまの 3 本）CP932日本語が化ける
Node ・ BunUTF-8そのまま読める

.NET の Console.WriteLine はコンソールの出力コードページに従うため、日本語 Windows では CP932 になる。Node と Bun はコードページを見ず、常に UTF-8 で書く。つまり移せば、この問題は直すまでもなく消える。

aichat は先に移行を済ませており、Bash から呼んでも化けない。残り 3 本も同じ形にする。

当て木は別に用意した。tools/50_run/psh が PowerShell の出力を読み分けて UTF-8 で流す。移植が終われば要らなくなる。

決めたこと

取り決めの本体は共通化計画の「別の処理系へ移すときの取り決め」にある。ここに書くのは、今回決めた進め方だけ。

点決めなぜ
順序 convert-encoding → text → html2md 他のツールのファイルを直す道具なので、先に移すと移植作業そのものが楽になる。テストも最も厚い（140 件）
テスト 既存の ps1 をそのまま流用する スクリプト冒頭の $Exe を差し替えるだけで移植版に当たる。移植と同時にテストを書き直すと、差が出たとき切り分けられない。node:test への移行は切り替え後
型チェック 最初は入れない bun も node も型チェックをしない。入れるのは切り替え後。型注釈は書いておく
切り替え 1 本ずつ 1 本通れば、それだけ先に UTF-8 化の恩恵が出る

public/ が優先 path になっている

PATH は public/ を html2md/ より先に見る。移植版の入口をここへ置いた瞬間に切り替わる。

…/html2md/public     ← 先に見る（移植版の入口を置く）
…/html2md            ← 後（いまの exe）

exe のリネームが要らなくなった。共通化計画は「名前を入れ替える」段を置いているが、public/ があれば置くだけで切り替わり、消すだけで戻る。C# 版は名前を変えずにそのまま残せるので、突き合わせにも使い続けられる。

置いた瞬間に、呼ぶ側すべてが移植版に変わる。ほかのプロジェクトも同じ PATH を見ている。テストが全件一致してから置く。

進め方

1 本につき次の順で進める。置くのは最後。

順やること確かめ方
1src/<名前>/*.ts に移す。オプションは現存と同じまま—
2既存の ps1 テストを移植版に向ける（$Exe の差し替え）全件が現存と同じ結果になる
3本番の資料でも突き合わせるテストケースに無い書き方が本番にはある
4public/ に入口（<名前> と <名前>.cmd）を置くBash ・ cmd の両方から呼べる
5しばらく使って確かめる問題が出たら public/ から消すだけで戻る

入口は 2 本

呼ぶ側から見て名前は変わらない。中身がどちらの処理系で走るかは入口が決める。bun を優先し、無ければ node。書き方は共通化計画にある。

呼ぶ側選ばれるもの
Bashpublic/<名前>（拡張子なしの sh）
cmd ・ PowerShellpublic/<名前>.cmd（PATHEXT に sh は無い）
突き合わせhtml2md.exe 等（名前を変えずに残す）

移植の下地

道具C# の行数すでにあるもの
convert-encoding1,704無し
text1,316無し
html2md2,566tools/90_misc/bench-html2md/port.js（419 行）

port.js は下地としては 1/6 程度。ベンチのために変換の中核だけを移したもので、検査・SVG の切り出し・CSS 変数の解決・chapters の表化・他ファイルへのアンカー張り替えが入っていない。そのまま育てるより、書き起こす前提で見たほうがよい。

踏んだもの

CP932 のエンコーダは標準に無い

TextDecoder は shift_jis を読めるが、TextEncoder は UTF-8 しか書けない。2 バイト組を総当たりでデコードして逆引きを組み立てた（9,206 件・14 ms）。依存を増やさずに済む。半角カナは 1 バイトなので別に持つ（U+FF61〜U+FF9F が 0xA1〜0xDF に並ぶ）。

if ( ) の中の %errorlevel% は実行前の値になる

rem 誤り。ブロックを解析した時点で展開され、いつも 0 が返る
if %errorlevel%==0 (
    bun "…\main.ts" %*
    exit /b %errorlevel%
)

エラーにならず、静かにいつも 0 を返す。移植版のテストで終了コードを見る 19 件がすべて落ち、移植の誤りと見分けが付かなかった。分岐を goto にして、終了コードをブロックの外で読む形に直した。

同じ形が 2 箇所にあった——共通化計画のサンプルと psh.cmd。どちらも直した。これから作る入口も goto の形にする。

大小を区別しない突き合わせが、移すと落ちる

C# は HashSet<string>(StringComparer.OrdinalIgnoreCase) で大小を無視して比べていた。TypeScript の Set にその仕組みは無いので、入れるときに小文字へ寄せた——が、引くときを直し忘れた。

その結果、.html → .md の置き換えがすべて素通りし、16 ケース中 8 ケースが落ちた。例外は出ず、リンクが .html のまま残るだけなので、テストが無ければ気づけない。

比較の仕方が言語で変わるところは、入れる側と引く側の両方を見る。C# の OrdinalIgnoreCase・Path の大小無視は、移した先では自分で揃える必要がある。

CP932 に無い記号を cmd に書いてしまう

text.cmd のコメントに —（U+2014 EM DASH）を書いたところ、SJIS 化で止まった。CP932 にあるのは ―（U+2015 HORIZONTAL BAR）で、U+2014 は無い。見分けが付かない。

移植版の convert-encoding が捕まえた。[NG] sjis で表現できない文字があります: 2 行目の '—' (U+2014) と位置まで出る。書き換えずに止まるので、気づかないまま ? に化けることがない。

切り替えの後に回すもの

  • オプションを -- へ寄せる（check-markdown ・ check-contrast）。移植中に変えると、一致の確認が古い形と新しい形の混在になる
  • テストを node:test へ移す
  • 型チェック（tsc --noEmit）を入れる
  • psh を消す。PowerShell ツールが戻れば不要
