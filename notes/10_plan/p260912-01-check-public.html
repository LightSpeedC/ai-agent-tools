何を解決するか

課題 i260912-01。ai-agent-rules からの依頼。public のリポジトリに出したものは消せない。個人名・実体パス・認証情報が 1 度でも混ざれば、履歴を書き換えない限り残る。

共通ルールには「機密情報のマスキング」と「コミット前の確認」があり、人が目で確かめる形になっている。目視は、量が増えると必ず抜ける。異体字の混入のように、そもそも目で見分けられないものもある。

取り返しがつかない側の失敗である。コードは書き直せるが、公開されたリポジトリの履歴に入った個人情報は消せない。誤検出で止まる不便より、見逃す害のほうが大きい。迷ったら止める側に倒す。

今の手当てとの違い

いまあるもの何を見るか足りないところ
check-markdownMarkdown が GitHub で崩れないか中身が出してよいものかは見ない
check-contrastHTML の配色が読めるか同上
共通ルールの「コミット前の確認」人が目で確かめる実行されたかどうかが残らない。量が増えると抜ける

置き場と形

html2md に置く

このフォルダは「HTML と Markdown の変換と検証」の置き場として作った。公開前検査はその外側にあたる。それでもここに置く。理由は 3 つ。

  • PATH に入っているのはこのフォルダだけ。別の置き場を作ると、使う側が 2 箇所を知ることになる
  • check-markdown ・ check-contrast と同じ性格の道具（推測せず実物で判定し、指摘の件数を終了コードで返す）
  • 公開資料を作るプロジェクトは複数あり、1 本にすれば全部が守られる。共通化計画が解決した問題と同じ構図

決定引き受けるにあたり、共通化計画の「置くもの」に check-public を足し、このフォルダの位置づけを「共有ツール置き場」に広げる。変換と関係ない道具が今後ここに増えることを受け入れる。

プロジェクト名は後で変える予定。html2md は変換ツールの名前で、置き場の名前としては狭い。名前を変えるのは道具が出揃ってからで、この計画には含めない。

ps1 で書く。exe にはしない

案内容採否
A（採用） check-public.ps1 ＋ check-public.cmd。check-markdown ・ check-contrast と同じ形 採用検査系は ps1 で揃っている。正規表現の調整が頻繁に要る種類の処理で、ビルドを挟まないほうが直しやすい
B C# で書き check-public.exe にする 見送りi260830-13 で check-markdown の exe 化を「やらない」と決めた前例に揃える。起動の速さが要る場面が無い

html2md の検査からも呼ぶ

決定依頼のとおり、html2md の検査からも呼ぶ。変換を回すたびに公開前検査が通るので、公開の直前まで気づかない状態にならない。

外せるようにする。変換は編集のたびに何度も回すため、切れないと重さが効いてくる。

実装外し方
exe--no-public-check
ps1-NoPublicCheck

指摘があれば html2md 自身の終了コードも 1（指摘あり）にする。検査の種類が増えても終了コードの意味は変えない。

どう呼ぶかは決まっていない

html2md.exe は C# 、参照実装は ps1 で、検査の本体をどちらに置くかで形が変わる。

案形代償
A（推す） 検査の本体は check-public.ps1 の 1 本。exe も ps1 も同じスクリプトを起動して結果を受け取る 実装が 1 本で済み、exe と ps1 で結果がずれない。代償は PowerShell の起動時間（1 回あたり 1 秒弱）と、exe が PowerShell に依存すること
B C# と ps1 に同じ検査を 2 本書く。ほかの変換・検査と同じ持ち方にする 起動は速く、依存も増えない。代償は乖離。正規表現の調整が両方に要り、片方だけ直す事故はこのプロジェクトで繰り返し起きている
C 検査の本体を C# で書き、check-public.exe として独立させる。ps1 はその exe を呼ぶ 起動が速く実装も 1 本。代償はビルドが要ること。誤検出の調整が頻繁に要る種類の処理で、直すたびにビルドを挟む

A を推す。この道具の値打ちは検査の精度にあり、精度は誤検出を見ながら何度も直して上がる。2 本に分けると、その調整が 2 倍になるか、片方だけ古くなる。1 秒弱の遅さは --no-public-check で外せる。

呼ぶ引き金

決定変換のたびに走るほかに、変換が起きない場面の引き金を共通ルールに書き足す。道具を作っても、呼ぶ引き金が無ければ実行されない。

  • 最初のコミットの前
  • gh repo create で public を作る前
  • GitHub Pages を公開する前

書き足す先と文言は別に提示する。ルールの更新は指示を待つ。

検査する 6 項目

依頼で挙がった 6 つをそのまま採る。各項目は独立に切れるようにする（-Skip で名指し）。誤検出が多い項目だけを外して使えないと、道具ごと使われなくなる。

#対象見つけ方誤検出の抑え方
1 メールアドレス 一般的なアドレスの形 example.com ・ noreply@ ・ <メールアドレス> のような伏せ字は除く
2 実体パス C:\Users\ の直後がプレースホルダでないもの <username> ・ $env:USERPROFILE ・ ~ は除く。実行しているユーザー名も環境から取って照合する
3 認証情報 password passwd secret api_key token= に値が続くもの 値が空・プレースホルダ・変数参照（$ % {{ }}）なら除く。いちばん誤検出しやすい項目
4 除外語 リストに書かれた語の単純一致 リストは利用者が持つ（第 4 章）
5 異体字の混入 日本語・英数字の並びに混ざったキリル・ハングル その言語だけで書かれた行・コードブロックは除く
6 git の author git config user.name ・ user.email と、ローカルのユーザー名を本文から探す 名前をリストに書かずに済むのが利点。git の外で実行したときは黙って飛ばす

探す範囲

git が追跡しているファイルだけを見る。.gitignore で除外したものは公開されないため、見る必要が無く、見れば必ず誤検出になる（除外語リスト自身がそこにある）。

バイナリは飛ばす。文字コードは text find と同じ判定を使い、SJIS ・ UTF-16 も取りこぼさない。ここを取りこぼすと、cmd ・ reg だけが検査されない状態になる。

除外語リスト

顧客名・案件名・内部システム名は、正規表現では見つけられない。リストとして持つしかない。

リスト自体が機密になるため、先頭 _ のファイルを既定にする。共通ルール「.gitignore の共通除外設定」により全階層が Git 管理外になる。

項目決め
既定の置き場プロジェクト直下の _public-ng-words.txt
指定-WordList <パス> で差し替えられる
形式1 行 1 語。空行と # 始まりは読み飛ばす
大小文字区別しない
無いときこの項目だけ飛ばし、飛ばしたことを画面に出す。エラーにはしない

リストが無いことを黙って通さない。「検査した」という記録だけが残り、いちばん効く項目が働いていない状態になる。

出力と終了コード

終了コードはほかの検査ツールと同じ契約にする。使う側が道具ごとに覚え直さずに済む。

コード意味
0指摘なし
1指摘あり
2引数や対象の誤り

出力はファイルと行番号、当たった項目、当たった箇所。当たった値そのものは伏せる。

docs/01-背景.html:42  [実体パス]  C:\Users\<伏せ>\...
notes/10_plan/p260901-01-設計.html:13  [除外語]  1 件

=== 2 件の指摘があります ===

検出した値を画面にそのまま出さない。出力は会話ログ・CI のログに残る。伏せるための道具が漏らす側にまわってはいけない。

引数

引数既定内容
-Path <パス>カレント対象のプロジェクトフォルダ
-WordList <パス>_public-ng-words.txt除外語リスト
-Skip <名前>—飛ばす項目。複数回指定できる
-All—追跡外のファイルも見る

決まったこと

#決めたことどこに書いたか

決まったこと（2026-09-12 の追記）

第 2 章に「検査の本体を ps1 ・ C# と ps1 の 2 本 ・ C# exe のどれにするか」を残していたが、要件が増えたうえで実測し、どれでもない形に決まった。詳しくは処理系の比較。

決めたこと内容
処理系Bun ＋ TypeScript。起動込み 48 ms（PowerShell の 12 分の 1）。SJIS ・ UTF-16 を標準で読める。Bun は .ts を .js と同じ速さで実行する
動く場所Windows ・ Linux ・ Mac。この要件で PowerShell 5.1（Windows 専用）と csc の exe（.NET Framework）が落ちた
判断の重み実行時の速さを重視し、事前の段（コンパイル・型チェック）は重み付けしない。頻度が低いため
型チェック必須。Bun も Node も実行時には型を見ない（実測）。tsc --noEmit を別に回す
依存増やす。typescript と @types/node の 2 つ。「依存パッケージを増やさない」の方針をここで変える
型チェックの時期ソースを修正したとき
単一 exe 化採らない。bun build --compile は速くならず（48 → 53 ms）、84.7 MB になり、型チェックもしない

あわせて、共通化計画の第 9 章に別の処理系へ移すときの取り決め（オプションを -- に揃える／古い形は案内して止める／全テストが一致してから切り替える／起動は bun 優先で無ければ node）を書いた。

この計画に入っていないもの

  • git の履歴の検査。いま作業ツリーにある内容だけを見る。過去のコミットに入ったものを見つけても、直すには履歴の書き換えが要り、道具の役目を越える
  • 自動での修正。見つけて止めるところまで。何に置き換えるかは書き手が決める
  • フックへの組み込み。引き金は人が呼ぶ形から始める
