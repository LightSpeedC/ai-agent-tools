## 1. 背景

html2md・convert-encoding・text 等の出力を DOS の `more` コマンドへパイプしてページングすると、UTF-8 の出力が CP932 として読まれて文字化けする。`more` は Windows 標準の .NET／PowerShell 系が持つ「出力コードページ問題」の受け手側で、[課題 i260912-06](../40_issues/issues.html) と根が同じ。

UTF-8 セーフなページャー（`less`）を新設する。

## 2. 実装方式（決定済み）

<strong>TypeScript（bun 優先・node 予備）にする。</strong>他ツール（html2md・text・convert-encoding・psh・check-*）と同じ理由で、Node・Bun は常に UTF-8 で出すため。C#／PowerShell を選ぶと、この課題そのものを再び踏む。

置き場・呼び方は他ツールと同じ形に揃える。

| ファイル | 役割 |
|---|---|
| `less` | sh 入口。bun を優先、無ければ node で `src/less/main.ts` を実行 |
| `less.cmd` | cmd 入口。同じ振り分け |
| `src/less/main.ts` | 本体 |
| `src/less/bun-ffi.d.ts` | 型チェック専用の最小限のアンビエント宣言（`Bun`・`bun:ffi`）。下記「Bun では動かない」を参照 |

## 3. 機能範囲（決定）

<strong>A（最小限のページング）を採用。あわせて上下スクロールを追加する。</strong>2026-09-17 決定。

- `q` — 終了
- `Space`／`PageDown` — 画面の高さの 3/4 くらい下
- `Enter`／`↓` — 1 行下
- `↑` — 1 行上
- `PageUp` — 画面の高さの 3/4 くらい上

検索・行番号・`g`/`G`（先頭・末尾へ）は今回持たない（B の残り）。標準出力がパイプ／端末でない（リダイレクト先がファイル等）ときは、ページングせずそのまま流す。

> [!NOTE]
> ✅ **済** 2026-09-19、利用者の指示で移動量を変更。`Space` は当初「1画面分」だったが、`PageDown` と同じ「画面の高さの 3/4 くらい」に統一。`PageUp`／`PageDown` の移動量も 2/3 → 3/4 に変更。あわせてステータス行にキー一覧を追加（下記「詳細仕様」を参照）。

> [!NOTE]
> **暫定と恒久**: 検索・行番号等、今回見送った機能は、実際に使ってみて不足を感じたら個別に足す（一度に全部作らない）。

## 4. 詳細仕様

### 入力

- 標準入力からパイプで受け取る（`html2md | less` の形）
- ファイル引数は今回持たない。**まずパイプ専用**（用途は「他コマンドの出力を見る」ため）

> [!IMPORTANT]
> #### キー入力の取得元（上下スクロール追加で新たに要る論点）
> <strong>`cmd | less` の形では、`process.stdin` はデータそのもの（パイプ）で埋まっており、キー入力には使えない。</strong>先頭を1画面表示するだけの案（Space/Enter/qだけ）ならデータを読み終えた後に `process.stdin` を使い回せたが、**上下スクロールは表示中も随時キーを受けるため、データ用のストリームとキー入力用のストリームを分ける必要がある。**
> 取得方法が Node と Bun で異なる（下記の落とし穴を参照）ため、`KeySource`（`onData`／`close` の2つだけを持つ）という共通の形に抽象化し、`page()` 側はどちらの処理系かを意識しない。
> ```typescript
> interface KeySource {
> 	onData(cb: (chunk: string) => void): void;
> 	close(): void;
> }
> ```
> **開けなければ（コンソールが無い環境）、スクロール操作を諦めて素通しにする**（下記「開けないとき」）。

> [!WARNING]
> <strong>実装時に踏んだ落とし穴（1）。</strong>素の `'CONIN$'` を渡すと、Node がカレントフォルダからの相対パス（例: `N:\ai-agent-tools\CONIN$`）として解決してしまい、`ENOENT` で失敗する（Bash・PowerShell 両方の実環境で実測）。**Win32 のデバイス名前空間 `\\.\` を前置する**と正しく開け、`isTTY` も `true` になる。

> [!CAUTION]
> **実装時に踏んだ落とし穴（2）。**`isTTY` が `true` を返しても、`setRawMode` が成功するとは限らない。読み取り専用（`'r'`）で `CONIN$` を開くと、Node では `setRawMode` が `EPERM` で落ちる。Windows の `SetConsoleMode` は書き込みアクセスも要るため、**`'r+'`（読み書き）で開く**必要がある。この不具合は手動確認（`isTTY` が `true` になることだけ）をもって「動く」と判断してしまい、利用者が実際にパイプ経由で実行するまで見つからなかった。
> **Bun では `'r'` ／ `'r+'` ／ `'w+'` ／ `'a+'` のどのモードで開いても直らない。**`setRawMode` が Node とは別のメッセージ（「TTY ではない」）で失敗し続ける（4モードとも実測）。Node は `'r+'` ／ `'w+'` でだけ成功しており、アクセス権の問題ではなく、**Bun の Windows 向け `node:tty` 実装が、標準入出力（fd 0/1/2）以外の fd を raw mode 対応の TTY として扱わない**という実装上の制約だと見られる（Bun の Issue 追跡でも Windows の Terminal/PTY 関連機能が未対応・制限ありと記載されている）。
> <strong>回避策: `node:tty` を経由せず、MS-CRT（`msvcrt.dll`）の `_kbhit` / `_getch` を `bun:ffi` で直接呼ぶ。</strong>これらはコンソールを直接読む実装のため、標準入力がパイプで埋まっていても影響を受けない（`echo ... | bun test.mjs` の形で実測）。`Win32 Console API`（`ReadConsoleInputW` 等）を直接叩く方式も前例がある（[bun-win32](https://github.com/ObscuritySRL/bun-win32)、外部パッケージとして公開されている）が、`CreateFileW` でハンドルを開き、`SetConsoleMode` を保存・復元し、`INPUT_RECORD`（共用体）をバイト列から自前でデコードする必要があり、実装量が大きい。`_kbhit`/`_getch` はコンソールのモード管理を CRT 側がやってくれるため、外部パッケージへの依存無しで数十行で済む。
> ```typescript
> const { dlopen, FFIType } = await import('bun:ffi');
> const { symbols } = dlopen('msvcrt.dll', {
> 	_kbhit: { args: [], returns: FFIType.i32 },
> 	_getch: { args: [], returns: FFIType.i32 },
> });
> ```
> 矢印・PageUp/Down は「拡張キー」で、`_getch()` が `0` か `0xE0` を返した後、もう一度 `_getch()` を呼ぶとスキャンコード（↑72／↓80／PgUp73／PgDn81）が来る（MS-CRT の昔からの仕様）。`handleKey()` が読める ANSI エスケープ列（`'\x1b[A'` 等）に変換してから渡すことで、Node 側と同じ解釈ロジックをそのまま使い回せる。
> `bun:ffi` の型は `bun-types` を依存に追加せず、使う分だけ `src/less/bun-ffi.d.ts` に自前で宣言した（外部パッケージへの依存を増やさない方針に合わせた）。
> 実行時にどちらの処理系かを見分けるのは `typeof Bun !== 'undefined'`（Bun がグローバルに注入する `Bun` オブジェクトの有無で判定）。**これがこのプロジェクトで初めて、シェルの入口ではなく main.ts 自身が実行時にランタイムを判断するコード**になる（他ツールは入口スクリプトの `command -v bun`／`where bun` だけで振り分けており、本体は Node の API だけで両対応している）。

### ページング

- 標準入力を全部読み切ってから始める（戻りスクロールのため、全行をメモリに持つ）
- `process.stdout.rows` で端末の行数を取り、1 画面分の行数を決める（取得できなければ 24 行）
- 表示位置は「先頭からの行オフセット（`top`）」1 つで持つ。キー操作は `top` を動かして再描画するだけ
- 再描画は画面クリア（`\x1b[2J\x1b[H`）してから `top` 〜 `top+高さ` を出す。最下行にステータス行を出す。2026-09-19、利用者の指示でキー一覧を含む形にした: `-- less (NN%) q で終了 | Page Up | ↑ | ↓・Enter | Page Down・Space --`（2026-09-19 に `Space・Page Down` から並び順を修正）
- `top` は `0` 〜 `行数-画面高さ` の範囲にクランプする
- 標準出力が端末でない（`process.stdout.isTTY` が false）とき、または `CONIN$` を開けないときは、ページングせずそのまま出力する

> [!IMPORTANT]
> #### 再描画のちらつき
> 実機確認で判明。**それまでの `render()` は移動量の大小によらず、キーを押すたびに画面全体をクリアしてから毎回全部描き直していた。**↓キー（1行スクロール）のように変化が小さいときでも画面全体が点滅する。
> ✅ **済** 2026-09-18、利用者の指示で下記の形に実装した（差分更新にする）。
> - **下方向（`top` が増える）は常にスクロール方式にする**（↓・Enter・Space・PageDown のすべて）。`scrollDown()` がカーソルを最下行に置いてから、新しく見える行の数だけ改行＋テキストを出す。改行のたびに端末が自然に1行分スクロールする（既存の内容はそのまま上へ押し出される）ため、移動量が画面の高さを超えていても同じやり方で書ける
> - **↑（矢印、1行）だけスクロール方式にする**。`scrollUp()` が `\x1bM`（Reverse Index）でカーソルを最上行に固定した状態から逆方向へ1行分スクロールし、最上行にできた空行へ新しく見える行を書く
> - **PageUp は今までどおり全画面クリア＋再描画のままにする**（`move()` に渡す `strategy` を `'redraw'` にする）。Reverse Index を複数行分繰り返す形は端末依存の懸念があり、もともと大きく動くキーなので点滅も気にならない
> - **ステータス行**（画面最下行の `-- less (NN%) --`）は、スクロール方式でも `writeStatus()` が毎回その場で上書きする（`\x1b[<行>;1H` でカーソルを合わせ、`\x1b[2K` で消してから書く）
> - **端に達していて実際には動かないとき（先頭で↑／末尾で↓等）は、何も出力しない。**`move()` の先頭で `clampTop` 後の値が現在の `top` と同じなら、再描画・ステータス更新とも行わず即座に戻る
> `render()`／`move()` だけの変更で済み、`handleKey()`・`KeySource` は影響を受けない。`tools/40_test/run-less-tests.ts`（bun・node とも8件）と型チェックは通したが、**実際の画面遷移（ちらつきが無くなったか、各キーの見た目）は自動化できないため、利用者による実機での確認が要る。**

> [!CAUTION]
> #### 実装時に踏んだ落とし穴（3）: スクロール範囲を区切らないとスクロールしない
> 実機確認で判明。<strong>↓キー・Enter を押しても表示が進まず、ステータス行の％表示だけが増えた。</strong>原因は、画面が「コンテンツ h 行＋ステータス行 1 行」の計 h+1 行を使っているのに、`scrollDown()` は「コンテンツの最終行（h 行目）」にカーソルを置いて改行していた点。**そこは端末にとって画面の最終行ではない**（1行下にステータス行がある）ため、改行してもスクロールは起きず、カーソルがステータス行へ動いてそこへ新しい行のテキストを上書きしていた。
> ✅ **済** 2026-09-19 に修正。**DECSTBM（`\x1b[1;h r`）でスクロール範囲をコンテンツ用の h 行だけに限定する**（`setScrollRegion()`、ページング開始時に1回設定）。この範囲内でだけ改行・Reverse Index が正しくスクロールし、範囲外のステータス行は影響を受けない。終了時（`finish()`）に `resetScrollRegion()`（`\x1b[r`）で画面全体に戻す。
> ✅ **済** あわせて、**`q` で終了したときの画面クリアを無くした**（利用者の指示）。ページャーの最後の表示をそのまま残し、カーソルをステータス行の下へ移して改行するだけにする。

> [!CAUTION]
> #### 実装時に踏んだ落とし穴（4）: スクロール範囲を区切っても、書き方次第でステータス行が残る
> 実機確認で判明。落とし穴（3）の修正後、<strong>`Enter` を押すとステータス行が消えずに残ったまま画面がスクロールしていった。</strong>原因は `scrollDown()` の書き方: 改行（`\n`）を先に出してからテキストを書いており、(1) 改行だけでは列が先頭に戻らない（`\n` は CR を含まない）ため、複数行分では列がずれる、(2) 書く前に行末までクリアしていないため、スクロールが確実に起きていない場合や、新しい行が前の内容より短い場合に文字が残る。
> ✅ **済** 2026-09-19、利用者の指示で修正。<strong>「行頭へ戻す（`\r`）→行末までクリア（`\x1b[K`）→テキストを書く→`\r\n`で次行へ」の順にする。</strong>スクロール範囲の最終行（h 行目）に最初に1回だけ位置決めした後は、各行を書くたびの `\r\n` で自動的に次の行の先頭（同じくスクロール範囲の最終行）へ戻るため、ループ内で毎回位置決めし直す必要はない。`scrollUp()` にも同じ理由で行頭復帰＋行末クリアを追加した。
> ✅ **済** 2026-09-19、150桁端末での実機確認で **↓・Enter とも乱れなく動くことを確認**。

> [!CAUTION]
> #### 実装時に踏んだ落とし穴（8）: スクロール（LF）を書き込みの後にすると、書いたばかりの内容が1行押し上げられる
> 実機確認で判明。<strong>下方向へ動くたび、最下行に空行が1行できる。上方向（`scrollUp`）では起きない。</strong>原因は落とし穴（4）の修正で採った順序（「クリア→書く→`\r\n`」）そのもの: **LF（スクロール）がテキストを書いた「後」に起きるため、書いたばかりの内容までスクロール範囲の中で1行分押し上げられ、最下行が空いたまま残る。**`scrollUp()` は逆に「まず Reverse Index でスクロールしてから書く」順だったため、この問題が起きていなかった（実機で報告されるまで気づかなかった）。
> ✅ **済** 2026-09-19 に修正。<strong>`scrollDown()` も `scrollUp()` と同じ「スクロールを先に、書くのを後に」の順にする。</strong>各行を「`\r\n`（行頭へ戻して次行へ＝スクロール）→行末までクリア→テキスト」の順で書く。スクロールで生まれた空行に書き込むだけになるため、書いたばかりの内容が押し上げられることが無くなる。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済みだが、**画面遷移の見た目そのものは自動化できないため、利用者による実機での再確認が要る。**

> [!NOTE]
> #### PageUp もスクロール方式にする（機能追加）
> ✅ **済** 2026-09-19、利用者の指示で `scrollUp()` を複数行に対応させ、`PageUp` も全画面再描画（`'redraw'`）ではなくスクロール方式にした。**画面の下寄りに来る行から先に書く**（後から挿す行ほど上に押し出されるため、逆順で書くと最終的に上から正しい順に並ぶ）。`move()` の `strategy` 引数と `'redraw'` 分岐、`render()` は**今後また使う予定があるため残した**（利用者の指示。既定値は `'scroll'` にし、呼び出し側は省略できる）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済みだが、**画面遷移の見た目そのものは自動化できないため、利用者による実機での確認が要る。**

> [!CAUTION]
> #### 実装時に踏んだ落とし穴（5）: 初回表示・PageUp でステータス行が1行上にずれる
> 実機確認で判明。<strong>最初の表示、および PageUp（`'redraw'` 方式）のあと、ステータス行が画面の最下行ではなく下から2行目に出る。</strong>原因は落とし穴（4）と同種: `render()` がコンテンツを書き終えたあと、改行（`\n`）だけでステータス行へ移っていた。改行は列を先頭へ戻さないため、コンテンツの最終行の文字数ぶんカーソルが右にずれたまま次の行へ移り、そこから書いたステータス行の反転表示が桁あふれして自動折り返しを起こし、見た目上1行分ずれていた。
> ✅ **済** 2026-09-19 に修正。**`render()` のステータス行書き込みを、絶対位置で書く `writeStatus()` に置き換えた**（重複していたステータス行の組み立てロジックも一本化）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済みだが、**画面遷移の見た目そのものは自動化できないため、利用者による実機での再確認が済むまで「済」にはしない。**

> [!CAUTION]
> #### 実装時に踏んだ落とし穴（6）: Bun はコンソールの出力コードページを UTF-8 にしない
> 実機確認で判明。**`less -h | less` で使い方の説明（全て日本語）が文字化けした**（UTF-8 のバイト列が CP932 として解釈される典型的な化け方）。原因は、**Node は Windows のコンソール出力コードページを自動的に UTF-8（65001）に設定するが、Bun はしない**こと。`less` の対話ページングは bun 優先のため、これまでの実機確認（`aichat -h` 等）でも実は同じ問題を踏んでいたが、内容の大半が ASCII で CP932 と UTF-8 の解釈結果が同じだったため気づかれなかった。
> ✅ **済** 2026-09-19 に修正。Bun のキー入力設定（`openBunKeySource()`）の中で、`bun:ffi` から `kernel32.dll` の `SetConsoleOutputCP(65001)` を明示的に呼ぶ（`_kbhit`/`_getch` と同じ手法の延長）。失敗しても対話ページング自体は続ける（別の try/catch にする）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

> [!CAUTION]
> #### 実装時に踏んだ落とし穴（7）: ヘルプの桁揃えを手で数えたスペースで決め打ちしていた
> 実機確認で判明。`↓・Enter`（矢印・中点・英単語が混在するラベル）の行だけ、他の行と桁が揃っていなかった。原因は **手でスペースを数えて決め打ちしていた**ことで、ラベルの並び順を変えたときに数え直しを忘れた。加えて、`↓`・`・`・`↑` の表示幅（この端末では全角＝2桁として描画される）を最初から正しく知らず、実機で試すまで分からなかった。
> ✅ **済** 2026-09-19 に修正。<strong>表示幅を計算する `displayWidth()`（ASCII・半角ｶﾀｶﾅは1桁、それ以外は2桁）と、それで桁を揃える `pad()` を実装し、`Usage` の組み立てをこれで行うようにした。</strong>ラベルの文字を今後変更しても自動的に桁が揃う。共通ルールにも「全角・半角混在のテキストを桁揃えするとき」を追記し、ai-chat-lite の public ルームへ周知した（他プロジェクトでも同じ不具合が起きないようにするため）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

> [!NOTE]
> #### 終了時・末尾の表示（機能追加）
> - ✅ **済** 2026-09-19、利用者の指示で `q` 終了時、反転表示のステータス行を消し、通常色（反転無し）の終了メッセージ「`-- less 終了 --`」に置き換えた（`finish()`）

## 5. テスト方針

キー入力を伴う対話的な画面遷移は自動テストにしにくい。**切り分けて考える。**

- **自動テストにする**: 1 画面分の行数計算、`top` のクランプ（範囲外に動かそうとしても止まる）、`isTTY` が false のときにページングせず素通しする経路
- **手動確認にとどめる**: 実際のキー入力（`Space`・`Enter`・矢印・`PageUp`/`PageDown`・`q`）による画面遷移、`CONIN$` が開けること自体、日本語を含む長文での表示崩れの有無、**Bun での `_kbhit`/`_getch` によるキー入力（拡張キーのデコードを含む）**

> [!NOTE]
> <strong>自動テストの構造上の限界。</strong>自動テストは `spawnSync` で標準出力をパイプに捕まえるため `process.stdout.isTTY` が常に `false` になり、キー入力を読む経路（`openNodeKeySource`／`openBunKeySource`）そのものに一度も到達しない。`bun:ffi` での `dlopen`・`_kbhit()` 呼び出しが例外を出さないこと（標準入力をパイプで埋めた状態でも）は手元で個別に確認したが、これはテストスイートには組み込めておらず、実際のキー入力による画面遷移は利用者による実機確認が要る。

置き場は他ツールと同じ`tools/40_test/run-less-tests.ps1`（＋同名の cmd）。
