## 1. 背景

html2md・convert-encoding・text 等の出力を DOS の `more` コマンドへパイプしてページングすると、UTF-8 の出力が CP932 として読まれて文字化けする。`more` は Windows 標準の .NET／PowerShell 系が持つ「出力コードページ問題」の受け手側で、[課題 i260912-06](../40_issues/issues.html) と根が同じ。

UTF-8 セーフなページャー（`less`）を新設する。

## 2. 実装方式（決定済み）

<strong>TypeScript（bun 優先・node 予備）にする。</strong>他ツール（html2md・text・convert-encoding・psh・check-*）と同じ理由で、Node・Bun は常に UTF-8 で出すため。C#／PowerShell を選ぶと、この課題そのものを再び踏む。

置き場・呼び方は他ツールと同じ形に揃える。

| ファイル | 役割 |
|---|---|
| `less` | sh 入口。bun を優先、無ければ node で `src/less/main.ts` を実行 |
| `less.cmd` | cmd 入口。同じ振り分け |
| `src/less/main.ts` | 本体 |
| `src/less/bun-ffi.d.ts` | 型チェック専用の最小限のアンビエント宣言（`Bun`・`bun:ffi`）。下記「Bun では動かない」を参照 |

## 3. 機能範囲（決定）

<strong>A（最小限のページング）を採用。あわせて上下スクロールを追加する。</strong>2026-09-17 決定。

- `q` — 終了
- `Space` — 1 画面分下
- `Enter`／`↓` — 1 行下
- `↑` — 1 行上
- `PageDown` — 画面の高さの 2/3 くらい下
- `PageUp` — 画面の高さの 2/3 くらい上

検索・行番号・`g`/`G`（先頭・末尾へ）は今回持たない（B の残り）。標準出力がパイプ／端末でない（リダイレクト先がファイル等）ときは、ページングせずそのまま流す。

> [!NOTE]
> **暫定と恒久**: 検索・行番号等、今回見送った機能は、実際に使ってみて不足を感じたら個別に足す（一度に全部作らない）。

## 4. 詳細仕様

### 入力

- 標準入力からパイプで受け取る（`html2md | less` の形）
- ファイル引数は今回持たない。**まずパイプ専用**（用途は「他コマンドの出力を見る」ため）

> [!IMPORTANT]
> #### キー入力の取得元（上下スクロール追加で新たに要る論点）
> <strong>`cmd | less` の形では、`process.stdin` はデータそのもの（パイプ）で埋まっており、キー入力には使えない。</strong>先頭を1画面表示するだけの案（Space/Enter/qだけ）ならデータを読み終えた後に `process.stdin` を使い回せたが、**上下スクロールは表示中も随時キーを受けるため、データ用のストリームとキー入力用のストリームを分ける必要がある。**
> 取得方法が Node と Bun で異なる（下記の落とし穴を参照）ため、`KeySource`（`onData`／`close` の2つだけを持つ）という共通の形に抽象化し、`page()` 側はどちらの処理系かを意識しない。
> ```typescript
> interface KeySource {
> 	onData(cb: (chunk: string) => void): void;
> 	close(): void;
> }
> ```
> **開けなければ（コンソールが無い環境）、スクロール操作を諦めて素通しにする**（下記「開けないとき」）。

> [!WARNING]
> <strong>実装時に踏んだ落とし穴（1）。</strong>素の `'CONIN$'` を渡すと、Node がカレントフォルダからの相対パス（例: `N:\ai-agent-tools\CONIN$`）として解決してしまい、`ENOENT` で失敗する（Bash・PowerShell 両方の実環境で実測）。**Win32 のデバイス名前空間 `\\.\` を前置する**と正しく開け、`isTTY` も `true` になる。

> [!CAUTION]
> **実装時に踏んだ落とし穴（2）。**`isTTY` が `true` を返しても、`setRawMode` が成功するとは限らない。読み取り専用（`'r'`）で `CONIN$` を開くと、Node では `setRawMode` が `EPERM` で落ちる。Windows の `SetConsoleMode` は書き込みアクセスも要るため、**`'r+'`（読み書き）で開く**必要がある。この不具合は手動確認（`isTTY` が `true` になることだけ）をもって「動く」と判断してしまい、利用者が実際にパイプ経由で実行するまで見つからなかった。
> **Bun では `'r'` ／ `'r+'` ／ `'w+'` ／ `'a+'` のどのモードで開いても直らない。**`setRawMode` が Node とは別のメッセージ（「TTY ではない」）で失敗し続ける（4モードとも実測）。Node は `'r+'` ／ `'w+'` でだけ成功しており、アクセス権の問題ではなく、**Bun の Windows 向け `node:tty` 実装が、標準入出力（fd 0/1/2）以外の fd を raw mode 対応の TTY として扱わない**という実装上の制約だと見られる（Bun の Issue 追跡でも Windows の Terminal/PTY 関連機能が未対応・制限ありと記載されている）。
> <strong>回避策: `node:tty` を経由せず、MS-CRT（`msvcrt.dll`）の `_kbhit` / `_getch` を `bun:ffi` で直接呼ぶ。</strong>これらはコンソールを直接読む実装のため、標準入力がパイプで埋まっていても影響を受けない（`echo ... | bun test.mjs` の形で実測）。`Win32 Console API`（`ReadConsoleInputW` 等）を直接叩く方式も前例がある（[bun-win32](https://github.com/ObscuritySRL/bun-win32)、外部パッケージとして公開されている）が、`CreateFileW` でハンドルを開き、`SetConsoleMode` を保存・復元し、`INPUT_RECORD`（共用体）をバイト列から自前でデコードする必要があり、実装量が大きい。`_kbhit`/`_getch` はコンソールのモード管理を CRT 側がやってくれるため、外部パッケージへの依存無しで数十行で済む。
> ```typescript
> const { dlopen, FFIType } = await import('bun:ffi');
> const { symbols } = dlopen('msvcrt.dll', {
> 	_kbhit: { args: [], returns: FFIType.i32 },
> 	_getch: { args: [], returns: FFIType.i32 },
> });
> ```
> 矢印・PageUp/Down は「拡張キー」で、`_getch()` が `0` か `0xE0` を返した後、もう一度 `_getch()` を呼ぶとスキャンコード（↑72／↓80／PgUp73／PgDn81）が来る（MS-CRT の昔からの仕様）。`handleKey()` が読める ANSI エスケープ列（`'\x1b[A'` 等）に変換してから渡すことで、Node 側と同じ解釈ロジックをそのまま使い回せる。
> `bun:ffi` の型は `bun-types` を依存に追加せず、使う分だけ `src/less/bun-ffi.d.ts` に自前で宣言した（外部パッケージへの依存を増やさない方針に合わせた）。
> 実行時にどちらの処理系かを見分けるのは `typeof Bun !== 'undefined'`（Bun がグローバルに注入する `Bun` オブジェクトの有無で判定）。**これがこのプロジェクトで初めて、シェルの入口ではなく main.ts 自身が実行時にランタイムを判断するコード**になる（他ツールは入口スクリプトの `command -v bun`／`where bun` だけで振り分けており、本体は Node の API だけで両対応している）。

### ページング

- 標準入力を全部読み切ってから始める（戻りスクロールのため、全行をメモリに持つ）
- `process.stdout.rows` で端末の行数を取り、1 画面分の行数を決める（取得できなければ 24 行）
- 表示位置は「先頭からの行オフセット（`top`）」1 つで持つ。キー操作は `top` を動かして再描画するだけ
- 再描画は画面クリア（`\x1b[2J\x1b[H`）してから `top` 〜 `top+高さ` を出す。最下行にステータス（`-- less (NN%) --`）を出す
- `top` は `0` 〜 `行数-画面高さ` の範囲にクランプする
- 標準出力が端末でない（`process.stdout.isTTY` が false）とき、または `CONIN$` を開けないときは、ページングせずそのまま出力する

> [!IMPORTANT]
> #### 再描画のちらつき（未対応・実装予定）
> 実機確認で判明。**今の `render()` は移動量の大小によらず、キーを押すたびに画面全体をクリアしてから毎回全部描き直している。**↓キー（1行スクロール）のように変化が小さいときでも画面全体が点滅する。
> **対処案（差分更新にする）。2026-09-17、利用者の指示で下記の形に決定。**
> - **下方向（`top` が増える）は常にスクロール方式にする**（↓・Space・PageDown のすべて）。カーソルを最下行に置いた状態で、新しく見える行の数だけ改行＋テキストを出す。改行のたびに端末が自然に1行分スクロールする（既存の内容はそのまま上へ押し出される）ため、移動量が画面の高さを超えていても同じやり方で書ける
> - **↑（矢印、1行）だけスクロール方式にする**。`\x1bM`（Reverse Index）でカーソル位置を起点に逆方向へ1行分スクロールし、最上行にできた空行へ新しく見える行を書く
> - <strong>PageUp は今までどおり全画面クリア＋再描画のままにする。</strong>Reverse Index を複数行分繰り返す形は端末依存の懸念があり、もともと大きく動くキーなので点滅も気にならない
> - **ステータス行**（画面最下行の `-- less (NN%) --`）は、スクロール方式でも毎回その場で上書きする（`\x1b[<行>;1H` でカーソルを合わせ、`\x1b[2K` で消してから書く）
> - **端に達していて実際には動かないとき（先頭で↑／末尾で↓等）は、何も出力しない。**`move()` の先頭で `clampTop` 後の値が現在の `top` と同じなら、再描画・ステータス更新とも行わず即座に戻る
> `render()`／`move()` だけの変更で済み、`handleKey()`・`KeySource` は影響を受けない。

## 5. テスト方針

キー入力を伴う対話的な画面遷移は自動テストにしにくい。**切り分けて考える。**

- **自動テストにする**: 1 画面分の行数計算、`top` のクランプ（範囲外に動かそうとしても止まる）、`isTTY` が false のときにページングせず素通しする経路
- **手動確認にとどめる**: 実際のキー入力（`Space`・`Enter`・矢印・`PageUp`/`PageDown`・`q`）による画面遷移、`CONIN$` が開けること自体、日本語を含む長文での表示崩れの有無、**Bun での `_kbhit`/`_getch` によるキー入力（拡張キーのデコードを含む）**

> [!NOTE]
> <strong>自動テストの構造上の限界。</strong>自動テストは `spawnSync` で標準出力をパイプに捕まえるため `process.stdout.isTTY` が常に `false` になり、キー入力を読む経路（`openNodeKeySource`／`openBunKeySource`）そのものに一度も到達しない。`bun:ffi` での `dlopen`・`_kbhit()` 呼び出しが例外を出さないこと（標準入力をパイプで埋めた状態でも）は手元で個別に確認したが、これはテストスイートには組み込めておらず、実際のキー入力による画面遷移は利用者による実機確認が要る。

置き場は他ツールと同じ`tools/40_test/run-less-tests.ps1`（＋同名の cmd）。
