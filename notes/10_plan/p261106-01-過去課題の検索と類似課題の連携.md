理想の姿を先に決め、過去の課題も決定も全部新しい形へ移す。すべての記録が一意の id を持ち、1 か所に書いた関連を相互にたどれ、索引が横断して似たものを引く。決定番号は全面的に振り直し、本文の旧番号も書き換える。

## 2. 作るもの

### 索引 (144-A)

- **置き場は `notes/40_issues/_index.sqlite`**。`_` 始まりなので Git 管理外。**捨てても、課題のファイルから作り直せる**
- **持つもの**: 課題と決定の id ・ 件名 ・ 状態 ・ グループ ・ 本文 ・ `refs` と `related`
- **更新は、必要になったとき**。ファイルの更新日時と内容の指紋を見て、変わった分だけ作り直す。索引が壊れていたら、全件から作り直す
- **SQLite の大原則を守る** (`-wal` ・ `-shm` は 3 つ一組で扱う。開いたら閉じる)。**捨てるときも 3 つまとめて**
- **全文検索の方式 (FTS5 の trigram か、別の方法か) は、まだ確かめていない**。node と bun の両方で使えるかを実測してから決める

### 類似課題の提示と相互リンク (145-A ・ 146-A)

- **`issue new` が、似た過去の課題を数件提示する**。提示するだけで、自動では何も書かない
- **`issue similar <id>` を足す** (名前は仕様のときに案を出す)。似た課題を、近い順に出す
- **似ているかどうかの判定は、まず簡単な方法 (語の重なり) で作り、このプロジェクトの課題で、人が見て合うかを測ってから**、別の方法を足すか決める。**精度は、まだ測っていない**
- **リンクは `related` に書く** (利用者が選んだものだけ)。**相互にたどれる**ように、逆向きは索引から出す。`issue show` が「この課題を指している課題」も表示する
- **横断 (別プロジェクトとの結びつき) は、フェーズ 5** (146-A)。`project_id` が付いた id で指し、名簿と承認が要る

### 関連の書き場所と見え方 (148-A 拡張 ・ 155-A ・ 156-A)

- **原則**: 順方向だけをファイルに書き、逆向きは生成のときに計算する。同じ関係を両側に書かない (片側が古くなるのを防ぎ、別プロジェクトのファイルを直さずに済む)

| 記録 | 関連を書けるか | 書く場所 |
|---|---|---|
| 課題 | 書ける | 課題のファイルの `refs` (計画 ・ 調査 ・ 構想を指す。既存) と `related` (似た課題を指す。新設) |
| 決定 | 書ける | 決定のファイルの `refs` (課題 ・ 計画 ・ 調査を指す) と `supersedes` (置き換えた決定)。親は id から分かる (152-A) |
| 計画 ・ 調査 | **書かない** (指される対象になるだけ) | HTML で、本文は書き換えない (共通ルール「計画との関係」)。課題 ・ 決定が指し、逆向き (「この計画を指す課題 ・ 決定」) を生成して出す |

- **計画 ・ 調査の本文にある `<a href>` と課題番号 (`i…`) は、索引が読み取り専用で拾う案** (書き換えない)。拾う精度は未測定
- **課題のカード (`_issues.html`)**: 「関連」(その課題が書いた `related`) ・ 「この課題を指している」(逆向き。課題 ・ 決定) ・ 「この課題から出た決定」(親がこの課題の決定) を並べ、同じ HTML の中のアンカーで飛べる。**決定のカード**は、親 ・ 関連する課題や計画 ・ 置き換えた決定 ・ 置き換えられた決定を出す
- **`issue show <id>`** が、同じ内容を文字で出す (`--json` でも)。計画 ・ 調査の id を渡すと、「この計画を指す課題 ・ 決定」が出る
- **別プロジェクト**は `:名前:id` で書き、文字だけを出す。リンクにしない。逆向きは出せない (相手のファイルを読めない)。全プロジェクトを 1 枚にまとめるフェーズ 5 の集計ページの中だけは出せる
- **`related` に種類を持たない** (155-A)。`related` を両側に書いても、表示は 1 つにまとめる (警告にしない)
- **壊れた参照は警告** (156-A)。同じプロジェクトの中で指す先が無いとき。別プロジェクトの参照は検査しない。決定の連番の重複は `duplicate` で止める (152-A)
- **id は変えない**ので、親が割れる ・ まとまる ・ プロジェクトが改名されても、書いた参照は切れない (改名は `legacy_names`。154-A)。生成は毎回全ファイルを読み直せ、索引は速くするためだけで、無くても動く
- **まだ確かめていないこと**: 既存の `refs` の値の区切り (`related` と揃える。実装のときに確かめる)。本文のリンクを拾う精度

### 決定の記録 (147-A)

- **置き場は `notes/40_issues/decisions/`** (1 決定 1 ファイル。名前は `<id>-件名.md`)。**id は、親の番号 + `-d` + 連番** (152-A。例: 課題 `i261103-01` の 1 つ目の決定は `i261103-01-d1`、計画 `p261103-01` の 96 番目は `p261103-01-d96`)。**親は、その決定を採った課題・計画・調査**。いまも、課題に紐づく計画・調査は課題の `i` 番号を流用しており、それを決定へ広げる
- **この形の利点**: 親の番号がすでに一意なので、プロジェクトの全体で番号を割り当てる必要が無い。`1-A` が課題ごとに何度出ても、親が付くので別物になる。**連番は親の中だけで数える**
- **連番の重複を防ぐ**: **同じ PC で、同じ親へ同時に決定を足す場合は、課題と同じ予約 (`_lock/<id>/`。`mkdir` の排他) を使う**。別の PC やクラウドで同じ親に同時に足したときは、予約が届かないので、`issue check` の `duplicate` が後から止める (課題と同じ限界)
- **親が無い決定** (会話だけで決めたもの等): 人が親を決める。本当に親が無ければ、先に課題を立てる (判断が要ることは課題に残す、という基準と同じ)。**複数の課題にまたがる決定**は、主になる親を 1 つ選び、残りは関連 (148-A) に書く。**親の課題が割れる・まとまっても、決定の id は変えない**
- **ファイル名に `:` は使えない** (Windows)。`-` でつなぐ。**プロジェクトをまたぐ参照は、プロジェクトの id をコロンで囲んで書く** (153-A。例: `:ai-agent-manager:i260924-02-d1`)。chat の名乗り (`:ai-agent-tools:`) と同じ形で、別のプロジェクトの id の前方一致にならない。**コロンは、本文 ・ `refs` ・ `related` ・ `legacy_ids` ・ 画面の表示にだけ出る**。ファイル名と `project-id.txt` の中身には出ない
- **課題の先頭の情報 (meta) は、値がコロンで始まっても壊れない**。`meta.ts` は YAML ではなく `キー: 値` の行を読む (行頭の `キー:` のあとの、最初の空白から行末までが値)。コードを読んで確かめた。実際に `refs: :ai-agent-manager:i260924-02` を通すテストは、実装のときに足す
- **参照に書くプロジェクトの名前 (154-A)**: 現在の `items/project-id.txt` の `project_id` は 32 桁の乱数で、人が読めない。**参照には、プロジェクトのフォルダ名を書く**。`project-id.txt` に `name: <フォルダ名>` を足し (`schema` を 2 に上げる案。実装のときに決める)、乱数の `project_id` は内部の安定した識別に残す。**改名したときは、旧名を `legacy_names` に残す**。索引が、旧名の参照も新しい名前へ引き当てる
- **持つ項目**: 問い ・ 案 A/B/C (恒久か暫定か、1 行の理由) ・ 選んだ案 ・ 決めた日 ・ 参照する課題と計画 ・ 置き換えた決定 ・ 親の番号 ・ `legacy_ids`
- **チャットでは、id と説明を添えて聞く** (`p261106-01-d3 (決定の id の形)-A`)
- **過去の番号 (`96-A` ・ `121-C` ・ `137-A` 等) も、全面的に振り直す** (149-A)。旧番号は、決定のファイルの `legacy_ids` 欄 (`:プロジェクト id:旧番号` の形。例: `:ai-agent-manager:4-A`) に残す。チャットや外部の参照を引くため、本文を書き換えたあとも消さない。本文の旧番号の書き換えは、第 3 章
- **決定も索引に入れる**。似た過去の決定を、課題と同じ道具で引ける
- **共通ルールの書き換えが 2 件要る**。「複数の解決案がある場合の対応」(番号の形と記録先) と、「計画との関係」(本文の旧番号の書き換えを、例外にする。150-B)。**ツールの公開後に、1 つずつ差分を出して指示を待つ**

### 旧番号で書かれた過去の資料 (150-B)

- **決定を新しい id に振り直したあと、計画・調査の本文にある旧番号を、機械で新しい id に書き換える**。本文を読むだけで、新しい id が分かる (新旧が 1 つの体系になる)。**親は、旧番号が書かれていた資料の番号** (例: 計画 `p261103-01` に書かれた `96-A` は `p261103-01-d96`)。**親が 1 つに決まる所だけ置き換える**ので、`1-A` が別の課題・計画で何度出てきても取り違えない
- **これは、共通ルール「計画との関係」(計画の本文を書き換えない) の例外**。書き換えの案を差分で出し、指示を待つ。ツールの公開の後
- **誤置換を防ぐ**: ① 対応表 (旧番号 → 新しい id) に載る番号だけを置き換える。② 短い番号 (`1-A` 等) は、プロジェクトの中で 1 つに決まる所だけを置き換え、あいまいなものは置き換えずに一覧に出して、人が決める。③ 書き換える前に `--dry-run` で、置換する全箇所を一覧にする。④ Git の差分を人が見てから確定する。⑤ HTML を書き換えたら、html2md で Markdown も作り直し、両方がそろうことを確かめる
- **他プロジェクトの本文は、そのプロジェクトのセッションが実行する** (他プロジェクトのファイルは直さない)
- **旧番号の単位は、プロジェクトごとに違う**。ai-agent-tools は計画をまたぐ連番 (96〜142)、ai-agent-manager は計画の表の通し番号 (1〜11) と、課題の末尾の `決定: 1-A` (指摘の一覧の番号。それぞれ別の課題に 1 回ずつ出る) だった。**どちらも「書かれていた資料」を親にし、番号は親の中の連番に振り直す** (旧番号は `legacy_ids` に残る)。**ほかのプロジェクトの単位は、読むまで分からない**ので、`--dry-run` の一覧で先に確かめる
- **置換が正しいかは、読み違いが 1 件でも出ても、例外が出ず、静かに本文が変わる点が最大の危険**。対応表の突き合わせと差分の確認を省かない

### 会話の記録からの決定の抽出 (151-B)

- **入力は、各プロジェクトの `etc/history/jsonl/`**。**Git 管理外**なので、共通ルール「`.gitignore` で除外されたファイルは原則として読まない」に触れる。**プロジェクトごとに、利用者の許可が要る**
- **会話の中身を読む作業**。AI が候補を抽出し、人が確認する。**抽出した決定にも、機密情報のマスキング (個人名 ・ フルパス) を適用する**
- **記録が大きい** (100 MB を超えるものがある)。[JSONL 二分探索ツール 計画](p261103-02-jsonl二分探索ツール.md)が使える見込みだが、まだ確かめていない
- **抽出した決定の元は、`source` 欄に書く** (会話の記録の、セッションと時刻)

## 4. 進め方とリスク

### フェーズ (案。承認をいただくまで実装しない)

1. **このプロジェクトの済み 69 件を移す** (最初の測定で 94 件と見込んでいたが、読み取りで 69 件と分かった)。`issue migrate` の最初の形を、ここで作り、旧 HTML と件数を突き合わせる
2. **索引**。作る・更新する・作り直す。node と bun で通す
3. **検索と類似**。`issue search` を索引へ移し、`issue similar` と `issue new` の提示を作る。精度は、このプロジェクトで測る
4. **相互リンク**。`related` と、逆向きの表示
5. **決定の記録**。`decisions/` と、操作 (名前は仕様のときに案を出す)。このプロジェクトの過去の決定を、資料 (計画の「決めること」の表 ・ 調査) から全件移す (149-A)。**読めないものは「未判定」に出し、人が決める**
6. **会話の記録からの抽出** (151-B)。このプロジェクトの `etc/history/jsonl/` を、利用者の許可のもとで読み、資料に無い決定を拾う
7. **本文の旧番号の書き換え** (150-B)。共通ルールの例外を作る書き換えの指示を受けてから。`--dry-run` と差分の確認を通す
8. **ほかのプロジェクトへ** ([各プロジェクトの課題の移行 計画](p261105-01-各プロジェクトの課題の移行.md)のフェーズ) と、横断 (フェーズ 5)

各フェーズは、**テストを先に書き (❌Red)、実装して通し (✅Green)**、node と bun の両方で全件を通してから次へ進む。詳細仕様 (`notes/50_spec/`) は、実装のたびに現在の姿へ直す。

### リスクと、まだ確かめていないこと

- **約 740 件のうち、読めない書き方がどれだけあるか**: 未測定。`--dry-run` で先に数える
- **類似の判定の精度**: 未測定。簡単な方法で足りるかは、このプロジェクトの課題で人が見て確かめる
- **全文検索の方式と、node ・ bun での動作**: 未確認
- **別プロジェクトの課題を横断で引く承認の形**: 未決定 (フェーズ 5)
- **決定番号の旧番号の写し**: 計画の本文には、旧番号が残る。引けるのは、決定のファイルに写したものだけ
- **共通ルールの書き換え** (課題の管理 ・ 複数の解決案がある場合の対応 ・ 計画との関係): ツールの公開の後。1 つずつ差分を出して指示を待つ
- **決定の件数**: 未測定。資料に残る分と、会話の記録にだけある分の割合も分からない
- **会話の記録を読む許可**: プロジェクトごとに要る。許可が出ないプロジェクトの決定は、資料にある分だけになる
- **動いていないプロジェクト**: 最後まで旧形式のまま残る可能性がある。「完全」は、移したプロジェクトの中での完全
