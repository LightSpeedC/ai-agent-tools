# 過去課題の検索と類似課題の連携 計画 (ai-agent-tools)

理想の姿を先に決め、過去の課題も決定も全部新しい形へ移す。すべての記録が一意の id を持ち、1 か所に書いた関連を相互にたどれ、索引が横断して似たものを引く。決定番号は全面的に振り直し、本文の旧番号も書き換える。

> 📅 作成: 2026-11-06 / 更新: 2026-11-06

[^^](../../README.md)

**対象 ・ 入力 ・ 出力**: 対象は `issue` ツール ([課題管理ツール 計画](p261103-01-課題管理ツール.md)) と、各プロジェクトの課題の移行 ([各プロジェクトの課題の移行 計画](p261105-01-各プロジェクトの課題の移行.md))。入力は、各プロジェクトの課題 (**済みを含む**) と、これまで選択肢ルールで採ってきた決定。出力は、`items/done/` へ移した済みの課題、検索用の索引 (`notes/40_issues/_index.sqlite`。Git 管理外)、`decisions/` の決定の記録。**この計画は、利用者が 2026-11-06 に決めた 143〜151 を書き残すもの。実装は、各項目の承認をいただいてから。** 決定の入力には、計画・調査の本文に加えて、**会話の記録 (JSONL)** も含む (151-B)。

> [!IMPORTANT]
> **前の計画との関係**: [各プロジェクトの課題の移行 計画](p261105-01-各プロジェクトの課題の移行.md)は**未・着手だけを移す** (96-A) 前提で書いてある。**143-A で、その前提を改める** (済みも移す)。計画は書き換えない (共通ルール「計画との関係」)。**食い違う箇所は、この計画が新しい。**「121-C (SQLite のキャッシュを持たない)」も、144-A で改める (**正本は変えず、索引だけを持つ**)。

## 1. 決まったこと

理由は、過去の課題も検索し、似た課題で連携するため (DB 化したかった理由)。済みを引けないと、類似の検索も連携もできない。

| 番号 | 決めたこと | 改める前の決定 |
|---|---|---|
| 143-A (済みの課題も移す) | 済みも `items/done/` へ移す。旧 HTML は `issues-legacy.html` として残し、突き合わせに使う | 96-A (未・着手だけを移す) |
| 144-A (正本は Markdown、索引だけ DB) | 1 課題 1 ファイルは変えず、検索用の索引を SQLite で派生させる。作り直せるもの。Git 管理外 (`_` 始まり) | 121-C (SQLite のキャッシュを持たない) |
| 145-A (立てるときの提示と、横断の結びつき) | 課題を立てるとき、似た過去の課題を提示する。別プロジェクトの課題とも結びつける。**相互にリンクする** | ― |
| 146-A (作る順序) | 1 つのプロジェクトの中から先に作り、横断はフェーズ 5 で足す | ― |
| 147-A (決定番号の持ち方) | 決定を、課題と同じ仕組みで 1 件 1 ファイルにする。id は `d` + yymmdd + `-` + 36 進 2 桁 | プロジェクトごとの整数の連番 (`137-A` 等) |
| 148-A 拡張 (関連は 1 か所にだけ書く) | 決定のファイルにだけ関連する課題を書き、逆向きは索引と生成で出す。**拡張: 課題・決定・計画・調査のすべてに、同じ方式を使う** (拡張の読み方は、利用者の確認待ち) | ― |
| 149-A 拡張 (過去の決定も全面的に移す) | 過去の決定も全件を新しい形へ移し、番号は全面的に振り直す。旧番号は `legacy_ids` に残す | ― |
| 150-B (本文の旧番号を書き換える) | 計画・調査の本文にある旧番号を、機械で新しい id に書き換える | 共通ルール「計画との関係」(計画の本文を書き換えない) |
| 151-B (会話の記録からも拾う) | 資料に残っていない決定を、会話の記録 (JSONL) からも拾う | ― |

> **相互リンクの作り方 (見込み)**: 片方の課題にだけ `related` を書き、**逆向きのリンクは索引から導く**。両側に書くと、別プロジェクトのファイルを直すことになり (共通ルール「プロジェクトフォルダ外へのアクセス」)、片側だけ古くなる。この方式は 148-A で決まった。

## 2. 作るもの

### 索引 (144-A)

- **置き場は `notes/40_issues/_index.sqlite`**。`_` 始まりなので Git 管理外。**捨てても、課題のファイルから作り直せる**
- **持つもの**: 課題と決定の id ・ 件名 ・ 状態 ・ グループ ・ 本文 ・ `refs` と `related`
- **更新は、必要になったとき**。ファイルの更新日時と内容の指紋を見て、変わった分だけ作り直す。索引が壊れていたら、全件から作り直す
- **SQLite の大原則を守る** (`-wal` ・ `-shm` は 3 つ一組で扱う。開いたら閉じる)。**捨てるときも 3 つまとめて**
- **全文検索の方式 (FTS5 の trigram か、別の方法か) は、まだ確かめていない**。node と bun の両方で使えるかを実測してから決める

### 類似課題の提示と相互リンク (145-A ・ 146-A)

- **`issue new` が、似た過去の課題を数件提示する**。提示するだけで、自動では何も書かない
- **`issue similar <id>` を足す** (名前は仕様のときに案を出す)。似た課題を、近い順に出す
- **似ているかどうかの判定は、まず簡単な方法 (語の重なり) で作り、このプロジェクトの課題で、人が見て合うかを測ってから**、別の方法を足すか決める。**精度は、まだ測っていない**
- **リンクは `related` に書く** (利用者が選んだものだけ)。**相互にたどれる**ように、逆向きは索引から出す。`issue show` が「この課題を指している課題」も表示する
- **横断 (別プロジェクトとの結びつき) は、フェーズ 5** (146-A)。`project_id` が付いた id で指し、名簿と承認が要る

### 決定の記録 (147-A)

- **置き場は `notes/40_issues/decisions/`** (1 決定 1 ファイル)。id は `d261106-01` の形で、課題の `i` と同じ採り方 (`_lock/` で同じ PC の重複を避け、別の PC の重複は `issue check` が見つける)
- **持つ項目**: 問い ・ 案 A/B/C (恒久か暫定か、1 行の理由) ・ 選んだ案 ・ 決めた日 ・ 参照する課題と計画 ・ 置き換えた決定 ・ 旧番号
- **チャットでは、id と説明を添えて聞く** (`d261106-01 (決定番号の持ち方)-A`)
- **過去の番号 (`96-A` ・ `121-C` ・ `137-A` 等) も、全面的に振り直す** (149-A)。旧番号は、決定のファイルの `legacy_ids` 欄 (`プロジェクト id` + 旧番号) に残す。チャットや外部の参照を引くため、本文を書き換えたあとも消さない。本文の旧番号の書き換えは、第 3 章
- **決定も索引に入れる**。似た過去の決定を、課題と同じ道具で引ける
- **共通ルールの書き換えが 2 件要る**。「複数の解決案がある場合の対応」(番号の形と記録先) と、「計画との関係」(本文の旧番号の書き換えを、例外にする。150-B)。**ツールの公開後に、1 つずつ差分を出して指示を待つ**

## 3. 移行計画への影響

[各プロジェクトの課題の移行 計画](p261105-01-各プロジェクトの課題の移行.md)のうち、143-A で変わる点。それ以外 (各プロジェクトのセッションが移す・別の PC は 1 台で移す・順序) は、そのまま。

| 項目 | 前の計画 | この計画での扱い |
|---|---|---|
| 移す範囲 | 未・着手だけ (96-A) | 済みも `items/done/` へ。このプロジェクトの済み 94 件も、移す必要がある (未実施) |
| `issue migrate` | 未・着手を移す | 済みも移す。**読めなかった課題は、推測せず「読めなかった」に出す** (前の計画と同じ)。**約 740 件の書き方の違いを、先に `--dry-run` で数える** |
| 旧 HTML | `issues-legacy.html` へ改名して残す (127-A) | 同じ。ただし済みは新しい形にもあるので、**旧 HTML は、突き合わせ (写し間違いの確認) の相手** |
| 0 件のプロジェクト | 次に課題を立てるとき | 済みがあれば、**0 件でも検索の材料になる**。移す時期は、この計画では決めない (前の計画の 139 のまま) |
| 量 | 小さい (見込み) | **大きくなる**。件数は約 740 件。読み方の測定は、まだしていない |

### 旧番号で書かれた過去の資料 (150-B)

- **決定を新しい id に振り直したあと、計画・調査の本文にある旧番号を、機械で新しい id に書き換える**。本文を読むだけで、新しい id が分かる (新旧が 1 つの体系になる)
- **これは、共通ルール「計画との関係」(計画の本文を書き換えない) の例外**。書き換えの案を差分で出し、指示を待つ。ツールの公開の後
- **誤置換を防ぐ**: ① 対応表 (旧番号 → 新しい id) に載る番号だけを置き換える。② 短い番号 (`1-A` 等) は、プロジェクトの中で 1 つに決まる所だけを置き換え、あいまいなものは置き換えずに一覧に出して、人が決める。③ 書き換える前に `--dry-run` で、置換する全箇所を一覧にする。④ Git の差分を人が見てから確定する。⑤ HTML を書き換えたら、html2md で Markdown も作り直し、両方がそろうことを確かめる
- **他プロジェクトの本文は、そのプロジェクトのセッションが実行する** (他プロジェクトのファイルは直さない)
- **置換が正しいかは、読み違いが 1 件でも出ても、例外が出ず、静かに本文が変わる点が最大の危険**。対応表の突き合わせと差分の確認を省かない

### 会話の記録からの決定の抽出 (151-B)

- **入力は、各プロジェクトの `etc/history/jsonl/`**。**Git 管理外**なので、共通ルール「`.gitignore` で除外されたファイルは原則として読まない」に触れる。**プロジェクトごとに、利用者の許可が要る**
- **会話の中身を読む作業**。AI が候補を抽出し、人が確認する。**抽出した決定にも、機密情報のマスキング (個人名 ・ フルパス) を適用する**
- **記録が大きい** (100 MB を超えるものがある)。[JSONL 二分探索ツール 計画](p261103-02-jsonl二分探索ツール.md)が使える見込みだが、まだ確かめていない
- **抽出した決定の元は、`source` 欄に書く** (会話の記録の、セッションと時刻)

## 4. 進め方とリスク

### フェーズ (案。承認をいただくまで実装しない)

1. **このプロジェクトの済み 94 件を移す**。`issue migrate` の最初の形を、ここで作り、旧 HTML と件数を突き合わせる
2. **索引**。作る・更新する・作り直す。node と bun で通す
3. **検索と類似**。`issue search` を索引へ移し、`issue similar` と `issue new` の提示を作る。精度は、このプロジェクトで測る
4. **相互リンク**。`related` と、逆向きの表示
5. **決定の記録**。`decisions/` と、操作 (名前は仕様のときに案を出す)。このプロジェクトの過去の決定を、資料 (計画の「決めること」の表 ・ 調査) から全件移す (149-A)。**読めないものは「未判定」に出し、人が決める**
6. **会話の記録からの抽出** (151-B)。このプロジェクトの `etc/history/jsonl/` を、利用者の許可のもとで読み、資料に無い決定を拾う
7. **本文の旧番号の書き換え** (150-B)。共通ルールの例外を作る書き換えの指示を受けてから。`--dry-run` と差分の確認を通す
8. **ほかのプロジェクトへ** ([各プロジェクトの課題の移行 計画](p261105-01-各プロジェクトの課題の移行.md)のフェーズ) と、横断 (フェーズ 5)

各フェーズは、**テストを先に書き (❌Red)、実装して通し (✅Green)**、node と bun の両方で全件を通してから次へ進む。詳細仕様 (`notes/50_spec/`) は、実装のたびに現在の姿へ直す。

### リスクと、まだ確かめていないこと

- **約 740 件のうち、読めない書き方がどれだけあるか**: 未測定。`--dry-run` で先に数える
- **類似の判定の精度**: 未測定。簡単な方法で足りるかは、このプロジェクトの課題で人が見て確かめる
- **全文検索の方式と、node ・ bun での動作**: 未確認
- **別プロジェクトの課題を横断で引く承認の形**: 未決定 (フェーズ 5)
- **決定番号の旧番号の写し**: 計画の本文には、旧番号が残る。引けるのは、決定のファイルに写したものだけ
- **共通ルールの書き換え** (課題の管理 ・ 複数の解決案がある場合の対応 ・ 計画との関係): ツールの公開の後。1 つずつ差分を出して指示を待つ
- **決定の件数**: 未測定。資料に残る分と、会話の記録にだけある分の割合も分からない
- **会話の記録を読む許可**: プロジェクトごとに要る。許可が出ないプロジェクトの決定は、資料にある分だけになる
- **動いていないプロジェクト**: 最後まで旧形式のまま残る可能性がある。「完全」は、移したプロジェクトの中での完全
