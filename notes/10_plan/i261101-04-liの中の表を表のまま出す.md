# li の中の表を表のまま出す 計画 (i261101-04)

html2md は、`<li>` の中の `<table>` を 1 行の文字に潰している。字下げした Markdown の表として出し、GitHub で表として読めるようにする。

> 📅 作成: 2026-11-07 / 更新: 2026-11-07

[^^](../../README.md)

**対象 ・ 入力 ・ 出力**: 対象は ai-agent-tools の html2md (`src/html2md/table.ts` の `convertList`)。入力は、`<li>` の中に `<table>` を持つ HTML。出力は、その li の下に字下げした Markdown の表を持つ `.md`。

> [!IMPORTANT]
> <strong>実装した (2026-11-07、計画の承認のあと)。</strong>計画どおり。試験 `table-in-li` を足し、`strong-cell-in-li` の期待値を表の形に直した。どちらも先に❌Red を見てから、✅Green にした。期待値の `.md` を GitHub の Markdown API で描かせ、表が 6 つ、箇条が崩れずに描かれることを確かめた。このプロジェクトで html2md を流したところ、変わった `.md` は 0 件 (li の中に表を持つ資料が無い)。<strong>計画に足した点が 1 つ。</strong>一番外の箇条の末尾にできる空の行は落とす (箇条の後の空の行は、呼び出し側が置くため)。

## 1. 決めたことと、確かめたこと

課題 `i261101-04` の「li の中の表を、1 行に潰さず表のまま出すか」について、2026-11-07 に利用者が B (表のまま出す) を選んだ。不具合 (`****` が残る) は、688fbf5 ですでに直っている。この計画は、その先の見た目の改善になる。

### GitHub の描き方 (2026-11-07 に実測)

見本の Markdown を、check-markdown と GitHub の Markdown API (`gfm`) に通した。次の 3 つの形は、どれも `<li>` の中に `<table>` として描かれた。check-markdown も問題なしだった。

| 形 | 表の字下げ | 結果 |
|---|---|---|
| 箇条書き (`- `) の中。太字のセルが隣り合う (元の不具合の形) | 2 文字 | ✅ 表になる。`<strong>` はセルごとに分かれる |
| 番号付き (`1. `) の中 | 3 文字 | ✅ 表になる |
| 入れ子の箇条 (外側から 2 文字、内側の記号のあと 2 文字) の中 | 4 文字 | ✅ 表になる |

```markdown
- 項目 1 の文

  | 名前 | 結果 |
  |---|---|
  | **node ・ Rust の 2 本** | **☑** |
```

> [!IMPORTANT]
> <strong>表を持つ箇条は、段落の間が空く。</strong>表の前に空の行が要るため、GitHub はその箇条全体を「ゆるい箇条」として描き、各項目を `<p>` で包む (実測の HTML で確かめた)。表を持たない箇条は、いまと変わらない。空の行を置かずに表を書く形は、GFM では表として読まれないので、選ばない。

## 2. 変える動き

- <strong>li の中身を、表の前 ・ 表 ・ 表の後に分ける。</strong>入れ子の `ul` ・ `ol` を取り出す処理 (いまの `convertList`) と同じ形で、`<table>` を取り出す。`md-skip` の表は、いまと同じく出さない
- **表の前の文**は、いまと同じく、記号の後ろの 1 行にする
- **表**は、いまの `convertTable` で Markdown の表にし、各行の頭に字下げを付ける。字下げは「その箇条の字下げ (`4 × depth`) ＋ 記号の幅 (`- ` は 2、`n. ` は番号の桁数 ＋ 2)」。表の前後に空の行を置く
- **表の後の文**が残れば、同じ字下げの段落として、表の後に空の行を挟んで出す
- **li の中に表が 2 つ以上あれば**、順に同じ扱いで出す
- **表の中の表** (セルの中の `<table>`) は、いまと同じく潰す。この計画の範囲に入れない
- li に表が無いときの出力は、**1 バイトも変えない** (試験で確かめる)

688fbf5 の直し (`</td>` ・ `</th>` を空白にする) は残す。表の中の表など、潰す道が残るため。

## 3. 試験

**先に書き、落ちるのを見てから実装する** (❌Red → ✅Green)。`tests/cases/` に、期待値を手で書いたケースを足す。

| ケース | 確かめること |
|---|---|
| `strong-cell-in-li` (既存) | 期待値を、表のまま出す形に書き換える。`****` が出ないことは、そのまま確かめる |
| `table-in-li` (新規) | `ul` ・ `ol` (番号が 2 桁になる 10 番目の項目を含む) ・ 入れ子の中の表。表の前後の文。1 つの li に表が 2 つ。`md-skip` の表 |
| 既存の全ケース | li に表を持たないケースの出力が変わらないこと |

- 新しいケースの期待値の `.md` を、**check-markdown に通し**、GitHub で表として描かれることを確かめる (手で書いた期待値が、GitHub で正しいことの裏付け)
- bun と node の両方で通す (ローカルルール第 3 章「優先するランチャーがあると、もう一方は 1 ケースも通らない」)

### ほかのプロジェクトへの影響

- li の中に表を持つ HTML がある所だけ、次に html2md を流したときに `.md` が変わる。見つかっているのは、ai-chat-lite の `issues-archive.html` の 1 か所
- 変わった箇条は、段落の間が空く (第 1 章の注意)。崩れではない

### まだ確かめていないこと

- li の中に表と `<pre>` の両方があるときの並び (いまは `<pre>` も 1 行に潰している。この計画では `<pre>` の扱いは変えない)
