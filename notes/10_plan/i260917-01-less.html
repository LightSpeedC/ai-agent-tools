UTF-8 出力を DOS の more で受けると文字化けする問題を、UTF-8 セーフなページャーで解決する。

背景

html2md・convert-encoding・text 等の出力を DOS の more コマンドへパイプしてページングすると、UTF-8 の出力が CP932 として読まれて文字化けする。more は Windows 標準の .NET／PowerShell 系が持つ「出力コードページ問題」の受け手側で、課題 i260912-06 と根が同じ。

UTF-8 セーフなページャー（less）を新設する。

実装方式（決定済み）

TypeScript（bun 優先・node 予備）にする。他ツール（html2md・text・convert-encoding・psh・check-*）と同じ理由で、Node・Bun は常に UTF-8 で出すため。C#／PowerShell を選ぶと、この課題そのものを再び踏む。

置き場・呼び方は他ツールと同じ形に揃える。

ファイル役割
lesssh 入口。bun を優先、無ければ node で src/less/main.ts を実行
less.cmdcmd 入口。同じ振り分け
src/less/main.ts本体
src/less/bun-ffi.d.ts型チェック専用の最小限のアンビエント宣言（Bun・bun:ffi）。下記「Bun では動かない」を参照

機能範囲（決定）

A（最小限のページング）を採用。あわせて上下スクロールを追加する。2026-09-17 決定。

  • q — 終了
  • Space／PageDown — 画面の高さの 3/4 くらい下
  • Enter／↓ — 1 行下
  • ↑ — 1 行上
  • PageUp — 画面の高さの 3/4 くらい上

検索・行番号・g/G（先頭・末尾へ）は今回持たない（B の残り）。標準出力がパイプ／端末でない（リダイレクト先がファイル等）ときは、ページングせずそのまま流す。

済2026-09-19、利用者の指示で移動量を変更。Space は当初「1画面分」だったが、PageDown と同じ「画面の高さの 3/4 くらい」に統一。PageUp／PageDown の移動量も 2/3 → 3/4 に変更。あわせてステータス行にキー一覧を追加（下記「詳細仕様」を参照）。

暫定と恒久: 検索・行番号等、今回見送った機能は、実際に使ってみて不足を感じたら個別に足す（一度に全部作らない）。

詳細仕様

入力

  • 標準入力からパイプで受け取る（html2md | less の形）
  • ファイル引数は今回持たない。まずパイプ専用（用途は「他コマンドの出力を見る」ため）
  • 済2026-09-21、利用者の指示で追加。入力の文字コードは convert-encoding・text と同じ判定（src/lib/detector.ts の detect()）で自動判定する（UTF-8・SJIS・UTF-16 等）。決められない（両方妥当な非 ASCII を含む等）ときは UTF-8 として読む。テスト（bun・node とも10件成功）・型チェック・全体テストは確認済み

キー入力の取得元（上下スクロール追加で新たに要る論点）

cmd | less の形では、process.stdin はデータそのもの（パイプ）で埋まっており、キー入力には使えない。先頭を1画面表示するだけの案（Space/Enter/qだけ）ならデータを読み終えた後に process.stdin を使い回せたが、上下スクロールは表示中も随時キーを受けるため、データ用のストリームとキー入力用のストリームを分ける必要がある。

取得方法が Node と Bun で異なる（下記の落とし穴を参照）ため、KeySource（onData／close の2つだけを持つ）という共通の形に抽象化し、page() 側はどちらの処理系かを意識しない。

interface KeySource {
	onData(cb: (chunk: string) => void): void;
	close(): void;
}

開けなければ（コンソールが無い環境）、スクロール操作を諦めて素通しにする（下記「開けないとき」）。

実装時に踏んだ落とし穴（1）。素の 'CONIN$' を渡すと、Node がカレントフォルダからの相対パス（例: N:\ai-agent-tools\CONIN$）として解決してしまい、ENOENT で失敗する（Bash・PowerShell 両方の実環境で実測）。Win32 のデバイス名前空間 \\.\ を前置すると正しく開け、isTTY も true になる。

実装時に踏んだ落とし穴（2）。isTTY が true を返しても、setRawMode が成功するとは限らない。読み取り専用（'r'）で CONIN$ を開くと、Node では setRawMode が EPERM で落ちる。Windows の SetConsoleMode は書き込みアクセスも要るため、'r+'（読み書き）で開く必要がある。この不具合は手動確認（isTTY が true になることだけ）をもって「動く」と判断してしまい、利用者が実際にパイプ経由で実行するまで見つからなかった。

Bun では 'r' ／ 'r+' ／ 'w+' ／ 'a+' のどのモードで開いても直らない。setRawMode が Node とは別のメッセージ（「TTY ではない」）で失敗し続ける（4モードとも実測）。Node は 'r+' ／ 'w+' でだけ成功しており、アクセス権の問題ではなく、Bun の Windows 向け node:tty 実装が、標準入出力（fd 0/1/2）以外の fd を raw mode 対応の TTY として扱わないという実装上の制約だと見られる（Bun の Issue 追跡でも Windows の Terminal/PTY 関連機能が未対応・制限ありと記載されている）。

回避策: node:tty を経由せず、MS-CRT（msvcrt.dll）の _kbhit / _getch を bun:ffi で直接呼ぶ。これらはコンソールを直接読む実装のため、標準入力がパイプで埋まっていても影響を受けない（echo ... | bun test.mjs の形で実測）。Win32 Console API（ReadConsoleInputW 等）を直接叩く方式も前例がある（bun-win32、外部パッケージとして公開されている）が、CreateFileW でハンドルを開き、SetConsoleMode を保存・復元し、INPUT_RECORD（共用体）をバイト列から自前でデコードする必要があり、実装量が大きい。_kbhit/_getch はコンソールのモード管理を CRT 側がやってくれるため、外部パッケージへの依存無しで数十行で済む。

const { dlopen, FFIType } = await import('bun:ffi');
const { symbols } = dlopen('msvcrt.dll', {
	_kbhit: { args: [], returns: FFIType.i32 },
	_getch: { args: [], returns: FFIType.i32 },
});

矢印・PageUp/Down は「拡張キー」で、_getch() が 0 か 0xE0 を返した後、もう一度 _getch() を呼ぶとスキャンコード（↑72／↓80／PgUp73／PgDn81）が来る（MS-CRT の昔からの仕様）。handleKey() が読める ANSI エスケープ列（'\x1b[A' 等）に変換してから渡すことで、Node 側と同じ解釈ロジックをそのまま使い回せる。

bun:ffi の型は bun-types を依存に追加せず、使う分だけ src/less/bun-ffi.d.ts に自前で宣言した（外部パッケージへの依存を増やさない方針に合わせた）。

実行時にどちらの処理系かを見分けるのは typeof Bun !== 'undefined'（Bun がグローバルに注入する Bun オブジェクトの有無で判定）。これがこのプロジェクトで初めて、シェルの入口ではなく main.ts 自身が実行時にランタイムを判断するコードになる（他ツールは入口スクリプトの command -v bun／where bun だけで振り分けており、本体は Node の API だけで両対応している）。

ページング

  • 標準入力を全部読み切ってから始める（戻りスクロールのため、全行をメモリに持つ）
  • process.stdout.rows で端末の行数を取り、1 画面分の行数を決める（取得できなければ 24 行）
  • 表示位置は「先頭からの行オフセット（top）」1 つで持つ。キー操作は top を動かして再描画するだけ
  • 再描画は画面クリア（\x1b[2J\x1b[H）してから top 〜 top+高さ を出す。最下行にステータス行を出す。2026-09-19、利用者の指示でキー一覧を含む形にした: -- less (NN%) q で終了 | Page Up | ↑ | ↓・Enter | Page Down・Space --（2026-09-19 に Space・Page Down から並び順を修正）
  • top は 0 〜 行数-画面高さ の範囲にクランプする
  • 標準出力が端末でない（process.stdout.isTTY が false）とき、または CONIN$ を開けないときは、ページングせずそのまま出力する

再描画のちらつき

実機確認で判明。それまでの render() は移動量の大小によらず、キーを押すたびに画面全体をクリアしてから毎回全部描き直していた。↓キー（1行スクロール）のように変化が小さいときでも画面全体が点滅する。

済2026-09-18、利用者の指示で下記の形に実装した（差分更新にする）。

  • 下方向（top が増える）は常にスクロール方式にする（↓・Enter・Space・PageDown のすべて）。scrollDown() がカーソルを最下行に置いてから、新しく見える行の数だけ改行＋テキストを出す。改行のたびに端末が自然に1行分スクロールする（既存の内容はそのまま上へ押し出される）ため、移動量が画面の高さを超えていても同じやり方で書ける
  • ↑（矢印、1行）だけスクロール方式にする。scrollUp() が \x1bM（Reverse Index）でカーソルを最上行に固定した状態から逆方向へ1行分スクロールし、最上行にできた空行へ新しく見える行を書く
  • PageUp は今までどおり全画面クリア＋再描画のままにする（move() に渡す strategy を 'redraw' にする）。Reverse Index を複数行分繰り返す形は端末依存の懸念があり、もともと大きく動くキーなので点滅も気にならない
  • ステータス行（画面最下行の -- less (NN%) --）は、スクロール方式でも writeStatus() が毎回その場で上書きする（\x1b[<行>;1H でカーソルを合わせ、\x1b[2K で消してから書く）
  • 端に達していて実際には動かないとき（先頭で↑／末尾で↓等）は、何も出力しない。move() の先頭で clampTop 後の値が現在の top と同じなら、再描画・ステータス更新とも行わず即座に戻る

render()／move() だけの変更で済み、handleKey()・KeySource は影響を受けない。tools/40_test/run-less-tests.ts（bun・node とも8件）と型チェックは通したが、実際の画面遷移（ちらつきが無くなったか、各キーの見た目）は自動化できないため、利用者による実機での確認が要る。

実装時に踏んだ落とし穴（3）: スクロール範囲を区切らないとスクロールしない

実機確認で判明。↓キー・Enter を押しても表示が進まず、ステータス行の％表示だけが増えた。原因は、画面が「コンテンツ h 行＋ステータス行 1 行」の計 h+1 行を使っているのに、scrollDown() は「コンテンツの最終行（h 行目）」にカーソルを置いて改行していた点。そこは端末にとって画面の最終行ではない（1行下にステータス行がある）ため、改行してもスクロールは起きず、カーソルがステータス行へ動いてそこへ新しい行のテキストを上書きしていた。

済2026-09-19 に修正。DECSTBM（\x1b[1;h r）でスクロール範囲をコンテンツ用の h 行だけに限定する（setScrollRegion()、ページング開始時に1回設定）。この範囲内でだけ改行・Reverse Index が正しくスクロールし、範囲外のステータス行は影響を受けない。終了時（finish()）に resetScrollRegion()（\x1b[r）で画面全体に戻す。

済あわせて、q で終了したときの画面クリアを無くした（利用者の指示）。ページャーの最後の表示をそのまま残し、カーソルをステータス行の下へ移して改行するだけにする。

実装時に踏んだ落とし穴（4）: スクロール範囲を区切っても、書き方次第でステータス行が残る

実機確認で判明。落とし穴（3）の修正後、Enter を押すとステータス行が消えずに残ったまま画面がスクロールしていった。原因は scrollDown() の書き方: 改行（\n）を先に出してからテキストを書いており、(1) 改行だけでは列が先頭に戻らない（\n は CR を含まない）ため、複数行分では列がずれる、(2) 書く前に行末までクリアしていないため、スクロールが確実に起きていない場合や、新しい行が前の内容より短い場合に文字が残る。

済2026-09-19、利用者の指示で修正。「行頭へ戻す（\r）→行末までクリア（\x1b[K）→テキストを書く→\r\nで次行へ」の順にする。スクロール範囲の最終行（h 行目）に最初に1回だけ位置決めした後は、各行を書くたびの \r\n で自動的に次の行の先頭（同じくスクロール範囲の最終行）へ戻るため、ループ内で毎回位置決めし直す必要はない。scrollUp() にも同じ理由で行頭復帰＋行末クリアを追加した。

済2026-09-19、150桁端末での実機確認で ↓・Enter とも乱れなく動くことを確認。

実装時に踏んだ落とし穴（8）: スクロール（LF）を書き込みの後にすると、書いたばかりの内容が1行押し上げられる

実機確認で判明。下方向へ動くたび、最下行に空行が1行できる。上方向（scrollUp）では起きない。原因は落とし穴（4）の修正で採った順序（「クリア→書く→\r\n」）そのもの: LF（スクロール）がテキストを書いた「後」に起きるため、書いたばかりの内容までスクロール範囲の中で1行分押し上げられ、最下行が空いたまま残る。scrollUp() は逆に「まず Reverse Index でスクロールしてから書く」順だったため、この問題が起きていなかった（実機で報告されるまで気づかなかった）。

済2026-09-19 に修正。scrollDown() も scrollUp() と同じ「スクロールを先に、書くのを後に」の順にする。各行を「\r\n（行頭へ戻して次行へ＝スクロール）→行末までクリア→テキスト」の順で書く。スクロールで生まれた空行に書き込むだけになるため、書いたばかりの内容が押し上げられることが無くなる。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済みだが、画面遷移の見た目そのものは自動化できないため、利用者による実機での再確認が要る。

PageUp もスクロール方式にする（機能追加）

済2026-09-19、利用者の指示で scrollUp() を複数行に対応させ、PageUp も全画面再描画（'redraw'）ではなくスクロール方式にした。画面の下寄りに来る行から先に書く（後から挿す行ほど上に押し出されるため、逆順で書くと最終的に上から正しい順に並ぶ）。move() の strategy 引数と 'redraw' 分岐、render() は今後また使う予定があるため残した（利用者の指示。既定値は 'scroll' にし、呼び出し側は省略できる）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済みだが、画面遷移の見た目そのものは自動化できないため、利用者による実機での確認が要る。

実装時に踏んだ落とし穴（5）: 初回表示・PageUp でステータス行が1行上にずれる

実機確認で判明。最初の表示、および PageUp（'redraw' 方式）のあと、ステータス行が画面の最下行ではなく下から2行目に出る。原因は落とし穴（4）と同種: render() がコンテンツを書き終えたあと、改行（\n）だけでステータス行へ移っていた。改行は列を先頭へ戻さないため、コンテンツの最終行の文字数ぶんカーソルが右にずれたまま次の行へ移り、そこから書いたステータス行の反転表示が桁あふれして自動折り返しを起こし、見た目上1行分ずれていた。

済2026-09-19 に修正。render() のステータス行書き込みを、絶対位置で書く writeStatus() に置き換えた（重複していたステータス行の組み立てロジックも一本化）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済みだが、画面遷移の見た目そのものは自動化できないため、利用者による実機での再確認が済むまで「済」にはしない。

実装時に踏んだ落とし穴（6）: Bun はコンソールの出力コードページを UTF-8 にしない

実機確認で判明。less -h | less で使い方の説明（全て日本語）が文字化けした（UTF-8 のバイト列が CP932 として解釈される典型的な化け方）。原因は、Node は Windows のコンソール出力コードページを自動的に UTF-8（65001）に設定するが、Bun はしないこと。less の対話ページングは bun 優先のため、これまでの実機確認（aichat -h 等）でも実は同じ問題を踏んでいたが、内容の大半が ASCII で CP932 と UTF-8 の解釈結果が同じだったため気づかれなかった。

済2026-09-19 に修正。Bun のキー入力設定（openBunKeySource()）の中で、bun:ffi から kernel32.dll の SetConsoleOutputCP(65001) を明示的に呼ぶ（_kbhit/_getch と同じ手法の延長）。失敗しても対話ページング自体は続ける（別の try/catch にする）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

実装時に踏んだ落とし穴（7）: ヘルプの桁揃えを手で数えたスペースで決め打ちしていた

実機確認で判明。↓・Enter（矢印・中点・英単語が混在するラベル）の行だけ、他の行と桁が揃っていなかった。原因は 手でスペースを数えて決め打ちしていたことで、ラベルの並び順を変えたときに数え直しを忘れた。加えて、↓・・・↑ の表示幅（この端末では全角＝2桁として描画される）を最初から正しく知らず、実機で試すまで分からなかった。

済2026-09-19 に修正。表示幅を計算する displayWidth()（ASCII・半角ｶﾀｶﾅは1桁、それ以外は2桁）と、それで桁を揃える pad() を実装し、Usage の組み立てをこれで行うようにした。ラベルの文字を今後変更しても自動的に桁が揃う。共通ルールにも「全角・半角混在のテキストを桁揃えするとき」を追記し、ai-chat-lite の public ルームへ周知した（他プロジェクトでも同じ不具合が起きないようにするため）。テスト（bun・node とも8件成功）・型チェック・全体テストは確認済み。

実装時に踏んだ落とし穴（8）: エスケープシーケンスの文字化け（調査中・原因は Bun ランタイム自体の可能性が高い）

2026-09-21、利用者から実機での報告: ときどき less 実行時にエスケープシーケンスの文字がそのまま表示される。2回目の実行では直る。psls claude.exe | less（psls が埋め込む太字・色付けのエスケープシーケンスを含む）で再現。

直った部分（済）

  • Bun は ENABLE_VIRTUAL_TERMINAL_PROCESSING（コンソールがエスケープシーケンスを解釈するモード）を自動で有効化しない。共通処理 src/lib/win-console.ts の enableWindowsConsoleVt() で明示的に有効化し、終了時に元へ戻すようにした（less・psls 両方で使う）
  • finish() が、コンソール状態を元へ戻す key.close() を、終了メッセージを書く out() より先に呼んでいたため、終了メッセージだけが化けていた。out() を先に呼ぶ順序に直した

済2026-09-21 に修正。上記2点は実機で確認済み。

結論。「less・psls 固有の問題」ではなく、「Bun で書いたプログラム同士をパイプで繋ぎ、かつ開始時のコンソールのコードページが UTF-8（65001）でない」ときに、Bun ランタイム自体が起こす文字化けだった。bun:ffi・less／psls のコードは一切関係ない（このプロジェクトのコードを一切含まない最小再現で確定）。実行後にコードページが 65001 に変わる副作用も、この Bun 側の処理が原因と見られる。

Bun の公式リリースノートに近い症状の修正記録がある（Bun v1.3.4 リリースノート: 「Windows console codepage not being properly saved and restored, which could cause garbled text on non-English Windows systems when using bunx」）。ただしこれは bunx 経由に限定された記述で、手元の v1.4.2（1.3.4 より新しい）の変更点にはこの話題への言及が無く、今回の再現条件（bunx を使わない、Bun スクリプト同士のパイプ）がこの修正の対象に含まれるかは確認できていない。

実運用でも結論と整合する例を確認済み: aichat -h | less（aichat は Rust 製 exe、Bun ではない）は問題なく表示される。「Bun 同士」でなければ起きないという結論と一致する。

済2026-09-21、oven-sh/bun#43660 として Issue を提出済み。Bun 側の対応待ちのため、このプロジェクト側では未解決のまま残る。

実装時に踏んだ落とし穴（9）: Windows PowerShell 5.1 は、Bun とは無関係に別の理由で全部化ける

2026-09-21、利用者が pwsh 7 と Windows PowerShell 5.1（同一マシン、cmd.exe とは別の端末）で node・bun の全組み合わせ（node→node ／ node→bun ／ bun→node ／ bun→bun）× コードページ（932・65001）を実測。

この課題の結末: less は Bun を使わない（psls は対象外）

済2026-09-21、利用者の判断。上記「落とし穴（8）」の Bun 自体のバグ（bun-to-bun パイプで文字化け）が実機で繰り返し発生し、Bun 側の修正を待つ運用は現実的でないと判断。化けるのは bun 同士のパイプだけ（実測済み）のため、less の起動を node 専用にすれば、psls | less（bun→node）は安全になる。

採用した範囲。less・less.cmd のランチャーから bun の分岐を削除し、node 専用にした（src/less/main.ts 本体は node・bun 両対応のまま変更していない。テストは両ランタイムで引き続き実行する）。psls は対象外（bun:ffi で Win32 API を直接叩いており node 版が無いため、bun のまま残す。詳細と理由は 課題 i260917-01 を参照）。psls 単体の実行（他コマンドとパイプで bun 同士を繋がない使い方）では、この Bun のバグは発火しない。

コードページ（SetConsoleOutputCP）は無意味だった: ConPTY の仕様

コードページの有効化・復元は当初セットで実装していたが、途中で無意味と判明したため削除した。実機での切り分け（bun:ffi 経由・PowerShell の P/Invoke 経由のどちらで SetConsoleOutputCP(65001) を呼んでも、成功は返るが外部の chcp に反映されない）により、Bun 固有の問題ではなく、この環境では呼んでも効果が無い API と判断した。日本語がそのまま出せているのはこの呼び出しのおかげではなかった。

原因を検索して特定した。Windows Terminal 等が使う ConPTY（疑似コンソール）の仕様で、「ConPTY のチャンネルは常に UTF-8 で、コードページの変換は疑似コンソールの内部で行われる」ため、SetConsoleOutputCP で変えた値が外側（本物のターミナル）には伝わらない（microsoft/terminal #9174）。同様の報告が PowerShell 本体側にもある（PowerShell/PowerShell #14941）。Bun・この環境固有の不具合ではなく、ConPTY 経由のターミナル全般で起きる仕様という結論。

終了時・末尾の表示（機能追加）

桁数を超える長い行の折り返し（未対応）

実機確認で判明（aichat -h の出力に端末の桁数を超える行があると疑われる）。今の実装は「lines[] の1要素＝画面の1行」を前提に、すべての行番号・カーソル位置（scrollDown／scrollUp／render／スクロール範囲）を計算している。1行が端末の桁数（例: 140桁のコンソールで140桁超）を超えると、端末側で自動的に2行以上へ折り返されて表示されるため、この前提が崩れ、以降の行番号がずれる。

対処案。

  • A: 長い行は表示幅に収まるように切り詰める（横スクロールなし）。実装は単純だが、はみ出した内容が読めなくなる
  • B（採用）: 折り返しを許容し、1論理行が何画面行を使うかを計算に入れる。2026-09-19、利用者の指示で採用。スクロール量・カーソル位置の計算を、論理行ベースから画面行（表示行）ベースへ組み替える必要があり、実装量は A より大きい

B の詳細設計（2026-09-19、まだ未実装）。

  • 端末の折り返し自体は「行末ちょうどで CRLF なら改行するだけ、1桁でもはみ出せば先に折り返してから続きを出す」という、pending wrap（DECAWM）の動作（実機で確認済み）。この動作に頼らず、こちら側で先に折り返しを計算して「画面行」を作っておく
  • 表示幅は既存の displayWidth()（ASCII・半角ｶﾀｶﾅ＝1桁、それ以外＝2桁）をそのまま使う
  • 右端に1桁しか残っていない位置へ2桁文字（漢字等）を表示しようとするときは、その1桁へ空白を入れてから折り返す（利用者の指示）。端末の pending wrap が「置けない文字は次の行へ送る」のと同じ結果になり、2桁文字が桁の途中で分断されない
  • この折り返し済みの「画面行」を、lines[] とは別の配列としてあらかじめ持っておく（利用者の指示：「空白(CRLF)いれてある状況と同様に仮想行を持っておく」）。scrollDown／scrollUp／render／clampTop／virtualLength は、今の lines[] の代わりにこの画面行配列を参照する形に置き換える（displayLine() 経由の [EOF]／[改行なし] は、画面行配列の最後の要素に対して同じロジックで付ける）
  • 端末の桁数（process.stdout.columns）が変わったら作り直す必要があるが、リサイズの検知は今回のツールでは未対応（別の話として残す）
